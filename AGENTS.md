# fosforo

## Overview

A Mac-first GPU-rendered phosphor oscilloscope and signal-analysis plugin, authored as a CLAP and rendered with Metal.

The display name is **Fósforo**; the repository, binary, and identifiers stay ASCII `fosforo`.

## Current state

Phase 3 of [the build plan](docs/plans/todo/2026-07-25-repo-foundation-and-phased-build-plan.md), four numbered steps in. **Phase 2 is closed.** The plugin loads in REAPER and Logic, passes stereo audio through, saves state, taps one channel into `src/dsp/ring.zig`, and reads a trailing 20 ms window on the render thread which `Renderer.frame` copies into a per-frame `MTLBuffer`. That the picture is the signal is the one claim no harness could close, because the drawable is `framebufferOnly` and reading it back would change the shipping renderer; it was settled instead by the host procedure in [#38](https://github.com/cboone/fosforo/issues/38), run against hash-verified installs and measured out of screenshots rather than judged by eye.

The trace now deposits additively into a persistent `RGBA16F` ping-pong accumulation pair ([#55](https://github.com/cboone/fosforo/issues/55)), so `shaders/scope.metal` encodes **two** render passes and three draws: `decay_fragment` then `trace_fragment` into the accumulation, and `resolve_fragment` into the drawable. Two chores the plan sequenced behind that one have also landed: `scripts/measure-trace` is committed here and its guard reads colour rather than counting shades ([#64](https://github.com/cboone/fosforo/issues/64)), and `zig build smoke-leaks` runs in CI at 40 cycles ([#63](https://github.com/cboone/fosforo/issues/63)), which refused the peak-RSS slope it was filed to add.

**What the pixels became is now checked automatically** ([#51](https://github.com/cboone/fosforo/issues/51)). `zig build smoke-trace` is a third smoke half, needing a device and no window and required in CI beside `smoke-gpu`: `Renderer` grew a `Surface` union and a second constructor, so the shipping `frame` resolves into a texture the backend owns rather than a drawable, and `src/gpu/measure.zig` reads the result back as rows, periods and implied samples. Ten planted defects were caught, #55's resolve gain among them.

**The resolve is finished** ([#60](https://github.com/cboone/fosforo/issues/60), [ADR 0019](docs/adr/0019-brightness-is-a-fixed-transfer-function.md)). It compresses accumulated energy through extended Reinhard and looks the result up in one of four gradients running to white, into a `BGRA8Unorm_sRGB` drawable so the arithmetic runs in linear light. The hot core ADR 0007 predicted is emergent and is executed rather than claimed: `smoke-trace` drives one deposit and thirty and reads `RGB(75, 189, 96)` and `RGB(255, 255, 255)` off the picture. The trace deposits a scalar now; there is no colour anywhere in `shaders/scope.metal`.

**The beam is geometry** ([#57](https://github.com/cboone/fosforo/issues/57)). Each inter-sample segment is an instanced quad and `trace_fragment` shades it by distance from the *segment*, so caps are round, joints have no wedge gaps, and the endpoints at `x = ±1` have area — which closed #38's 1914-of-1920 edge columns at 960 of 960 on a single frame. The width is **3.0 points**, in points rather than pixels so the rail clearance is scale-free, and the profile is the biweight `(1 - u²)²`, whose compact support is what keeps unlit pixels at exactly 0.0. The seam's raw-samples prediction held: still no `MTLVertexDescriptor`, still a plain `[]const f32`. Two consequences that were not anticipated. Overlap at joints retired the "one frame cannot deposit twice on a pixel" premise the tonemap's argument rested on, taking a moving trace from 1.0000 deposits to **2.6133**. And it made per-pixel brightness scale with samples per logical point, roughly `1 + 1.6 * s`, which would white out a moving trace at 192 kHz; `TraceUniforms.density` clamps that, and it is not velocity weighting because it is one number per frame that depends on nothing about the signal.

**What is left of the phosphor look is filed:** velocity weighting ([#58](https://github.com/cboone/fosforo/issues/58)) and bandlimited reconstruction ([#59](https://github.com/cboone/fosforo/issues/59)).

[#22](https://github.com/cboone/fosforo/issues/22) has landed, which was phase 2 work carried forward rather than a phase 3 step: it is the install-path ambiguity the provenance gotcha below describes, and it had already voided two verification runs of the kind every remaining issue here depends on. Every build now says which worktree and commit it came from ([ADR 0018](docs/adr/0018-stamp-provenance-without-namespacing-identity.md)), `CLAP_PATH` was established to work and is deliberately not used, because this project runs one host stream at a time, and two of the issue's four proposals were refused with measurements rather than built.

[#61](https://github.com/cboone/fosforo/issues/61) has landed, pulled forward from step 9 because shader hot-reload is worth five issues' worth of iteration rather than none. A debug build watches `shaders/scope.metal` and swaps the pipelines without restarting the host, which discharges a consequence [ADR 0009](docs/adr/0009-runtime-shader-compilation.md) recorded when it chose runtime compilation. It also settled the number the rest of phase 3 will be argued against: a source Metal has not seen takes about **40 ms** to compile, against 0.14 ms for one it has, so the compile runs on a thread of its own and hands finished pipelines to the render loop through a mailbox. [#59](https://github.com/cboone/fosforo/issues/59) defers the same "where does slow work run" question about its own upsampling and can reuse that shape.

[#56](https://github.com/cboone/fosforo/issues/56) has landed, and it inherited a value rather than a defect, exactly as this paragraph used to predict: because the white point derives from the decay, the provisional `decay_per_frame = 0.90` was a pure persistence knob, and turning a per-frame factor into a time constant was a matter of naming the rate it was anchored at. That rate is 60 Hz, so `palette.decay_tau_nanos` is `-(1 / 60) / ln(0.90)` or **158.19 ms** and every offscreen number the harness printed before it prints still. On this machine the trail is now twice what it was, because the panel runs at about 120 Hz where a per-frame 0.90 faded twice as fast; at 60 Hz nothing changed. `Renderer.frame` takes an absolute monotonic reading rather than an interval, and `CVTimeStamp` was refused with an argument recorded in `src/platform/displaylink.zig`.

**The next issue in the plan's order is [#58](https://github.com/cboone/fosforo/issues/58)**, with [#59](https://github.com/cboone/fosforo/issues/59) behind it.

## Non-negotiables

These are settled decisions recorded in [`docs/adr/`](docs/adr/). Do not relitigate them in code review; supersede them with a new ADR instead.

- **macOS on Apple Silicon only.** Not a portability oversight (ADR 0001).
- **Zig is pinned to 0.16.0.** `build.zig.zon` is the single source of truth and CI reads it. Compiler bumps are deliberate, scheduled work (ADR 0002).
- **The plugin is authored once, as a CLAP.** Never author an Audio Unit or VST3 directly; clap-wrapper projects outward (ADR 0003).
- **Metal must not leak above `src/gpu/iface.zig`.** That seam is load-bearing even though only one backend exists (ADR 0005).
- **No WebView UI** (ADR 0006).
- **Nothing reachable from the audio thread may allocate, lock, or make a syscall** (ADR 0010).
- **The GUI smoke harness is an executable behind its own steps, never part of `zig build test`** (ADR 0013).
- **`std.Io` is reached through the one instance in `src/platform/io.zig`, constructed with `init_single_threaded` and never with `Threaded.init`** (ADR 0015).
- **The ring's release store and acquire load are verified by `zig build ring-race` and guarded by the canary in `src/dsp/ring.zig`.** Weakening either without reading ADR 0016 is the failure this exists to stop (ADR 0016).
- **The vertical axis is absolute. The display never rescales itself to the signal, and over-scale rails rather than being hidden or clipped away** (ADR 0017).

## Development

```bash
zig build                  # produces zig-out/Fosforo.clap, and nothing else
zig build test             # unit tests
zig build impl             # libfosforo_impl.a alone, which is all CMake wants from Zig
zig build audio-unit       # produces build/assets/Fosforo.component, through CMake; slow, see below
zig build plugins          # both bundles, still in the worktree
zig build install-clap     # build the CLAP, install it, print the hash of what landed
zig build install-plugins  # the same for BOTH bundles, so a host result can be trusted
zig fmt --check build.zig src/
scripts/read-provenance zig-out/Fosforo.clap  # which branch and commit a built bundle came from
zig build install-clap && /Applications/REAPER.app/Contents/MacOS/REAPER 2>&1 \
  | grep --line-buffered fosforo   # the whole host loop; hot reload needs no env var
zig build validate-shaders # needs the Metal toolchain; see below
zig build smoke            # runs Metal and AppKit for real; needs a GPU and a window server
zig build smoke-gpu        # the half that needs no window: device, shader, pipeline
zig build smoke-trace      # the other half that needs no window: what the shader actually drew
zig build smoke-appkit     # the half that opens a window and cycles the editor
zig build smoke-leaks      # 400 cycles under `leaks --atExit`, judged by scripts/smoke-leak-check
zig build smoke-leaks -Dleak-cycles=40  # what CI runs; the criteria do not vary with depth, the cost does
zig build ring-race        # the history buffer on two threads under Thread Sanitizer; needs a Linux host
zig build-exe src/ring_race.zig -fsanitize-thread -lc -target x86_64-linux-gnu  # compile-check it from macOS
codesign --verify --strict --verbose zig-out/Fosforo.clap  # the bundle signature, not the linker's
git ls-files -z | xargs -0 shfmt -f | xargs shfmt -d      # no parser/printer options: they discard .editorconfig
git ls-files -z | xargs -0 shfmt -f | xargs shellcheck
typos                      # spell-checks the whole tree; allowlist and ignore patterns in typos.toml
ruff format --check . && ruff check .  # the one Python file; ruff.toml is what makes it visible
scripts/measure-trace shot.png         # reads a trace out of a screenshot, in backing pixels
scripts/measure-trace --refresh 60 shot.png  # a capture taken with the display pinned to 60 Hz
scripts/measure-trace --scale 1 shot.png     # a capture from a non-Retina display
```

`zig build` alone produces a loadable `.clap`, which REAPER opens natively. That is the day-to-day loop and it never invokes CMake.

**Every `install-*` step builds exactly what it installs, copies it to `~/Library/Audio/Plug-Ins`, and prints the hash of what landed; every other step stays in the worktree.** That invariant is the whole distinction between the steps whose names begin with "install", including Zig's own, which writes to `zig-out` and says so in `zig build --help`. It is also what closed #43: both install steps used to build the CLAP and neither built the Audio Unit, so `install-plugins` installed a component only if CMake happened to have been run in that worktree already, and a worktree where it had not kept whatever component another branch had installed and said nothing about it.

CMake is needed only for the Audio Unit that Logic requires, and it is much slower because it fetches the AudioUnit SDK. `zig build audio-unit` runs `scripts/build-audio-unit`, which configures only when `build/` is absent and builds `fosforo_all`; those are the two things worth getting right and they are no longer something to remember:

```bash
cmake -B build cmake/                       # what the script does once per worktree
cmake --build build --target fosforo_all    # and every time; not fosforo_auv2, see below
```

Validate with `clap-validator validate zig-out/Fosforo.clap`. CI runs it on every push against **both** `.clap` bundles, the Zig-built one and the clap-wrapper-built `build/assets/Fosforo.clap`, so neither is only a local step, and it asserts every bundle's signature alongside them. The Audio Unit has no equivalent: `auval` cannot see this component at all, for the reason in the gotchas below, so loading it in Logic is the only check there is.

## Releasing

A release is a single signed, notarized, stapled `.pkg` that places both bundles (ADR 0014). It is built locally and deliberately never in CI, because this repository is public and the alternative is Developer ID private keys in repository secrets. Three steps, each independently re-runnable, so a rejected notarization does not cost a rebuild:

```bash
export FOSFORO_SIGNING_IDENTITY="Developer ID Application: ..."
export FOSFORO_INSTALLER_IDENTITY="Developer ID Installer: ..."
scripts/build-release-bundles          # both bundles, hardened and timestamped
scripts/build-installer                # one pkg, signed with the Installer identity
scripts/notarize-installer dist/Fosforo-VERSION.pkg
```

`scripts/build-installer --unsigned` exercises packaging without a certificate. It cannot be notarized, is named so it cannot be mistaken for a release, and skips the input signature check, which it says out loud.

The credentials `notarytool` needs live in a keychain profile, never on a command line:

```bash
xcrun notarytool store-credentials "fosforo-notary" \
  --key ~/path/AuthKey_XXXXXXXX.p8 --key-id XXXXXXXX --issuer XXXXXXXX-...
```

An App Store Connect API key rather than an app-specific password, because it is scoped, independently revocable, and not the Apple ID password. The `.p8` downloads once and never again, so the copy on disk is the only copy; `.gitignore` covers `*.p8` for that reason.

**The certificates on hand expire 2027-02-01 and replacing them is outstanding** ([#30](https://github.com/cboone/fosforo/issues/30)). They were issued through Xcode under the G1 intermediate rather than G2, which caps both leaves at their issuer's expiry; the gotcha below has the full diagnosis and the check that surfaces it. Nothing already signed is at risk, because a secure timestamp outlives the certificate — what stops is signing anything new, and on current sequencing that happens before v0.1.0 is cut. Re-issue from the developer portal rather than Xcode, and do not revoke the superseded pair.

## Gotchas

- **`xcrun` caches tool lookups.** If `xcrun metal` reports the Metal toolchain missing right after installing it, run `xcrun --kill-cache`.
- **CLAP bindings come from preprocessed headers.** Zig 0.16's `translate-c` mishandles `#pragma once` under path aliasing, so `build.zig` runs the headers through `zig cc -E` first. Object-like macros do not survive that; the ones that matter are restated and tested in `src/clap/c.zig` (ADR 0004).
- **`unnamed_0` is toolchain-generated.** The anonymous union in `clap_window` is reached only through `clap.cocoaView()`. Re-verify after any Zig upgrade.
- **Metal's and AppKit's constants are hand-restated.** Their headers are Objective-C, so `translate-c` cannot read them the way it reads CLAP's. `MTLPixelFormat`, `MTLLoadAction`, `MTLStoreAction`, and `MTLPrimitiveType` live in `src/gpu/metal/renderer.zig`, and #60 added two of the first — `BGRA8Unorm_sRGB` at 81 and `RGBA32Float` at 125, both read out of `MTLPixelFormat.h` rather than recalled, which is the practice that caught the line-strip enum; `NSView.autoresizingMask` lives in `src/platform/objc.zig`. Unlike the restated CLAP macros in `src/clap/c.zig`, there is no surviving header symbol to test them against. They are ABI values Apple cannot renumber, and a wrong one shows as a black or garbled drawable rather than as anything subtle.
- **`@embedFile` reaches `shaders/` through the import table.** It resolves relative to the importing file and cannot escape the module root, which is `src/`. `build.zig` adds the shader with `addAnonymousImport`, which is why `@embedFile("scope.metal")` works from `src/gpu/metal/`. Keeping shaders outside `src/` is deliberate: `zig build validate-shaders` treats that directory as shaders rather than as Zig.
- **Keep three deployment targets in step:** `build.zig`, `cmake/CMakeLists.txt`, and `macos/Info.plist` all specify macOS 11.0.
- **`build.zig` runs `git` at configure time, and three things about that are easy to get wrong.** It stamps the branch and commit into every binary (ADR 0018), and none of the following is stylistic. **`git rev-parse --abbrev-ref HEAD --short HEAD` prints the branch name twice**, because `--abbrev-ref` is sticky across every ref that follows it, so a combined call silently puts the branch in the field meant for the commit and produces a line that is wrong while still looking well-formed; use two calls. **Failure is a supported state, not an error**: `b.runAllowFail` with `.ignore` on stderr, never `b.run`, because `b.run` calls `process.fatal` and a tarball built from `build.zig.zon`'s `.paths` carries no `.git` at all, which must yield `branch=unknown` and a clean build. And **this costs ADR 0009 nothing**, on a stronger precedent than `/usr/bin/codesign`: `b.dependency("objc", ...)` already runs zig-objc's build function at configure time, which executes `xcrun` to find the SDK that nothing here can link Cocoa or Metal without, so a subprocess and a working Xcode or CLT install were both hard requirements before this existed. Where `xcrun` failing is fatal, `git` failing is not. The cost that is real: the option values feed the module's cache key, so the first build after each commit is a full rebuild.
- **The AUv2 build rewrites its own `Info.plist`.** Two `POST_BUILD` scripts correct what clap-wrapper generates, and the `clap-wrapper` CI job asserts both results independently, because a rewriting step cannot detect its own absence. `cmake/narrow-au-resource-usage` strips a hardcoded `resourceUsage` dictionary claiming network and whole-filesystem access, emitted next to the `sandboxSafe` flag that Apple documents as mutually exclusive with it; it no-ops safely if clap-wrapper stops emitting it, so re-check when the pin moves. `cmake/set-au-display-name` replaces the generated name and description, for the reason in the display name bullet below. Both must stay ahead of the signing command, which is the third and last `POST_BUILD` command on that target; see the next bullet for why the order is load-bearing.
- **Every bundle is signed by the build, and two different signatures are involved.** The linker ad-hoc signs the Mach-O binary on arm64 unconditionally, which is why these bundles load at all, but that signature covers only the binary: it reports `flags=0x20002(adhoc,linker-signed)` and `Sealed Resources=none`, and `codesign --verify` rejects the bundle with `code has no resources but signature indicates they must be present`. The bundle signature is a separate thing and nothing upstream supplies it. clap-wrapper's only `codesign` calls sign its own generated AUv2 build helper, `wrap_clap.cmake` has none at all, and `make_clapfirst.cmake` states that signing is the consuming project's decision. So `build.zig` signs `zig-out/Fosforo.clap` and `cmake/CMakeLists.txt` signs both bundles it builds, all three ad-hoc, and CI asserts all three. Override the identity with `zig build -Dcodesign-identity=` or `-DFOSFORO_CODESIGN_IDENTITY=`, and both call sites then add `--timestamp` and `--options runtime` as well, because notarization rejects a submission missing either. Those two follow from the identity rather than being switches of their own, so a distributable signature cannot be half-configured, and neither is ever applied ad-hoc: `--timestamp` would make a plain build need the network, and an ad-hoc signature has no certificate whose expiry a timestamp could outlive. `scripts/assert-adhoc-signature` guards that in both CI jobs, and it asserts a negative `codesign --verify` cannot: a conditional that leaked would still produce a valid signature, so the first symptom would be a job hanging on Apple's timestamp server rather than failing anything legible. It checks three independent marks, because they fail independently: the `runtime` flag, a `Timestamp=` line, and an `Authority=` chain. The positive direction has no CI equivalent, since no runner has a certificate, and is checked by hand. **The AUv2 signing command must remain the last `POST_BUILD` command registered on that target,** because signing seals the `Info.plist` the two scripts above rewrite: sign first and `codesign --verify` reports tampering rather than a missing signature, which is worse than not signing. That is also why the `clap-wrapper` job runs `codesign --verify` and both `--check` scripts together and treats the three as one test: signing in the wrong order passes the two `--check` runs and fails the signature, while a dropped signing step fails only the signature. `/usr/bin/codesign` is a base-OS binary rather than an on-demand Xcode component, so none of this costs the hermetic build ADR 0009 protects. Every automated invocation names it by absolute path rather than resolving it through `PATH`, so that stays true even where a wrapper or shim shadows the name; the commands above are the short form because a human types those.
- **Releasing involves two different certificates, and one of them is invisible to the usual check.** Bundles are signed with Developer ID **Application**; the pkg is signed with Developer ID **Installer**. `security find-identity -v -p codesigning` lists the first and **not** the second, because the `codesigning` policy does not match installer certificates, so a null result there is not evidence that one is missing. Check with `security find-identity -v` and no policy argument, and confirm the Application certificate appears in the same output as a positive control. An Apple Development certificate is the trap worth naming: it signs, timestamps and hardens exactly like a Developer ID Application one and passes `codesign --verify --strict`, and it will never notarize. Nothing short of reading the `Authority=` line tells them apart, which is what `scripts/assert-distributable-signature` exists to do.
- **A Developer ID certificate's expiry is capped by its issuer's, and Xcode can hand you a nearly-dead issuer.** The pair issued on 2026-08-04 expire 2027-02-01 `22:12:15`, six months out rather than the usual five years, and both match that instant *to the second* despite being issued 33 seconds apart. That is Apple clamping a leaf's validity to its issuer's `notAfter`: Xcode's Manage Certificates panel issued them under the G1 `Developer ID Certification Authority`, which expires exactly then, rather than under `OU=G2`, which runs to 2031-09-17 and is already trusted in the login keychain. Nothing in the usual toolchain shows this. `security find-identity -v -p codesigning` prints neither expiry nor issuer, and `codesign -dvv` names the authority without its validity window; `security find-certificate -c "<name>" -p | openssl x509 -noout -issuer -dates` is the only check that surfaces it. Signed artifacts are unaffected, because a secure timestamp makes a signature outlive its certificate, which is the whole reason `--timestamp` is mandatory here; what expires is the ability to sign anything new. Issue replacements from the developer portal rather than Xcode, and do not revoke the superseded pair: revocation is for compromise and can invalidate already-distributed software. See issue #30.
- **`codesign --verify` and `spctl --assess` answer different questions, and passing the first says nothing about the second.** `codesign` asks whether the signature is internally consistent; Gatekeeper asks whether this machine will run the thing. Worse, a locally built file has never carried `com.apple.quarantine`, so assessing one is not a test of the download path at all. The only honest check is to fetch the release from a URL **in a browser**, confirm `xattr -p com.apple.quarantine` returns a value, and assess that copy. `curl` does not set the attribute and cannot substitute. `scripts/notarize-installer` runs the local assessment and says so, rather than implying it proved more than it did.
- **Only the pkg is stapled, not the bundles inside it.** Files laid down by an installer do not receive `com.apple.quarantine`, so the pkg's ticket is the one Gatekeeper consults and a per-bundle ticket would be a notarization round trip nothing reads. If installed bundles ever start being refused, the fallback is a first submission over a zip of the two bundles, stapling each before packaging.
- **`cmake --build` no longer touches `zig-out`, and the optimize-mode split it caused is still there.** Two facts that used to travel together and now do not. `cmake/CMakeLists.txt` drives Zig itself, through an `ALL` custom target, because the only thing CMake wants from Zig is `libfosforo_impl.a`. That target used to run a bare `zig build --release=fast`, which also reassembled the Zig-built bundle and signed it ad-hoc, since it passes no `-Dcodesign-identity`: a CMake build silently replaced whatever `zig build -Dcodesign-identity=` had produced, and every check afterwards read a different file than the one that was signed. It now runs `zig build --release=fast --prefix build/zig impl`, and **both halves of that are load-bearing.** The `impl` step assembles no bundle and signs nothing; the prefix keeps its ReleaseFast archive out of `zig-out/lib`, where it would otherwise race a Debug one from any concurrent `zig build`. Measured rather than assumed: the CLAP's hash *and* its mtime are unchanged across a full `cmake --build`, and `codesign --verify` passes afterwards. The ordering in `scripts/build-release-bundles` is consequently no longer load-bearing, and is kept only because reversing it buys nothing. What survives unchanged is the optimize-mode disagreement: `standardOptimizeOption` declares no default, so a plain `zig build` is **Debug** while everything CMake triggers is **ReleaseFast**, and after `zig build install-plugins` the installed CLAP is Debug next to a ReleaseFast Audio Unit. That is right for local work, since Debug is what emits the render meter REAPER can show and Logic can show nothing under any mode, and wrong for a release: a shipped CLAP must be built `--release=fast` explicitly, which is what `scripts/build-release-bundles` does.
- **The hardened runtime costs this plugin nothing, and an entitlements file would be inert.** Notarization requires `--options runtime`, and the obvious worry is that ADR 0009's runtime shader compilation needs `com.apple.security.cs.allow-jit` or one of the `allow-unsigned-executable-memory` family. It needs neither, for two independent reasons, both measured rather than reasoned about. First, `newLibraryWithSource:` compiles **out of process**: Metal hands the source to `MTLCompilerService.xpc`, an Apple-signed XPC service inside `Metal.framework`, so no executable memory is ever created in the caller's address space and there is nothing for a JIT entitlement to permit. A standalone binary signed `--options runtime` with no entitlements at all compiles `shaders/scope.metal` and resolves both functions, which is a *stricter* case than the plugin's. Second, entitlements attach to a process, and a plugin never gets one: it is loaded into the host's address space, so the host's entitlements apply and its own are ignored. REAPER runs hardened and carries `allow-jit`, `allow-unsigned-executable-memory` and `disable-library-validation`, that last being what lets it load a bundle signed by another team at all; Logic hosts AUv2 out of process in Apple's `AUHostingServiceXPC`, which carries the latter two. So there is deliberately no `entitlements.plist` in this repository, and adding one would change nothing about how the plugin runs. Re-measure before assuming otherwise; do not add entitlements speculatively.
- **A host loads what is installed, not what you just built, and the two are different acts.** `zig build` and `cmake --build` write into the worktree; REAPER and Logic read `~/Library/Audio/Plug-Ins/`. Nothing connects them but a copy someone has to remember to make, and this repository is normally checked out as several worktrees on several branches that all compete for that one location, so the installed bundle belongs to whichever of them copied last. **Confirm provenance before trusting any result a host gave you**, because the failure is silent and reads as a pass: a branch that added a resizable editor was once "verified" against an installed build whose `can_resize` returned false, where the window edge could not be dragged and nothing happening was the only available outcome.

  ```bash
  shasum -a 256 ~/Library/Audio/Plug-Ins/CLAP/Fosforo.clap/Contents/MacOS/Fosforo \
                zig-out/Fosforo.clap/Contents/MacOS/Fosforo
  shasum -a 256 ~/Library/Audio/Plug-Ins/Components/Fosforo.component/Contents/MacOS/Fosforo \
                build/assets/Fosforo.component/Contents/MacOS/Fosforo
  ```

  Two identical hashes mean the host is loading the branch under test; anything else means the result describes some other build. **`zig build install-plugins` builds both bundles, does both copies and both comparisons**, and printing the hashes is the point of it rather than a flourish; reach for it instead of the manual `cp`, which is how the Audio Unit went stale twice.

  **Every bundle now says which worktree built it, which is what the hashes above cannot do.** `build.zig` asks git at configure time and `src/build_info.zig` stamps a `fosforo-build:` line into the binary, so `scripts/read-provenance` answers "whose build is this?" from an installed file with nothing else in hand (ADR 0018). `install-plugins` reports it on every path, including the outgoing bundle it is about to delete, which is the moment this repository's central hazard actually happens and used to happen in silence:

  ```text
  clap: 9d15b5c59185  /Users/…/Fosforo.clap
  clap:   built from chore/add-build-provenance 4105425
  clap:   replaced main 3745df2
  ```

  A hash comparison answers "is this the build I just made?" and can only answer it when this worktree has a build to compare against; provenance answers the other question, which is the one that has cost time. `--check` asserts the marker is present, and CI runs it on the Zig-built CLAP and on both CMake-built artifacts, because the marker survives `--release=fast` only as a claim about the optimizer until something checks.

  **The Audio Unit is the half that goes stale, and the way it does so is by nothing happening.** `install-plugins` builds it now, so the ordinary path is covered, but `install-clap` deliberately does not, and there is no copy to compare when nothing was built. A component installed by some other branch then stays where it is, and a `shasum` of it against `build/assets/` is a comparison against a file that does not exist. That is why `scripts/install-plugins` reports an installed component it cannot account for, with its hash, its modification date *and* now the branch that built it: a date invites an inference and a branch name ends the question. It was what was missed once already (#43). It is a report rather than a refusal, because the CLAP-only loop is the common one.

  **A symlinked Audio Unit is invisible to macOS, and this is the trap the report exists to catch.** [#22](https://github.com/cboone/fosforo/issues/22) proposed pointing the shared `Components` directory at the active worktree; it was built and refused, because the component is then never registered. Logic's own scan log, `~/Library/Caches/AudioUnitCache/Logs/AUScan*.plist`, is the only instrument (`auval` cannot see this component at all), and it reads 60 Audio Units with `Fósforo` present as a copy, 59 with it absent as a symlink, and 60 again when the copy is restored. **Give the registrar time to settle before relaunching Logic**, or the reading is worthless: a first attempt read 59 for the copy as well, and only its control caught that. Nothing here creates such a link any more, and `install-plugins` detects, explains and replaces one made by hand.

  **One host stream at a time, and that is the working rule rather than a constraint to route around.** Only one worktree verifies against a host at any moment. So the loop is: install, launch, read. No `CLAP_PATH`, no moving bundles aside, no second copy of anything claiming `com.catamount.fosforo`.

  ```bash
  # Launch the binary, not `open -a`: an app started through LaunchServices does
  # not inherit the calling shell's environment, and this is also how clap.log is
  # read at all. Two details in that pipe are load-bearing, see below.
  zig build install-clap
  /Applications/REAPER.app/Contents/MacOS/REAPER 2>&1 | grep --line-buffered fosforo
  ```

  **`2>&1` and `--line-buffered` are both required, and each fails differently.** `src/clap/log.zig` mirrors through `std.debug.print`, which writes to **stderr**, so a bare `| grep fosforo` filters stdout and lets every one of the plugin's own lines through unfiltered — the pipe appears to do nothing. And `grep` block-buffers when its output is not a terminal, so the once-a-second `rendering at N Hz` meter arrives in bursts minutes apart, which reads exactly like a render loop that has stopped.

  **`zig build install-clap` is the whole of the provenance answer.** It builds exactly what it installs, copies it, and prints the hash *and* the provenance of what landed beside the provenance of the bundle it just replaced, which is why [ADR 0018](docs/adr/0018-stamp-provenance-without-namespacing-identity.md) exists. That is a stronger answer to "am I looking at my build?" than avoiding the shared directory is, and nothing has to be moved aside or restored afterwards.

  **Hot reload needs no environment variable under this rule.** `build.zig` bakes the absolute path of this worktree's `shaders/scope.metal` into every debug build, so a bundle installed from here is already aimed at here and saving the file changes the picture in the running host. `FOSFORO_SHADER_PATH` survives as the escape hatch for a worktree that has been *moved* since it was built, and for aiming one installed bundle at a different checkout; neither is the ordinary case.

  **`CLAP_PATH` was measured, works, and is deliberately not used.** `clap/entry.h` says a host must query it, `:`-separated and searched recursively, in addition to the standard locations, and REAPER 7.79 honours it: with `~/Library/Audio/Plug-Ins/CLAP` empty, a bundle in a worktree's `zig-out` is found, scanned and instantiated, and each instantiation prints its own provenance line naming that worktree. [#22](https://github.com/cboone/fosforo/issues/22) established that. What it buys is concurrency this project does not want, at the cost of a hazard it does: because the variable is *additive*, both copies claim `com.catamount.fosforo`, and REAPER caches CLAP bundles by filename with no path at all. With both present it loaded the `CLAP_PATH` copy and kept one cache entry — but the specification says nothing about precedence, and that is not something to build a verification run on. Recorded so the measurement is not repeated, not so the route is taken.

  **The Audio Unit has no equivalent and never did.** `AudioComponentRegistrar` scans only the two standard `Components` directories, there is no `AU_PATH`, and the symlink route is closed by the bullet above. So the component was always exclusive to one worktree at a time, which is the other half of why one stream is the rule: half the verification could not parallelize whatever the CLAP did.

  **The GPU and the window server are the second exclusive resource**, and they bind independently of the install path. `smoke-appkit` and `smoke-leaks` need them, since two harnesses cannot both open windows and time each other's frames. `smoke-gpu` and `smoke-trace` are exempt, since both acquire a device and neither opens a window, which is what makes them the cheap checks to run while something else holds a window open. Compiling, `zig build test` and `validate-shaders` contend for neither and overlap freely.

  **`clap-host` is what reads a release build's diagnostics, and that is now the whole of why it is here.** It takes an explicit path, so it reads the worktree rather than `~/Library/Audio/Plug-Ins/`, with no install step and no hash comparison to get wrong. Its original billing was concurrency — a second stream confirming a render while another owned the installed bundle — and the one-stream rule above retires that: there is no second stream. What survives is the thing nothing else does, which is that a `--release=fast` plugin has no readable diagnostic channel anywhere else. REAPER accepts `clap.log` and discards it, Logic cannot be launched from a terminal at all, and the `stderr` mirror is compiled out of a release build. It cannot test resizing and is not a load test, so it does not replace REAPER or Logic; what it does mean is that a second stream can confirm a render, exercise the editor lifecycle and read `clap.log` while another stream owns the installed bundle. The build plan's phase 3 section carries the working order this implies. [#22](https://github.com/cboone/fosforo/issues/22) has since relaxed the first constraint through `CLAP_PATH`, which REAPER honours, so `clap-host` is no longer the only way to run a CLAP out of a worktree; there is still no equivalent for the Audio Unit, so that half stays exclusive whatever happens.
- **A minimum editor size binds the view, and no host is obliged to bind its window to it.** `clap_gui_resize_hints_t` carries resizability and an aspect ratio and no bounds at all, so `adjust_size` and `clap_host_gui.request_resize` are the only two mechanisms, and both are requests. REAPER 7.78 implements `request_resize`, returns true, and keeps the plugin's view at the minimum; its own FX window still drags smaller, clipping the view inside it. **That is REAPER's behaviour rather than a defect here, established with a positive control:** a third-party plugin with a fixed size in Logic is also freely resizable in REAPER, so REAPER does not constrain its window to any plugin's declared size. `Editor.pushBack` is still worth its lines, because without it REAPER leaves the `NSView` a few points under while the drawable sits at the minimum, and the two disagree about the surface being rendered into. Whether another host binds its window is untested; only REAPER and Logic are available here.
- **A host can send a negative window dimension, and CLAP types them `u32`.** Dragging an editor's bottom edge up past its top makes REAPER send heights of 4294967295 and 4294967274, which are -1 and -22 computed as signed `CGFloat`. `clampAxis` in `src/clap/gui.zig` collapses anything above `i32`'s range to the minimum rather than the maximum, because no display is two billion points across and a drag that ran past zero is what actually happened. Left unguarded this reached Metal: the mailbox saturated the value to 65535 and asked for a 960x131070 drawable, eighty times the texture limit, from a thread with no way to refuse.
- **The background is indistinguishable from a black window by eye, so do not use your eyes on it.** The drawable shows byte `RGB(5, 5, 8)` wherever no energy has landed: correct for a phosphor scope's background, and identical to failure at a glance. **Since #60 that value is not a literal in the shader at all** — it is entry zero of every gradient in `src/gpu/palette.zig`, which is that issue's own question about whether the background stays a literal, answered by construction. The drawable is `BGRA8Unorm_sRGB`, so what the palette holds is the linear value `5 / (255 * 12.92)` and the hardware encodes it on write; `checkResolve` asserts the byte the picture actually shows equals the palette's value at zero energy, so the two cannot drift. It inherited that literal from `clear_fragment`, which #55 deleted along with the pass it owned, and keeping the exact value is what keeps `scripts/measure-trace`'s crop working. Two checks do work. Launch the host from a terminal and read the once-a-second `rendering at N Hz` line that debug builds emit, which is the only positive statement that frames are being presented. Or screenshot the editor and sample a pixel: the giveaway is the blue channel sitting two or three above red and green, mirroring the shader's `0.03` against `0.02`, which neither an unrendered layer nor a host's own background reproduces. **That check works at the background and nowhere else,** for a reason established later and recorded below: a screenshot carries the display's colour space rather than the framebuffer's, and the background is the one value where that conversion is identity. `zig build smoke-appkit` asserts the same thing automatically through `Editor.framesPresented`, which exists because this deliverable cannot be seen (ADR 0013). [#45](https://github.com/cboone/fosforo/issues/45) proposed changing the colour so that looking would prove something, and was closed as subsumed by [#38](https://github.com/cboone/fosforo/issues/38) on the grounds that the trace is what makes the render visible, so the background does not have to be. **The trace over it did not retire this bullet, it moved it.** A trace stuck flat at zero looks correct against silence, and a window frozen several seconds ago looks identical to a live one against steady material, so "I can see a waveform" is still not the check. The two that separate those cases are in the plan's verification section: stop the transport and confirm the trace goes flat within a frame or two, and count periods against the known 20 ms window rather than judging the shape.
- **`zig build smoke-trace` is what answers "what did the pixels become", and #55 is why it exists.** The accumulation shipped with a resolve gain of `1 - decay`, which normalises a *stationary* trace to the colour the unaccumulated line strip drew. The arithmetic is correct and the case it optimises is the wrong one: a sliding trace never lights the same pixel twice, so it never accumulates, so the gain divides every real signal by ten. A 100 Hz sine rendered as a black display, measured afterwards at peak green 53 against 255. **That passed 160 unit tests, `smoke-gpu`, `smoke-appkit`, `smoke-leaks`, `clap-validator` and the Metal validation layer**, and was found by eye in under a minute. `Editor.framesPresented` answers whether frames are presented, the counters answer whether resources balance, and `MTL_DEBUG_LAYER` answers whether the bindings are legal. [#51](https://github.com/cboone/fosforo/issues/51) added the check that answers the remaining question: replanted, that exact gain now fails `smoke-trace` with a channel 224 levels out.

  It renders through the shipping pipeline into a texture the backend owns, and it is **not** a readback of the drawable, which ADR 0013 refuses because `setFramebufferOnly:` is a property of the shipping renderer. `Renderer` carries a `Surface` union, `init` and `initOffscreen` share every acquisition, and `frame` branches at exactly three points: where it takes a colour attachment, where it binds one, and whether it presents. Change any of those three and the offscreen path stops being the shipping path, which is the whole basis for believing its numbers.

  **It reads two surfaces and the pairing is the point.** The accumulation is linear and unclipped, so the geometry assertions survive #57, #58 and #60 with changed numbers rather than a rewritten instrument; the resolved picture is the only place a defect confined to the resolve can show. The resolve check compares the two against each other rather than against the beam's literal, so it assumes nothing about how many segments covered a pixel.

  **It has not replaced a host.** It measures one frame of a window it supplied itself, so it says nothing about the audio path, the ring, the display link, or whether a host's editor is live: a trace stuck flat and a window frozen five seconds ago both pass it. The host procedure in [#38](https://github.com/cboone/fosforo/issues/38) is still what covers those.
- **`scripts/measure-trace` is the instrument that reads a picture, and it is this project's display contract restated in Python rather than a general tool.** Every number in #38's verification came out of it: the level sweep's peak rows, the plateau widths, the period counts, the implied sample values, all of them quoted in this file and in ADR 0017's reasoning as measurements. Point it at a `screencapture -o -x -t png -W` of the editor and it finds the drawable inside the window by itself, then reports rows and the sample values they imply. **Run the copy in the worktree under test**, never one from elsewhere: it restates constants from `src/gpu/iface.zig` and `src/gpu/palette.zig`, and a branch that moves one moves the tool in the same commit, so `main`'s copy is the wrong instrument for a branch. A stale copy lived in `~/Music/fosforo-test-tones/` until 2026-09-02, five times smaller than the committed tool and predating the tonemap, the palette and the centroid; it would have run and produced confident numbers against a mapping the shader no longer uses. That directory now holds a `README.md` saying so, and deliberately holds no copy and no symlink. **It restates constants it does not own**, `trace_full_scale` and `trace_rail` from `src/gpu/iface.zig` and the background, the core exponent, the white headroom, the four tints and `decay_tau_nanos` from `src/gpu/palette.zig`, and the test in `src/gpu/metal/renderer.zig` that reads the script as text is the only thing linking them; without it a constant that moved would leave the tool confidently reporting against the old mapping. It cannot measure any other oscilloscope, which is why it lives here and not in `audio-tools`, and it is the second half of one procedure: render, play, capture, measure. The first half went the other way, to `audio-tools`, and the bullet below on the test signals carries its new path and the invocation that reproduces this project's set. **Three things it will not tell you.** Under persistence the *lit rows* are the envelope over the fade rather than this frame's beam, so it prints a line saying so whenever a trail is lit; that is #55 changing what the measurement means rather than a defect. **#57 answered it for the reported peak and trough, which are now centroids**, and the way it first got that wrong is worth keeping: a centroid over the whole *column* averages the trail, so a 0.5 sine read `+0.0359` — silence — while the lit rows either side implied ±0.505 correctly. The centroid is taken over a column's first and last contiguous lit *run* instead, which reads ±0.5000 exactly on the same capture. `src/gpu/measure.zig` sums whole columns and is right to, because the harness drives one deposit into a cleared accumulation and there is no trail to average. It cannot see a palette other than the one the shader selects, so `--palette` has to be given to match `palette_row`. And since #56 it cannot see the **refresh rate the capture was taken at**, which now sets the white point: `--refresh` defaults to 120 for this machine's panel, and the two numbers it reaches are affected very differently. The lit threshold barely moves — 120.62 at 48 Hz to 120.33 at 240, three tenths of a byte, though it straddles a rounding boundary so the printed integer goes 121 below about 90 Hz and 120 above. The energy behind the brightest pixel moves a great deal, because inverting the curve near saturation is where the white point does its work: `t = 0.9` reads 5.0 deposits at 60 Hz and 7.0 at 120. Pass `--refresh` before quoting that number off a capture taken at anything but 120.

  **#60 was expected to end the green-channel isolation and did not, which is now a constraint rather than a reprieve.** Every gradient's largest tint component is exactly 1.0, so that channel stays an affine readout of the tonemapped value and the isolation, the guard and every published row survive with re-derived numbers. A re-tint that broke that property would change the meaning of every channel readout in this project at once and fail nothing but the one test written for it. What did change is `--threshold`, which is now **derived from an energy** rather than defaulted to 64: a fixed byte would have silently doubled the persistence envelope this tool reports, from about thirteen frames of trail to twenty-eight, because the sRGB toe moved what a byte means.

  **`zig build smoke-trace` did not retire it, and the two answer different questions.** This one reads a *host's* screenshot, so it covers the audio path, the ring, the display link and the compositor, and it is the only thing that can tell a live editor from one frozen five seconds ago. The harness renders a window it supplied itself into a texture, so it says nothing about any of that and everything about the shader's arithmetic. Two consequences: #38's host procedure still needs this tool, and the premise its guard rests on is asserted executably by the harness. **That premise changed with #60 and the assertion moved with it**: the deposit no longer carries a colour, so `checkBeamIsOneColour` and its measured ray of 0.2998 and 0.4500 are retired, and `checkDepositIsScalar` asserts instead that the accumulation's four channels agree to 0.00000 at every lit pixel — which is what now makes green the energy. `src/gpu/measure.zig` is its Zig counterpart and deliberately not a port: it reads linear floats rather than an 8-bit picture in a display's colour space, so it needs neither the crop, nor the guard, nor the sRGB conversion. **The half-pixel disagreement between them is gone**, which #57 forced rather than tidied: this tool omitted the pixel-centre term, which was defensible while every assertion was stated in a one-pixel band, and the centroid took the harness's tolerance to a twentieth of a pixel. At that point the offset was ten times the tolerance and the two instruments disagreed about captures they had both measured correctly. Numbers published before #57 were read off a lit edge and are half a pixel from comparable; the ones after it agree exactly.
- **Its guard refuses a capture by colour, its ray became a curve under #60, and its margins are the one thing here still carrying pre-#60 numbers.** The structure survived because the premise generalised: the picture is still a one-dimensional manifold, now a gradient rather than a straight ray, and the dominant channel still inverts it *exactly* because every gradient's largest tint component is 1.0. So the guard decodes the capture to linear, inverts on that channel, predicts the others through the palette, and re-encodes to compare in levels. **Re-derived from two REAPER captures rather than carried forward**, since the pre-#60 pair was measured against a straight ray: a 100 Hz sine at 0.5 and a level-2.000 sine, both at 1920x1080, read after the sRGB conversion.

  |          | sine 0.5 | level 2.000 |
  | -------- | -------- | ----------- |
  | lossless | 0.02%    | 0.02%       |
  | JPEG q95 | 22.19%   | 34.39%      |
  | JPEG q80 | 30.35%   | 43.70%      |
  | JPEG q60 | 28.34%   | 41.96%      |

  Three orders of magnitude, the same margin the ray had, so the threshold sits 25x above a good capture and 1100x below a recompressed one and needs no calibration against the machine it runs on. A tolerance of 1 would refuse a good capture at 2.01% and 3.49%, which is what makes this a floor rather than a preference.

  **#57 moved the tolerance from 2 to 3, and the old value was refusing good captures.** A falloff skirt puts about a percent of the drawable in the gradient's toe, where the sRGB curve runs at 3294.6 bytes per unit linear, and quantization there reaches three levels where a one-pixel trace only ever reached two. Re-derived against the same two captures the table above uses, each compared with itself recompressed:

  |             | lossless | q95    | q80    | q60    | lossless    | q95    | q80    | q60    |

At 3 they read 0.26% and 0.15%, leaving the threshold 1.9x and 3.3x above a good capture and 137x below the worst recompression — the same three orders of magnitude the pre-#57 pair had, which is what keeps it needing no calibration against the machine it runs on.

  **`SATURATED` stopped being inert here, which is what it was kept for.** It removed 3774 pixels of a pre-#60 capture and two of a post-#60 one; a post-#57 level-2.000 capture has **8338** of 2,073,600 excluded, because overlap at a wide beam's joints reaches the white point where a one-pixel line did not. The note that predicted #58 would make it matter again was right about the direction and early about the issue. **`SATURATED` is nearly inert and is kept for when it is not**: it removed 3774 pixels of a pre-#60 capture and removes two of a post-#60 one, because almost nothing reaches the white point while `white_headroom` stays provisional.
- **The shade count the guard replaced was a trap #55 set, and #60 retired what remained of it.** The old rule refused any drawable holding more than 32 distinct green levels, on the premise that a lossless capture holds two. True of a trace with no persistence and false the moment one fades: measured on a synthetic capture reproducing the shader's arithmetic, a moving trace with a trail holds **193**, so every good PNG was refused with a message telling the author to recapture it. What replaces it is a fact about the shader. Everything on the drawable is `background + c * beam`, because every deposit is the same colour and the decay multiplies the whole vector, so green predicts red and blue exactly and a fading pixel slides *along* that ray rather than off it. Chroma subsampling and ringing leave it, and so does a capture taken on a scaled display, which the count could not see at all. The margin is three orders of magnitude: 0.00% off the ray for a lossless capture against 32% to 43% for JPEG at every quality from 95 down to 60. **The count itself is now useless as a trail detector**, because a gradient puts dozens of levels in a single frame whether or not anything is fading; the tool reports it for continuity with #38's tables and reads the lit *rows* to decide whether a trail is present. **Below that the crop refuses first**, because a quality-40 JPEG destroys the exact `RGB(5, 5, 8)` `find_drawable` looks for, which is why that message names recompression as well as "not the editor".
- **A screenshot is written in the display's colour space, not the framebuffer's, and the discrepancy hides at exactly the value everyone checks.** The plugin writes into a `BGRA8Unorm_sRGB` drawable, so the render-output stage encodes its linear output on write; the compositor treats the stored bytes as sRGB, converts them for the display, and `screencapture` writes *those* numbers with the display's profile attached. **The stored bytes are the same ones format 80 stored before #60**, which is the whole reason that change was arranged to preserve them — what moved is which linear value produces a given byte, not the byte. On this machine `sips -g profile` reports a capture as **Display P3**, so a screenshot's pixels are not the shader's pixels. **#60's format change is invisible here, which was measured rather than argued**: a `clap-host` capture converted out of the display's profile reads exactly `RGB(5, 5, 8)` across 99.9% of the drawable, the same bytes format 80 put on screen, and silence reads `RGB(255, 255, 255)` on row 539 because a stationary trace dwells to the white point. The error is proportional to saturation and vanishes at black: measured on a REAPER capture at 2018x1778, the background survived as exactly `RGB(5, 5, 8)` while red at green 200-240 read **119 against the 70.9 the beam colour implies**, and 2.74% of the drawable sat off the colour ray. `scripts/measure-trace` therefore converts to sRGB before measuring anything, which takes that capture to 0.0074% off the ray and red to 70.9 against a predicted 70.9. **Two consequences worth carrying.** The pixel-sampling advice above is still correct and is now known to be correct *only* at the background, which is the one place the conversion is identity, so it can confirm that a render happened and can say nothing about what any brighter pixel became. And **no published row changed**: green barely moves under the conversion, so that capture's peak row is 459 either way and #38's tables stand. What was wrong was chroma, which is all the guard reads.
- **The signals the host verification plays are rendered by a tool in another repository, and only two of its numbers belong to this project.** `scripts/make-test-tones` was a bash-and-ffmpeg script here until [#67](https://github.com/cboone/fosforo/issues/67) deleted it; the generator it became is `tools/test-signals/maketones.py` in [cboone/audio-tools](https://github.com/cboone/audio-tools), parameterised so every frequency, level, duration and gate is an argument. This is the invocation that reproduces this project's twenty files:

  ```bash
  # from the root of an audio-tools checkout, not this one
  uv run tools/test-signals/maketones.py --outdir ~/Music/fosforo-test-tones \
    --levels 0.002 0.010 0.100 0.500 1.000 1.050 1.089 2.000 \
    --saws 0.900 1.100
  ```

  **Everything not named there is a default, and the two flags are the whole of what was ever plugin-specific.** `1.089` is `trace_rail / trace_full_scale` from `src/gpu/iface.zig`, or `0.98 / 0.9`, the ratio at which the trace stops climbing, and `1.050` is the last level below it that does not rail, so the pair brackets that threshold and makes the stalled peak the railing bullet below describes observable at all; the saws at `0.900` and `1.100` straddle the same threshold on a linear ramp, which is what makes a small overshoot legible rather than a matter of opinion; and the `0.002` floor is this display's own one-backing-pixel limit, the arithmetic recorded in the trace-floor bullet below, not a general choice. The six sine frequencies, the hard-panned pair, the click and the gated burst are that tool's defaults. **Nothing measured with the old script needs re-running.** The port was validated against the twenty WAVs still at `~/Music/fosforo-test-tones/` and every file is bit-identical to its ffmpeg counterpart, saws and gated transients included, so #38's tables, the figures quoted in this file, and ADR 0017's reasoning all stand as measurements rather than becoming claims about a generator that no longer exists.
- **`MTLStorageModePrivate` textures are invisible to `leaks` and to peak RSS both**, which is one instrument worse than the `MTLBuffer` case below and does not follow from it. A leaked buffer moves peak RSS from 47.7 MB to 57.7 MB; a leaked accumulation texture moves it from 44.1 MB to 44.3 MB while leaking nearly two gigabytes, because shared storage is in the process's resident set and private storage is not. `gpu.Renderer.liveTextures` is therefore the only instrument rather than the better of two, and it carries an obligation `liveWindowBuffers` does not: these are rebuilt on every resize that changes the pixel count, so the resize path has to decrement as well. It still cannot catch a `releaseAccumulation` that stops sending `release`, since the count returns either way. **Shared storage is not the escape it sounds like**, which #60 measured rather than assumed: its palette lookup is sixteen kilobytes in `Shared`, and forty cycles leaking one apiece moved the `leaks` byte total from 12,544 to 12,544, against the 640 KiB a visible leak would have added. Same blindness, so it joined this counter and the operation was renamed rather than a ninth being added — the rule ADR 0013 set is to *measure* separately, not to *count* separately.
- **Two Metal misconfigurations present a frame and draw the wrong picture, and only the validation layer names them.** An accumulation texture without `MTLTextureUsageRenderTarget`, and a pipeline compiled against a different pixel format from the attachment it encodes into. Both were planted and both pass `smoke-appkit` cleanly; `MTL_DEBUG_LAYER=1 MTL_DEBUG_LAYER_ERROR_MODE=assert zig-out/bin/fosforo-smoke appkit 3` reports each by name. Run it by hand after any change to a pipeline's format, a texture's usage, or a render pass's attachments. It is not in CI and [#63](https://github.com/cboone/fosforo/issues/63) is where that is being decided. #60 is the first change to actually trip that trigger — it moved the drawable's format and added a texture — and it came back clean at `appkit 3`, which is what one constant feeding the layer, the pipeline and the offscreen target buys.
- **The phosphor's fade is a time constant, and three things about how it reaches the shader are easy to get backwards.** `palette.decayOver(elapsed)` is `exp(-dt / tau)` with `tau` at 158.19 ms, derived at comptime from the pair `(60 Hz, 0.90)` so the anchor is the thing to argue with rather than a decimal. **`Renderer.frame` takes an absolute clock reading, never an interval**, because it is the only thing that knows which ticks committed: six early returns can skip one, and the time a skipped tick spanned is owed to whichever frame draws next, so the clock advances beside `accum_source` after `commit` and nowhere else. Hoisting that line above the semaphore wait was planted and it does not fail the decay check — it fails `CoreNotWhite`, because a retry after `.no_frame_slot` then sees a zero interval, nothing fades, and thirty deposits pile up to 29.703 against 9.539 while the white point stays where it was. **The first frame of a renderer's life stands in one interval at the reference rate rather than zero**, which looks like the fussier choice and is not: the fade is a no-op on a cleared pair either way, but zero sends `whitePoint` to its 8e5 clamp for that frame, which `smoke-trace` caught at two levels off its prediction and no eye would have. And the `exp` is computed once per frame on the CPU rather than once per pixel in MSL, which is what `AccumUniforms` carrying a decay rather than a `dt` and a `tau` buys.
- **The clock is `display_link.monotonicNanos()` and `CVTimeStamp` was refused, which is the reverse of what `src/platform/displaylink.zig` promised for two phases.** The argument is in that file and is not "the cheap one won": exponential decay composes, `exp(-(a + b) / tau) = exp(-a / tau) * exp(-b / tau)`, so the total fade depends on how long an interval was and not on how it was cut into frames. Both clocks are monotonic and both sum to the same wall time, so `output_time` buys a better subdivision on a frame that misses its deadline — at most one refresh period of phase error against a 158 ms constant, absorbed by the next interval rather than accumulated — against the cost of laying out 80 bytes of `CVTimeStamp` with a nested `CVSMPTETime` by hand, checked by nothing, where a wrong offset yields a plausible `dt` and a phosphor at the wrong speed. `src/gpu/palette.zig` holds the composition property as a test, so the premise is executable rather than asserted.
- **A full-screen `screencapture` over-crops, and `find_drawable`'s own failure message points at the wrong culprit.** Measured against a `clap-host` window: the crop came back 2296x1232 for a 1920x1080 drawable, having swept in adjacent dark chrome, and `scripts/measure-trace` refused it at 19.8% off the colour ray with the message about recompression and resampling. The **median deviation was 0.00**, which is the tell that the picture was fine and the bounding box was not. Capture the window rather than the screen. `-W` is interactive and is the ordinary way to do it: `screencapture -o -x -t png -W shot.png`, then click the editor. That is not a workaround, and clicking is only friction rather than a source of error, because `find_drawable` crops from the background rather than from the window's bounds.

  Non-interactively the id comes from `CGWindowListCopyWindowInfo`, which took the same session to 0.02% off the ray and the expected 1920x1080. There is no shell tool for that on a stock macOS, so it is one command:

  **Captures go in `verification/`**, which is tracked through a `.gitkeep` so the path always exists, with its contents gitignored. They are working artifacts of one session: frequent, a couple of megabytes each, and superseded by the next build. What belongs in the repository is the *numbers* `scripts/measure-trace` reads out of them, recorded in the issue or the plan. One capture reached a commit before that rule existed, and removing it meant rewriting three commits.

  **The editor is not its own window.** It is an `NSView` REAPER embeds in the window it opens for the plugin, so that is the id to capture and the main window titled after the project is the wrong one. Observed titles in REAPER 7.79: the one to capture is `CLAP: Fósforo (Catamount) - Track 2 "Test Tones"` at 960x593, which is a 960-point editor plus REAPER's own chrome, against `Fósforo - REAPER v7.79 - EVALUATION LICENSE` at 1728x1085 for the project. It is `CLAP:` rather than `FX:` because this is a CLAP; picking by size is the more durable rule. That is also why the capture needs cropping at all. Read `--explain` before recapturing: a high refusal with a zero median is a crop, and a high refusal with a high median is the lossy capture the message describes.
- **`zig build smoke-trace` is the only instrument that can see frame-rate independence, and the reason no screenshot can is structural.** Every other case there measures one frame, or a run at one rate; this is a claim about how successive frames *differ*, which is why #56's body expected it to be checked by pinning a display to 60 Hz in System Settings and judging a fade by eye. `checkDecayIsInRealTime` fades the same 96 ms as twelve 8 ms steps and as six 16 ms ones and asserts the two agree: 0.5430 and 0.5439 against a predicted 0.5451, 0.18% apart, where a per-frame factor would give 0.2824 and 0.5314. **Two traps if you touch it.** The span is 96 ms rather than 100 so both arms divide it into whole nanoseconds and cover the identical interval. And the expectation is composed per step rather than asked of the span, because `palette.max_elapsed_nanos` is 41.7 ms and `decayOver(96 ms)` clamps: it predicts 0.7684 against a true 0.5451, which is the first thing this check caught and it was in the check itself.
- **Metal has no line-width API, which is why the beam is geometry rather than a line.** Verified against the SDK headers rather than assumed: no `lineWidth`, no `setLineWidth`, nothing equivalent anywhere in `Metal.framework`. That is why the phase 2 trace was one device pixel, half a point on a 2x drawable, thin and jagged. #57 fixed it the only way ADR 0007 permits: each inter-sample segment is an instanced quad and the fragment shades it by distance from the segment, so the width is **3.0 points** and the antialiasing is the profile. The three wrong ways are still wrong and are recorded so they are not re-proposed: sub-pixel redraws triple the draw and stay aliased; MSAA needs `sampleCount` on the pipeline, the layer and the attachment plus a resolve, and ADR 0007 wants analytic antialiasing *instead*; and a line-width extension does not exist to be asked for.
- **The rail sits inside the drawable, and the reason changed at #57 while the value did not.** It used to be the rasterizer's coverage diamond: a one-pixel line centred on the drawable's boundary has half its diamond off-screen and may light nothing, so a railed signal would read as an absent one, which is the worst possible way for a level indication to fail. A quad has area and does not inherit that. What `iface.trace_rail`'s 1% now has to hold is the **beam's own half-width**, since a profile centred on the boundary loses whatever falls outside and the centroid `src/gpu/measure.zig` reads is dragged inward. The arithmetic is better than it was, because it is now scale-free: 1.5 points of half-width against `(1 - 0.98) * 135`, or 2.7 points, at the smallest editor `clampSize` permits, both in points, so the display's scale cancels instead of the guarantee holding separately at each one. `src/clap/gui.zig` holds the test and its bound moved with the reason.

  **The centre-line half pixel is answered, and the answer is that no bias was ever needed.** #38 measured silence in REAPER drawing a flat line on row 539 rather than 540 at 1920x1080, reading back as `+0.0021`, and declined the `+1.0/H` NDC bias on three grounds — two of which #57 falsified, since `Renderer` now stores its size and this is the step that re-answered the question. It turned out the geometry was never off: the *estimator* was reading the beam's top edge. A symmetric profile centred on the boundary between two rows weights them equally, so its energy-weighted centroid is that boundary exactly, and `zig build smoke-trace` now reads **centroid row 269.500, implying a sample of 0.00000** at 960x540. Nothing was biased and nothing needed to be. What would still be worth investigating is the line *flickering* between rows during playback, which would be a tie-break going unstable; that was watched for and did not happen.
- **The trace has a floor, and it is arithmetic.** One backing pixel of excursion needs a sample of `1 / (trace_full_scale * height / 2)`: about -54 dBFS at the default editor on a 2x display, about -42 dBFS at the smallest editor on a 1x one. Below that a sine moves the trace less than a pixel and reads as flat. It is the bottom of any level sweep and it is the price of ADR 0017's fixed axis, paid knowingly.
- **It has a ceiling too, and above 48 kHz the display invents structure rather than losing it.** The 20 ms window holds `0.02 * sample_rate` samples: 960 at 48 kHz, against a 960-point default editor, which is why [#37](https://github.com/cboone/fosforo/issues/37) chose that length and recorded that anything above it would alias. At 96 kHz it is 1920 samples, which on a 1x display at the default width is two per pixel and four in an editor dragged to its 480-point minimum. Every one of them is drawn, so what reaches the screen is whichever the rasterizer's coverage happens to catch. **On periodic material that is moiré, and moiré looks exactly like a real low-frequency component** — the display asserting something the signal does not contain, which is the same category of failure ADR 0017 refuses on the vertical axis rather than a cosmetic roughness. [#62](https://github.com/cboone/fosforo/issues/62) is min/max decimation and is the fix; `src/dsp/decimate.zig` has been reserved for it since phase 0 and does not exist yet. Until it lands, **verify at 48 kHz**, and treat any structure that appears only at a higher rate as suspect before believing it.
- **Railing is invisible at the level where it starts, and looking for a flat top is the wrong test.** Clamping begins at `trace_rail / trace_full_scale`, which is 1.0889 or +0.74 dBFS, and at exactly that level it removes a tenth of a backing pixel of travel at the default editor. A plateau reaches one pixel deep at 1.091 and five at 1.100; the sine that loses 443 pixels and looks obviously clipped is at 2.0. **What railing actually shows is the peak ceasing to climb:** 1.000 peaks 43 px below the rail, 1.050 peaks 19 px below it, and every level from 1.089 up peaks on exactly the same row. That saturation is the whole of what ADR 0017 means by declining to say how far over the signal is, and a level sweep that watches for a flat top instead of a stalled peak will report a defect that is not one. A saw is the sharper probe at small overshoots, because it crosses the rail on a linear ramp rather than at a turning point.
- **Stopping the transport draws a bright vertical line that lingers for about a second, and it is the signal rather than a defect.** A host does not stop calling `process` when the transport stops; it keeps the audio device running and hands over silence. So the ring holds a **step** from the last sample to zero, one inter-sample interval wide and up to the full drawable tall, and the beam draws it faithfully. Two things make it prominent rather than subtle, and neither is a bug. Every segment currently deposits the same energy per pixel whatever its screen length, so a segment spanning 500 rows lights all 500 as brightly as an informative slow one. And #60's move to `BGRA8Unorm_sRGB` made the toe 12.92 times steeper, so a single deposit now stays above green 16 for 54 frames rather than 31, roughly doubling visible persistence. [#79](https://github.com/cboone/fosforo/issues/79) tracks it, and **the expected resolution is that [#58](https://github.com/cboone/fosforo/issues/58) closes it as covered rather than fixed**: velocity weighting is precisely the relationship this artifact violates, and under it a 500-row segment would deposit 1/500 as much per pixel and be dim by construction. Check #58 against it before writing any rule to suppress it. Distinct from a *stale* window, which is [#53](https://github.com/cboone/fosforo/issues/53) and looks nothing like this: there the picture stops changing, here it changes correctly and the change is ugly.
- **Nothing links `TraceUniforms` in `src/gpu/metal/renderer.zig` to the struct of the same name in `shaders/scope.metal`.** Two declarations in two languages, and MSL computes its own offsets. A field added or reordered on one side only does not fail: it draws a plausible trace at the wrong scale, which is the hardest kind of wrong to notice. The `@sizeOf`/`@alignOf`/`@offsetOf` test in `renderer.zig` is the only thing that would catch it, and the binding indices have the same problem and a sharper answer, a test that reads the index out of the declaration carrying it rather than searching for the attribute alone. **Searching for the bare attribute is vacuous here and looked fine for two issues.** `buffer(0)` appears in this shader whatever the Zig side says, so `indexOf("buffer(0)")` passes when two indices are swapped, when a fragment binding drifts while a vertex one still uses the number, and when either of the two fragment textures moves alone. All three were planted against the old test and all three passed it. `bindingIndexAfter` anchors on the parameter, and fragment textures, fragment buffers and vertex buffers being three separate index spaces is exactly why three of these constants are zero and why a bare search proves nothing about any of them. Scalars only in that struct, deliberately: MSL aligns `float2` to 8 and `float4` to 16, so a vector member introduces padding the Zig side would have to reproduce by hand.
- **`zig build validate-shaders` never links a pipeline state, and `zig build smoke-gpu` does.** `metal -fsyntax-only` parses and type-checks and stops there, so a vertex function whose buffer arguments the pipeline cannot satisfy passes it and fails at `newRenderPipelineStateWithDescriptor:`. `probe` shares `buildPipelines` with `init`, so the GPU half of the smoke harness is the check that covers that, and the two jobs are not interchangeable despite both being described as validating the shader.
- **Compiling the shader costs about 40 ms when the source has changed and about 0.14 ms when it has not, and everything anyone reasons about here depends on knowing which case they are in.** Metal caches a compiled library by source hash *across processes*, so the two figures differ by a factor of nearly three hundred and the cheap one is the one an ordinary `set_parent` pays. Measured on this machine by timing `newLibraryWithSource:` and the three `newRenderPipelineStateWithDescriptor:` calls separately, in Debug, over 20 compiles in one process and five separate processes. **A cache miss**, which is what every hot reload is by definition: 34.3 to 43.5 ms with a median of 40.0 ms in the steady state, and 57 to 68 ms for the first compile in a process, the extra being the XPC connection to `MTLCompilerService` being set up. **A cache hit**, which is every launch of an unchanged build after the first on the machine: 0.14 ms total, 0.04 of it the library. In both cases the three pipeline states are noise, 0.17 to 0.80 ms, so `newLibraryWithSource:` *is* the cost and `Pipelines`' one-library-not-three argument is about the miss. Two things follow. The `Pipelines` docstring's claim that this is "the most expensive thing `init` does and sits on `set_parent`, where a host is waiting" is true only on a cold cache; in the steady state `init` is dominated by the accumulation textures instead. And 40 ms is five vsyncs at 120 Hz, which is what makes compiling on the render thread the wrong answer rather than merely inelegant: `Editor.tick` holds the `Gate` across its whole body, so an editor closed during a compile would busy-spin the host's main thread for the duration.
- **A debug build reloads the shader from disk while a host is running it, and two separate gates keep that out of a release.** `build.zig` hands debug builds the absolute path of `shaders/scope.metal` and hands every other build the empty string; `src/gpu/metal/shader.zig` reads it only when `builtin.mode == .Debug and !builtin.is_test`. **Neither gate substitutes for the other and the split is not belt-and-braces.** The first decides whether the bytes exist in the binary, which is the only way "no shipped binary carries a path into somebody else's worktree" is a proof rather than a claim about the optimizer, and the `clap-wrapper` job asserts that negative with the provenance marker as its positive control. The second decides whether any code runs, which `build.zig` cannot do: an empty option still links the watcher and a 64 KiB buffer into a release build. And only the second can carry `!builtin.is_test`, which is what keeps `zig build test` from reading the filesystem, since a test binary is a Debug build; `src/clap/log.zig:109` is the idiom it copies and one test in `shader.zig` fails if the term is dropped. `FOSFORO_SHADER_PATH` overrides the baked path, which is what survives a `git worktree move` with no rebuild, lets one installed debug bundle be aimed at whichever worktree is being worked in, and makes the whole thing testable. **The fallback rule has one case that is not obvious:** a set-but-missing env path falls back to the *embedded copy*, never to the build option, because you said which file you meant; and a relative env path is refused outright, because a plugin's working directory belongs to the DAW.
- **Compiling a shader on a thread that draws frames now trips an assertion, and that guard is the shape to copy rather than a detail of this one feature.** `platform.assertNotMainThread` keeps the render path unreachable from the main thread; this is the same rule from the side nothing guarded. A debug-only `threadlocal` in `src/gpu/metal/renderer.zig` marks every thread that has entered `frame`, `resize` or `upload`, and `buildPipelinesFromSource` asserts it is unset. **A threadlocal rather than an atomic is the design, not a detail:** several open editors mean several display-link threads, and one process-wide slot would hold whichever marked itself last. It exists because the harness is the wrong instrument for this: 40 ms inside a tick is invisible to a frame counter with a two-second timeout, so a compile that drifted back into the render loop reports a clean run, which was planted and confirmed. [#59](https://github.com/cboone/fosforo/issues/59) has to answer the same question about its own upsampling and inherits the guard for free.
- **Nothing validates a hot-reloaded shader's binding indices, and this is the price of the feature rather than an oversight.** The `bindingIndexAfter` tests, the `TraceUniforms` layout test and the `measure-trace` constants test all read the **embedded** copy at comptime, which is correct: a test about a file that can change between a build and a frame would say nothing. A file swapped in at runtime gets `buildPipeline`'s missing-function check and nothing else. So if the trace goes wrong immediately after a save, suspect a moved `[[buffer(N)]]` before suspecting the signal path, and run `zig build test`, which rebuilds against the edited file and does check it. [#77](https://github.com/cboone/fosforo/issues/77) is the issue that would check the indices at reload time, and it cannot see `TraceUniforms` layout drift either way. #51 has landed and does not close this either: `smoke-trace` measures the **embedded** shader, and nothing reloads during a trace run. **A build-time test comparing the two was considered and refused**, because they agree by construction through `@embedFile`'s cache dependency and the only way to write one is as a runtime test that reads the filesystem from inside `zig build test`.
- **`zig build` does not rebuild the smoke harness, and running a stale one wastes an afternoon.** `build.zig` installs `fosforo-smoke` with `b.addInstallArtifact` attached to the smoke steps rather than with `b.installArtifact`, deliberately, so the day-to-day loop keeps producing only the `.clap`. The consequence is that `zig build && zig-out/bin/fosforo-smoke appkit 40` runs whatever binary a *previous* smoke step left there, with no warning and no hash to compare. This is the provenance hazard the plug-in folder has, one directory closer to home. Run a smoke step, or run `zig build smoke-gpu` first if what you want is the harness rebuilt without waiting for the AppKit half.
- **The watcher polls, and each editor's cycle in `smoke-appkit` is shorter than one poll interval.** 250 ms between looks, against a cycle in `oneCycle` lasting about as long, so a watcher started on an editor's first frame is joined before it ever looks twice: an arm testing reload from inside `oneCycle` cannot work and reads as the watcher being broken. That is why `hotReloadPhase` holds one editor open instead, once per process. Polling rather than a `dispatch_source_t` on the file descriptor is also deliberate: such a source watches a vnode, and the save-by-rename case the three-field stamp exists for is exactly where the watched vnode stops being the path.
- **Logic cannot be launched from a terminal to read the plugin's diagnostics, the way REAPER can.** Running `Logic Pro.app/Contents/MacOS/Logic Pro` directly starts it outside the launch services path it expects and most plugins then fail to register, so the run is not the one worth measuring. There is no equivalent of REAPER's terminal-launch trick, and the debug `stderr` mirror in `src/clap/log.zig` is therefore unreadable in Logic. Verify the Audio Unit by the pixel sample described above, or by `zig build smoke-appkit`, and treat the CLAP in REAPER as the place diagnostics are read.
- **In the Audio Unit an editor is destroyed rather than hidden.** clap-wrapper's AUv2 view calls `_destroyWindow` from `viewDidMoveToWindow` and from `dealloc`, and never calls `gui->hide` at all, just as it never calls `gui->show`. So `Editor.hidden` is only ever exercised by a CLAP host: in Logic the render loop starts at `set_parent` and stops at `gui->destroy`, which means an open editor window is a running display link and a closed one has no editor behind it at all. That is what makes "N open editors" a sound way to count concurrent render loops there.
- **`auval` cannot see this component, and neither can `AudioComponentFindNext`.** On Darwin 25.5.0 both enumerate only Apple's built-in components, from an ordinary terminal outside any sandbox, while Logic sees every installed Audio Unit including this one. A null result from either is not evidence that the component failed to register. Use a host.
- **`~/Library/Caches/AudioUnitCache` is not the AU registration cache.** Deleting it is the standard advice, it changes nothing, and it is not rebuilt afterwards. The capability data lives in `~/Library/Preferences/com.apple.audio.AudioComponentCache.plist`. Relaunching Logic triggers a rescan; `killall AudioComponentRegistrar` does not, and `launchctl kickstart` on the registrar is refused under SIP.
- **The display name lives in four places.** It cannot be derived from one source, because it crosses Zig, CMake, and a generated plist. `src/clap/plugin.zig` holds the CLAP descriptor's `name` and `description` and is the source of truth; `macos/Info.plist` carries `CFBundleName` and `CFBundleDisplayName` for the Zig-built bundle; `DISPLAY_NAME` in `cmake/CMakeLists.txt` covers the CLAP that CMake builds; and `cmake/set-au-display-name` covers the Audio Unit, whose plist clap-wrapper composes from the ASCII `OUTPUT_NAME` and then describes as a wrapper. Change one, change all four. The ASCII `Fosforo` that names files, binaries, and `CFBundleExecutable` is a separate string and must not follow.
- **Some identifiers are permanent.** The AU triple (`aufx`/`Fsfr`/`Ctmn`) and the CLAP plugin `id` are stored in users' project files; changing either makes the plugin read as missing. The manufacturer name and display name are free metadata. See the plan's identifiers section before touching any of them.
- **Shader validation is deliberately not part of `zig build test`,** so the build stays hermetic (ADR 0009).
- **`zig build test` is a Debug build, and a module reached only from a `test` block is never type-checked by `zig build`.** Two independent facts, both easy to assume the other way round, and each with a consequence. `standardOptimizeOption` declares no default and CI's reusable workflow passes no `-Doptimize`, so the ordinary test run is Debug: `std.debug.assert` is live there and gone from the `--release=fast` build that ships, which is exactly why every trust boundary in this project refuses rather than asserts, and why `state.zig`'s `TestStream.seed` reaches for `@panic`. Separately, Zig analyzes `test` declarations only in a test build, so a module named solely in `src/main.zig`'s test block is parsed but never checked by a plain `zig build`: a type error in it passes the `Build`, `clap-validator` and `clap-wrapper` jobs and fails only `Test`. `src/dsp/ring.zig` was in that state until `src/clap/plugin.zig` imported it (#36). **Acquiring a caller only half fixes this, and the half it leaves is the surprising one:** Zig's analysis is lazy per declaration, not per module, so a plain `zig build` now checks `Ring.init`, `deinit`, `write` and `clear`, which the plugin calls, and still does not check `Ring.read` or `Ring.capacity`, which only tests call. A `pub fn` nothing reaches is not analyzed however the file it lives in was imported. Both halves were measured rather than reasoned about: a type error planted in `capacity` builds clean, and the same error in `write` fails the build. The build cache cannot answer this for you, because a manifest lists the files the compiler read rather than the ones it checked; the check that does answer it is a type error in the specific declaration you care about, which still produces a binary if nothing calls it.
- **The smoke harness is an executable, and that is not an oversight.** `src/smoke.zig` is the only thing here that runs a Metal or an AppKit call rather than type-checking one. It is not a test artifact because a test binary has to stay silent: `std.debug.print` from inside one interleaves with the runner's stream and the build runner reports the step as failed despite a zero exit code, which is the same hazard `src/clap/log.zig` disables its `stderr` mirror under `builtin.is_test` to avoid. And it is never wired into `zig build test`, on `validate-shaders`' precedent, because the default test path must not acquire a dependency on the machine having a GPU. It is also the only check in the project that can go red for reasons unrelated to the code, which is why the gating in CI is not uniform: `smoke-gpu`, `smoke-trace` and, since [#72](https://github.com/cboone/fosforo/issues/72), `smoke-appkit` all fail the job, while `smoke-leaks` stays under `continue-on-error` (ADR 0013). **That asymmetry is the argument rather than a leftover.** `smoke-appkit` fails on its own assertions plus the window-server connection 65 green runs settled, both of them facts about this repository; `smoke-leaks` also judges the runner's own AppKit chatter, against class prefixes including `NSView`, `CALayer` and `IOSurface`, so a framework leaking on its own account fails it with nothing here being wrong. A second consequence of the promotion is that an `appkit` failure now *skips* the leak step rather than running it, since nothing there carries an `if:`, which is `scripts/smoke-leak-check`'s own first assertion enforced one level up. **`smoke-leaks` runs there too**, at 40 cycles through `-Dleak-cycles`, since it is the `appkit` half with an instrument wrapped around it. Its criteria do not track depth — across five runs at 40 and at 400 cycles the report gave 288 leaks for 18,816 bytes four times and 285 for 18,464 once, so a tenfold change in depth moves it by under 2% and only run to run — while its cost does, because the harness waits on vsync about thirteen times per cycle and a hosted runner refreshes at half this machine's rate. Its `main` takes a `std.process.Init.Minimal`, which is how Zig 0.16 hands over argv; there is no `std.process.args()` any more.
- **`src/dsp/ring.zig`'s memory ordering is verified by `zig build ring-race`, which is the one check here that cannot run on this machine.** The release store in `write` and the acquire load in `read` are the whole of ADR 0010's protocol, and every test of that module is single-threaded, so replacing the release with a `.monotonic` store passes all 144 tests. `src/ring_race.zig` runs the two on real threads under Thread Sanitizer, and the reason that is not the stress test it looks like is the whole point: TSan does not look for corruption, it builds a happens-before graph and reports two threads reaching one address with no edge between them, so a weakened store is flagged whether or not the hardware ever reorders. Zig 0.16 links a `-fsanitize-thread` binary on `aarch64-macos` that segfaults before `main`, re-measured on 0.16.0 rather than inherited, so this runs on Linux in the `ring-race` job and `zig build ring-race` refuses on a macOS host with a message saying where it does run. **Three things about it are load-bearing and each looks optional.** The harness has a deliberately weakened second arm that must be flagged, because everything the real arm proves is an absence and `scripts/ring-race-check` cannot tell a correct ring from an instrument that was never running without it; the writer is bounded so it cannot lap the reader, because the torn-window path this design accepts on purpose is a data race in TSan's model and would fail the job at random; and a source canary in `ring.zig` reads the five atomic operations as text so the weakening also fails `zig build test` on the machine you are on, which the sanitizer job cannot do for you. See ADR 0016 before changing any of them. **Drawing the trace still does not close this**, which is worth knowing because two plans in `docs/plans/done/` say it would: a weakened store's visibility window is nanoseconds against a window that lags 20 ms and redraws sixty times a second, so a sine looks like a sine either way. The third plan in that chain, `2026-08-19-read-a-trailing-window-and-upload-it-across-the-seam.md`, says the opposite at length and is the one that ended the hand-offs.
- **`sanitize_thread` alone produces a Thread Sanitizer binary that detects nothing and says nothing about it, and `use_llvm = true` is what fixes it.** Zig 0.16 defaults to its self-hosted x86_64 backend for a Debug build on Linux, and that backend **links the sanitizer runtime while emitting none of its instrumentation**. The binary is the right size, it builds, links, runs, exits zero and reports no races, whatever you race inside it. There is no warning, because nothing is wrong from the compiler's point of view: you asked for a runtime and you got one. Measured by disassembling both builds of the same file rather than inferred: the default backend stores straight to the shared word, and adding `-fllvm` emits a `__tsan_write8` call immediately before that same store. This is the reason `scripts/ring-race-check` runs its deliberately-racing arm **first** and refuses to read anything into the ring's silence until that arm has been flagged, and it is not a hypothetical: the first CI run of the `ring-race` job reported a clean control, which is precisely the false pass the ordering exists to catch. Anything else here that ever acquires a sanitizer needs the same flag and the same kind of control.
- **`b.dependency` runs a dependency's `build` function at configure time, so a step that needs none of it can still be killed by one.** The first CI run of `ring-race` aborted with `unhandled error` inside zig-objc's `build.zig`, which calls `appleSDKPath` and panics on any OS that is not Darwin, before a single step ran and although the harness's module reaches neither zig-objc nor CLAP. Fetching a dependency's tarball is a cost you pay whatever step you asked for; *describing* its graph is a failure, and only the second one is fatal, which is the half easy to assume away. `build()` therefore registers `addRingRaceStep` and returns before constructing `Core` whenever the target is not macOS. Everything past that line is macOS-only anyway (ADR 0001), so the early return costs nothing, and it is what makes `zig build -Dtarget=x86_64-linux-gnu` do anything here at all. Anything else that ever needs to build off this platform goes above that return, not below it.
- **A clean `leaks` report is not evidence until you know `leaks` ran.** It exits non-zero whenever it finds anything and it always finds something: AppKit's LaunchServices chatter leaks a few hundred `NSXPCConnection` allocations per run, so its exit code cannot be the gate. `scripts/smoke-leak-check` therefore asserts that the harness passed and that a parseable report exists *before* it concludes anything from an absence. Match leaked objects by class prefix, never by the framework's public class names: dropping the command queue release in `Renderer.deinit` leaks an object `leaks` calls `AGXG17XFamilyCommandQueue`, and a grep for `MTLCommandQueue` reports that planted leak as clean.
- **`leaks` cannot see a leaked `MTLBuffer` at all, and this was measured rather than reasoned about.** Dropping the release of the window buffer ring in `Renderer.deinit` and running the harness 60 times produces a report `scripts/smoke-leak-check` calls clean, while the *same* omission applied to the command queue is caught in the same run. The leak is real: peak RSS across 200 cycles goes from 47.7 MB to 57.7 MB, and none of the 234 leaked classes in the report is a buffer under any name. `leaks` walks the malloc heap, and a Metal buffer's storage is not in it. This is a sharper form of the class-prefix gotcha above: there the right prefix finds the object, here there is no object to find. So the backend counts its own, through `live_windows` and `gpu.Renderer.liveWindowBuffers`, and `src/smoke.zig` asserts it is zero after the cycle loop; removing the release from `deinit` fails with `WindowBuffersLeaked`. **The counter proves the ring was handed back, not that `release` was sent**, so a `releaseWindows` that stopped releasing would still balance; what it catches is the realistic failure, a path that builds a ring and forgets it, which is what `probe` would otherwise have been. **Any allocation added later should be checked against `leaks` with a planted leak before assuming `smoke-leaks` covers it** — not only a Metal resource that is not a buffer, which is what this sentence used to say and which is how the case in the next bullet went unexamined for four issues.
- **`scripts/smoke-leak-check`'s class check is an allowlist of Objective-C class prefixes, and this project's own allocations do not have a class.** So a plain `c_allocator` leak was invisible to it: dropping `self.history.deinit` from `plugin.destroy` and running 40 cycles leaks roughly 42.6 million bytes against a clean 18,816, and the check called it clean, because `leaks` writes a block with no class as something the `<ClassName 0xADDRESS>` extractor does not match. That is a byte total two thousand times the baseline reported as nothing at all, in the check that was about to become this project's leak gate in CI. `MAXIMUM_LEAKED_BYTES` is what closes it, and the two assertions are complementary rather than one subsuming the other: a leaked command queue is 137,152 bytes, *under* the bound, and is caught only by its class; a leaked history ring has no class and is caught only by the bound. **The leak count is not a discriminator and must not become one.** Across two runs of that same planted leak the report gave 232 leaks and then 328, against a clean 288 that does not move at all, so the count wanders in both directions while forty megabytes go missing and one of those runs would have read as an improvement.
- **The three leak instruments do not rank the way they read, and the difference is what each is blind to rather than how thorough each is.** #63 was filed proposing a fourth, a peak-RSS slope, and refused after this table was worked out; see ADR 0013 for the refusal.

  | Planted defect                                   | `leaks` | Byte bound | `liveWindowBuffers` | `liveTextures` | `zig build test` |
  | ------------------------------------------------ | ------- | ---------- | ------------------- | -------------- | ---------------- |
  | Command queue or pipeline state never released   | yes     | no         | no                  | no             | no               |
  | Window buffer ring built and forgotten           | no      | no         | yes                 | no             | no               |
  | Accumulation pair built and forgotten            | no      | no         | no                  | yes            | no               |
  | Palette lookup built and forgotten               | no      | no         | no                  | yes            | no               |
  | Either `release` stops being sent, still counted | no      | no         | no                  | no             | no               |
  | A plain allocation this project owns             | no      | yes        | no                  | no             | on tested paths  |

  Four things to carry out of it. **`leaks` walks the malloc heap**, so it sees Objective-C objects and misses both a Metal buffer's storage and a block with no class. **The byte bound sees anything large**, which is why it is the one that reaches this project's own allocations, and it is set 56 times above the observed baseline precisely so it needs no calibration against the machine it runs on. **The counters are exact**, and they are the only instrument for a texture of either kind — `MTLStorageModePrivate` storage is in neither the malloc heap nor the resident set, and #60 measured that a small `Shared` texture is invisible to both as well. They no longer name *which* resource, which is why the harness's message says "textures" rather than "accumulation textures": a counter that cannot tell two kinds apart must not claim to. **The bottom row is covered by nothing**, deliberately: a `releaseWindows` that decrements without releasing balances every counter and leaks storage no instrument here can see, and chasing it was the whole of what a peak-RSS slope would have added.
- **`shfmt` reads `.editorconfig`, but only when given no parser or printer options.** The shell profile, equivalent to `-i 2 -ci -sr`, lives there because `cmake/narrow-au-resource-usage` was written to a style the repository never recorded, so bare `shfmt` reported an already-consistent file as unformatted. Passing any option from `shfmt --help`'s "Parser options" or "Printer options" groups (`-ln`, `-p`, `-s`, `-i`, `-bn`, `-ci`, `-sr`, `-kp`, `-fn`, `-mn`) makes `shfmt` discard `.editorconfig` wholesale, which means `shfmt -d` is correct and `shfmt -i 2 -d` silently is not. The output-mode selectors are exempt, so `-d`, `-w`, `-l` and `-f` are all safe. Verified per flag, not inferred from the documentation. The scripts in `cmake/` have no extension, so the section names each one directly; a `[*.sh]` section does not match them. **A new shell script must be added to that section.** The `shell` job selects files by shebang, so it lints a new script immediately, while `.editorconfig` styles it only once listed, and the failure that asymmetry produces is `shfmt` reporting tabs against a file that matches its siblings exactly. Always select files with `git ls-files`, never `shfmt -d .`: `shfmt` does not read `.gitignore`, so walking the tree reaches vendored scripts under `build/` once the CMake build has run, and `shfmt -w .` will reformat them. A fresh CI checkout has no `build/`, so `-d .` passes there and fails locally. The `shell` CI job enforces this and `shellcheck` together, and `.editorconfig` is deliberately absent from that workflow's `paths-ignore` lists so a change to the profile cannot skip the job that checks it.
- **`typos` runs from its own workflow, and that placement is what makes it enforce anything.** `.github/workflows/typos.yml` is separate from `ci.yml` because that workflow ignores `*.md`, `docs/**`, `LICENSE` and the agent config files on both triggers, which is right for a set of macOS builds and exactly wrong for a spell checker: the files it exists to check are the files that would skip it, so a job added there would be green on every pull request that could have failed it. `paths-ignore` is workflow-level rather than job-level, so no job can be exempted from it, and dropping `docs/**` from those lists would run the CMake build on every typo fix instead. The typos workflow therefore carries no `paths-ignore` at all, on the precedent that keeps `.editorconfig` out of `ci.yml`'s lists, and it runs on Ubuntu with a pinned binary and a committed SHA256 for the same reasons the `shell` job does, plus one this tool adds: its dictionary ships inside the binary, so an unpinned upgrade can introduce findings with no change on this side. The other half of making it run is `extend-ignore-re` in `typos.toml`, and both patterns there are load-bearing. Every Action here is pinned by commit and the pins get explained in prose; `typos` skips 40-character hex strings and not 7-character ones, so `91f9abd` reads to it as a misspelling of "and". That is not one finding in one plan file but a class recurring on every documented pin, and it is why this check was failing on `main` at the moment it was written. The pattern is anchored on backticks rather than on a word boundary, so both pin lengths are ignored while a misspelling beside either is still caught. The second pattern suppresses a span between `<!-- spellchecker:off -->` and `<!-- spellchecker:on -->`, which exists because `typos` has no inline directive at 1.49.0 and a document explaining a spell checker has to be able to spell out what it catches; an unclosed marker suppresses nothing rather than everything after it. **Add to `typos.toml` rather than rewording a word the tool is wrong about,** which is what the `precessing` entry already is: a phase-space loop that slowly rotates exhibits precession, whatever the audio context suggests. **Which of the two tables you add to is not a style choice.** <!-- spellchecker:off -->`extend-words` allows a *word*, and `typos` splits an identifier into words before judging it, so `PNGs` is rejected for the `PN` inside it and an `extend-words` entry keyed on `PNGs` suppresses nothing at all, silently, while one keyed on `PN` would allow that fragment everywhere.<!-- spellchecker:on --> Whole identifiers go in `extend-identifiers`, which is where `PNGs` is, and this sentence sits between the `spellchecker` markers for the reason the paragraph above gives.
- **`ruff` lints the one Python file here, and nothing else can see it.** `scripts/measure-trace` is the only `.py`-less Python in the tree and the `shell` job cannot reach it: that job selects with `shfmt -f`, which finds shell files by shebang, and `env -S uv run ... python` is not one it knows. Measured rather than assumed, `git ls-files -z | xargs -0 shfmt -f` returns twelve files and not that one, so before the `python` job existed the tool producing this project's published numbers was the only unchecked file in the repository. **The job's real failure mode is a vacuous pass**, because ruff discovers Python by extension and this file has none. `extend-include` in `ruff.toml` is what makes it visible, and **a bare `measure-trace` there matches nothing while reporting success**: ruff globs with a literal path separator, so a pattern containing no `/` matches only at the repository root. With an unused import planted in the script, that spelling reported "All checks passed" and `**/measure-trace` caught it. The tell in a passing log is `ruff format --check` printing the number of files it read, which must be 1. Two more things are not what you would guess. **ruff's default rule set is wider than the `E4, E7, E9, F` it is usually described as**, and at 0.16.5 it carries pylint's `PLW` and flake8-executable's `EXE`, which is how a `subprocess.run` with no explicit `check=` was found in a script that had been producing numbers for weeks; that is also why the version is pinned, on `typos`' precedent, since the rule set ships inside the binary. And **ruff formats Python fenced inside Markdown**, which would put all 53 `.md` files in its remit; that is excluded, because `ci.yml` ignores `*.md` and `docs/**` on both triggers, so a doc with an unformatted fence could never run the job that would catch it and would instead turn some later Zig change red. **`ruff` does not read `.editorconfig`**, unlike `shfmt`, so the `[measure-trace]` section there and `ruff.toml` are two independent statements of one style, kept in step by hand, with `ruff.toml` as the authority.
- **`clap-validator` is pinned twice over,** at workflow-level `env` in `.github/workflows/ci.yml`: the validator commit, because it is installed from git rather than a registry and a tag can move, and the Rust toolchain that builds it, because the crate declares an MSRV the runner image may stop satisfying. Bump them together and the cache key follows automatically. Warnings do not fail either job: `clap-validator` exits non-zero on failed and crashed tests only, so a `WARNING` line is visible in the log without breaking the build.
- **Two jobs validate a `.clap`, and they share one cached validator.** `.github/actions/clap-validator` is a local composite action that builds and caches it; `clap-validator` and `clap-wrapper` both call it and pass the workflow-level pins. The cache key lives only in that action, because a key written twice can drift, and a drifted key still passes: it just pays a full Rust build every run. On a cold cache both jobs build concurrently and race to save, which is safe, since the loser warns rather than failing.
- **Every `timeout-minutes` is measured, not copied.** Each one sits at roughly 4x the slowest run observed for that job, with the figure and its sample size in a comment beside it; `docs/plans/done/2026-07-29-tighten-ci-job-timeouts.md` holds the full table and the queries that produced it. Re-measure before changing one, rather than copying a neighbour: that is exactly how the old values propagated, and it left `shell` at 150x. Three details are easy to get wrong. The `ci / *` and `scan / *` values are `with:` inputs rather than job keys, because those jobs belong to reusable workflows, and one input covers all of a workflow's jobs, so the value is set by the slowest of them. **Two jobs are deliberate exceptions.** `shaders`' ceiling does not budget for the Metal toolchain download, which has never fired and is unmeasured, so if a runner image ever ships without the toolchain the job fails rather than carrying insurance indefinitely, and the ceiling gets raised once with real data. `smoke`'s stays at 8 rather than tracking 4x its measured 98s, because its worst case is structural rather than statistical: two of its steps are given two and three minutes to be seen wedging on a window server, and a ceiling derived from the observed duration would cut the job off below budgets it grants on purpose. And **a step-level `timeout-minutes` cannot exceed its job's**, so it is only a label wherever the job would catch the same wedge anyway, as on that download step and on `smoke`'s leak step, and a real bound only on a step that can fail the job by itself, which since #72 is what `smoke-appkit` is. The upstream `scan / Validate inputs` job sets no timeout at all and inherits GitHub's 360; that one is not reachable from this repository.
- **`--target fosforo_auv2` does not build the CLAP.** Setting `AUV2_MANUFACTURER_CODE` sends `make_clapfirst_plugins` down its explicit-configuration branch, which never adds a dependency from the AUv2 target to the CLAP one. Build `fosforo_all` when both artifacts are wanted. `scripts/build-audio-unit` encodes that, along with configuring only when `build/` is absent, and it is what both `zig build audio-unit` and the `clap-wrapper` CI job run, so the rule cannot be true in only one of the two places.
- **`std.Io` is adopted, narrowly, and `Threaded.init` must never be called.** Zig 0.16 moved `Mutex`, every clock, and `sleep` behind an `Io` instance. `src/platform/io.zig` owns the only one, built with `init_single_threaded`; `Threaded.init` calls `posix.sigaction` on `SIG.IO` and `SIG.PIPE`, and a plugin lives in the host's address space, so that replaces REAPER's or Logic's handlers rather than installing its own. Nothing in the type system stops it and the symptom surfaces in the host, which is why the constructor is named in one place. **The fear that motivated the alternative was measured and was wrong:** `Threaded.io()` names all 113 vtable entries so none can be stripped, but the debug `.clap` already carried 325 `Io.Threaded` symbols before any of this, because `std.debug.print` in `src/clap/log.zig` links the implementation for the debug-only `stderr` mirror. Adopting it for the render meter's clock moved the debug binary by -128 bytes and left the release binary byte-identical, since `monotonicNanos` was reached only from the debug-only `Editor.report` and was stripped with its caller. **#56 ended that half of it and not the half ADR 0015 is about.** The decay reads the clock every frame, so a `--release=fast` binary now imports `clock_gettime_nsec_np` and is **176 bytes** larger, measured by building with and without that one call; `Io.Threaded`'s symbols are still absent from it, which is what the vtable argument was ever about, and `init_single_threaded` is still the only constructor. **Two local primitives are deliberately not covered:** `Gate` in `src/clap/gui.zig`, because `Io.Mutex`'s contended path calls `futexWait` inside a gate `Editor.tick` holds across its whole body, and the libdispatch semaphore in `src/gpu/metal/renderer.zig`, because `std.Io.Semaphore` has `wait` and `waitUncancelable` and no try-wait at all. Both say so at the source. And `extern "c"` still bypasses the deployment-target check, so read the SDK header's availability line before adding another: these are Zig's declarations and no header attribute is ever read (ADR 0015).
- **`CVDisplayLink` is deprecated as of macOS 15 and is kept anyway.** Its replacements, `CAMetalDisplayLink` and `-[NSView displayLinkWithTarget:selector:]`, are macOS 14 and later, and the deployment target is 11.0 in three places. Nothing warns, because `src/platform/displaylink.zig` declares the functions itself and no deprecated header attribute is ever read, so the compiler will not be the thing that tells you this changed. Revisit it with the ADR that raises the deployment target, not incidentally.
- **`show` no longer draws anything, which is why `Renderer.frame` reports an outcome.** It starts the display link, and the first tick arrives on CoreVideo's thread a refresh period later. That silently removed `Renderer.frame` from the smoke harness, which called `show` and `hide` back to back: instrumenting the tick counted zero frames across ten cycles in a passing run. `frame` returns an `iface.Outcome`, `Editor` counts presented frames behind `framesPresented()`, and `src/smoke.zig` waits for the count to advance. If you add an early return to `frame`, give it an `Outcome` that is not `presented`, or the harness will start reporting frames that were never drawn.
- **`CVDisplayLinkStop` does not promise what teardown needs to know.** It stops future callbacks and says nothing about one already running, so `Editor.destroy` closes a `Gate` before freeing anything the tick touches. The gate's single word carries both the closed flag and the count of ticks inside, because checking the flag and entering as two operations is exactly the race it exists to close. Do not replace it with a bare atomic bool.
- **Nothing the render thread waits on may be unbounded, because `Editor.tick` holds the gate across all of it.** `Gate.close` spins until every tick inside has left, on the host's main thread, so any wait `Renderer.frame` can enter becomes a wait the DAW's UI can enter when an editor closes. The in-flight semaphore is therefore a try-wait rather than the canonical `DISPATCH_TIME_FOREVER`: a GPU that never signalled a completion handler would otherwise hang teardown for the life of the process. This bounds rather than eliminates the stall, and the residue is deliberate: `nextDrawable` can still take up to its own one-second timeout before returning nil, so a wedged GPU can stall an editor closing for about a second. Unbounded was the defect; a second is a stutter. Adding a new wait to `frame` means checking it against this.
- **The copy into a per-frame buffer happens inside `Renderer.frame`, after the semaphore wait, and moving it into `upload` would be a defect that only shows under load.** A per-frame buffer is safe to write only once its slot is known free, and the slot is taken by the try-wait at the top of `frame`. `Editor.tick` calls `upload` before `frame`, so an `upload` that wrote the GPU buffer directly would be writing one the GPU may still be reading on exactly the ticks where the wait goes on to fail: the frames dropped under load are the frames that corrupt. It shows as tearing rather than as a crash, which is the kind of thing that gets blamed on the GPU. `upload` therefore lands in a CPU staging array and `frame` copies staging into `windows[slot]`, advancing `slot` immediately after a successful wait. Writing the buffer from `upload` is still possible, but it needs `max_frames_in_flight + 1` buffers and it breaks the moment an upload is skipped, because the buffer it would rebind then holds a window from four encodes ago rather than the last good one. Staging also means a torn read costs nothing: `Editor.readWindow` skips the upload, and `frame` redraws the last intact window.
- **The history buffer's storage belongs to the instance, and `plugin.destroy` must free it after `editor.destroy()`.** `Editor.destroy` closes the `Gate` and spins until no tick is inside it, which is what establishes that the render thread is not partway through `Ring.read`; the free is safe only on that side of it, and swapping the two lines reintroduces a use-after-free in the one window where the editor is still ticking. The reason it is not freed in `deactivate` at all is that a host may deactivate with the editor open, which REAPER and Logic both do when a track is disabled, and there is no gate on that path. That lifetime is also why `history_samples` is a constant rather than a function of the sample rate: `create` runs before any rate exists. `activate` therefore clears rather than reallocates, and that `clear` is now the *only* thing making a new activation's history fresh, since `Ring.deinit` never touched the cursor and the fresh-`Ring` assignment that used to carry it is gone.
- **`Editor.destroy` resets what the editor owns and deliberately leaves `window` and `history` alone.** Those two are published by `plugin.init` and `plugin.activate` and describe the instance, which outlives any number of editors; a host closing and reopening an editor on an active plugin is ordinary. Clearing them there would leave the second editor reading nothing for the rest of the activation, with no symptom but a trace that never moved. The counters beside them, `presented` and `torn`, go the other way and must be cleared, because a stale count would be the next editor's opening claim.
- **`activate`'s sample-rate bounds are load-bearing now in a way they were not before.** Sizing the history from the rate used to refuse absurd values as a side effect: `Ring.init` rejected anything that saturated a `usize` or rounded down to no slots, so `activate`'s own check only had to keep `nan` out. Moving the allocation to `create` took that away, which is why `min_sample_rate` and `max_sample_rate` exist. They are wide enough that nothing a host could legitimately negotiate is refused; what they exclude is a rate that makes `self.sample_rate` useless to divide by, which phase 3 does.
- **Every early return in `Renderer.frame` has to hand its semaphore slot back.** The slot is taken at the top and handed to the command buffer's completion handler at the bottom; a `defer` covers everything between. Three skipped frames that each swallowed a slot would drain the semaphore to zero and stop the render loop permanently, which reads as "rendering stopped after a busy moment" and is the classic way this pattern fails.
- **The completion block captures the semaphore as an `objc.c.id`, deliberately.** `zig-objc` retains `id`-typed captures when the runtime copies a block to the heap, which is what lets `Renderer.deinit` release the semaphore while frames are still executing on the GPU. Changing the capture to a raw pointer compiles and then signals freed memory whenever an editor closes under load.
- **The render thread may set the layer's drawable configuration but not its frame.** `Renderer.resize` sets `contentsScale` and `drawableSize` inside a `CATransaction`; the layer's `frame` is set from `setFrameSize:` on the main thread in `src/platform/view.zig`. That split is ADR 0010's "the render thread touches Metal only and must never mutate AppKit state", and `platform.assertNotMainThread` in `frame` and `resize` enforces the other direction in debug builds.
- **The runtime view class name carries an address-derived suffix.** `objc_allocateClassPair` returns nil on a name that is already registered, and two copies of this plugin genuinely do coexist in one process when the CLAP and the clap-wrapper Audio Unit are both installed. Reusing the first copy's class would be worse than failing, because its method implementations point into that copy's `__TEXT` and dangle when it unloads. The class is never disposed, since disposing one with live instances is illegal.
- **REAPER accepts `clap.log` messages and discards them.** It implements the extension, so `Log.init` finds it and a host-only design would send every diagnostic into a hole with no visible destination. That is why debug builds mirror to `stderr` as well as calling the host, rather than treating `stderr` as a fallback for hosts that offer nothing. Launch REAPER from a terminal to read them.
- **[`clap-host`](https://github.com/free-audio/clap-host) is where those messages can actually be read, and it is the only host here that shows anything at all from a release build.** It is the CLAP reference host, it implements `clap.log`, and it routes messages into Qt's logging rather than dropping them the way REAPER does. Since the `stderr` mirror is compiled out of a release build, and Logic cannot be launched from a terminal at all, a `--release=fast` plugin otherwise has no readable diagnostic channel anywhere. It is a **manual** tool and nothing else: not a build dependency, not a CI step, not a substitute for a DAW. Build it once, outside this repository, and keep it:

  ```bash
  brew install ninja rtaudio rtmidi   # cmake, qtbase and pkgconf are already present for other reasons
  git clone --recurse-submodules https://github.com/free-audio/clap-host ~/Development/clap-host
  cd ~/Development/clap-host && cmake --preset ninja-system && cmake --build --preset ninja-system
  ```

  Do not install `qt6`: that alias resolves to the `qt` metapackage, while `find_package` asks only for `Qt6Core` and `Qt6Widgets`, both of which are in `qtbase`, and `qtbase` is linked into `/opt/homebrew` rather than keg-only, so no `CMAKE_PREFIX_PATH` is needed. `--recurse-submodules` is load-bearing, since `clap` and `clap-helpers` are submodules and configuring fails without them; `vcpkg` comes along too and the `ninja-system` preset never touches it. All three declare `cmake_minimum_required(VERSION 3.17)`, above CMake 4's floor of 3.5, so CMake 4.4.2 configures with no policy shim. Then, from a worktree:

  ```bash
  ~/Development/clap-host/builds/ninja-system/host/Debug/clap-host -p "$PWD/zig-out/Fosforo.clap"
  ```

  **Because it takes an explicit path, it reads the worktree rather than `~/Library/Audio/Plug-Ins/`,** which sidesteps the provenance hazard above entirely: no install step and no hash comparison, because you named the file. `-p` accepts the bundle directory or the inner binary and both work, but for different reasons than you would guess. A bare `dlopen` on the bundle fails with `not a file`; `QLibrary` is what resolves it to `Contents/MacOS/Fosforo`, confirmed with `DYLD_PRINT_LIBRARIES=1`, so the bundle form depends on Qt rather than on anything about the bundle. The long option is `--clap-plugin`, not the `--plugin` upstream's README claims.

  **The severity mapping is lossy, and one severity vanishes.** `CLAP_LOG_DEBUG` becomes `qDebug()`, `CLAP_LOG_INFO` becomes `qInfo()`, and `CLAP_LOG_WARNING`, `CLAP_LOG_ERROR`, `CLAP_LOG_FATAL` and `CLAP_LOG_HOST_MISBEHAVING` all collapse into `qWarning()`. `CLAP_LOG_PLUGIN_MISBEHAVING` falls out of the switch entirely and prints nothing, so a message sent at that severity is silently discarded by the one host adopted for reading messages. Nothing emits it today; anyone who adds one should know.

  **In a debug build every message appears twice,** once bare from Qt and once carrying the `[fosforo]` prefix from the `stderr` mirror, and that doubling is the tell for which channel you are reading. A release build shows only the bare copies, which is the positive control that the host path works rather than the mirror. `rendering at N Hz` disappears in release for an unrelated reason, `src/clap/gui.zig:629`, so a release run shows the lifecycle messages and no render meter.

  **It exercises more of the editor lifecycle than the issue proposing it claimed.** `create`, `get_size`, `set_parent`, `set_transient`, `suggest_title`, `show`, `hide` and `destroy` all run, which makes it a second opinion on embedding and, unlike the Audio Unit, a caller of `gui->hide`. Grepping its source for `set_parent` finds nothing, because it drives the plugin through clap-helpers' `PluginProxy`, which renames them to `guiSetParent` and the rest; grep the camelCase names or you will conclude it does nothing.

  **It cannot test resizing, and reaching for it to do so is the mistake worth naming.** `set_size`, `can_resize` and `adjust_size` are never called, and `host/main-window.cc` pins the window with `QSizePolicy::Fixed` and `setFixedSize()`, so the user cannot drag it. The one direction it implements is `guiRequestResize`, plugin to host, which this project does not use. It is not a load test either: a minimal Qt example says nothing about multi-instance behaviour or dropouts, and REAPER and Logic stay the tools for that. It also stays manual permanently, because Qt6, CMake, Ninja, rtaudio and rtmidi are precisely the non-hermetic dependency ADR 0009 keeps off the build, and ADR 0013 already assigns automated GUI verification to `src/smoke.zig`.

  Verified against `c8ce3ee` (2026-06-18), which builds CLAP 1.2.9 against this project's 1.2.10. **Nothing pins that commit,** so re-check after a pull. `MidiInCore::openPort: no MIDI input sources found!` and an empty `Loading with Audio API: ""` are normal startup noise, not symptoms. The window is 960x605 for a 960x540 editor, the extra 65 points being Qt's menu bar. And the editor still looks like a black window in it, so the pixel sample from the render gotcha above is still the check that decides: capture by window id, since a full-screen `screencapture` grabs the main display, which need not be the one clap-host opened on.
