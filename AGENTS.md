# fosforo

## Overview

A Mac-first GPU-rendered phosphor oscilloscope and signal-analysis plugin, authored as a CLAP and rendered with Metal.

The display name is **Fósforo**; the repository, binary, and identifiers stay ASCII `fosforo`.

## Current state

Phase 3 of [the build plan](docs/plans/todo/2026-07-25-repo-foundation-and-phased-build-plan.md), four numbered steps in. **Phase 2 is closed.** The plugin loads in REAPER and Logic, passes stereo audio through, saves state, taps one channel into `src/dsp/ring.zig`, and reads a trailing 20 ms window on the render thread which `Renderer.frame` copies into a per-frame `MTLBuffer`. That the picture is the signal is the one claim no harness could close, because the drawable is `framebufferOnly` and reading it back would change the shipping renderer; it was settled instead by the host procedure in [#38](https://github.com/cboone/fosforo/issues/38), run against hash-verified installs and measured out of screenshots rather than judged by eye.

The trace now deposits additively into a persistent `RGBA16F` ping-pong accumulation pair ([#55](https://github.com/cboone/fosforo/issues/55)), so `shaders/scope.metal` encodes **two** render passes and three draws: `decay_fragment` then `trace_fragment` into the accumulation, and `resolve_fragment` into the drawable. Two chores the plan sequenced behind that one have also landed: `scripts/measure-trace` is committed here and its guard reads colour rather than counting shades ([#64](https://github.com/cboone/fosforo/issues/64)), and `zig build smoke-leaks` runs in CI at 40 cycles ([#63](https://github.com/cboone/fosforo/issues/63)), which refused the peak-RSS slope it was filed to add.

**What the pixels became is now checked automatically** ([#51](https://github.com/cboone/fosforo/issues/51)). `zig build smoke-trace` is a third smoke half, needing a device and no window and required in CI beside `smoke-gpu`: `Renderer` grew a `Surface` union and a second constructor, so the shipping `frame` resolves into a texture the backend owns rather than a drawable, and `src/gpu/measure.zig` reads the result back as rows, periods and implied samples. Ten planted defects were caught, #55's resolve gain among them.

**The resolve is finished** ([#60](https://github.com/cboone/fosforo/issues/60), [ADR 0019](docs/adr/0019-brightness-is-a-fixed-transfer-function.md)). It compresses accumulated energy through extended Reinhard and looks the result up in one of four gradients running to white, into a `BGRA8Unorm_sRGB` drawable so the arithmetic runs in linear light. The hot core ADR 0007 predicted is emergent and is executed rather than claimed: `smoke-trace` drives one deposit and thirty and reads `RGB(143, 224, 154)` and `RGB(255, 255, 255)` off the picture. **The first of those figures was `RGB(75, 189, 96)` here until #96 read it off a run**: #57 gave the beam area and a density scale, so one deposit is brighter than it was when #60 measured it, and the number went stale on a branch that changed nothing about the resolve. The `smoke-trace` transcript is identical at #96's base and tip, so this is a correction rather than a movement. The trace deposits a scalar now; there is no colour anywhere in `shaders/scope.metal`.

**The beam is geometry** ([#57](https://github.com/cboone/fosforo/issues/57)). Each inter-sample segment is an instanced quad and `trace_fragment` shades it by distance from the _segment_, so caps are round, joints have no wedge gaps, and the endpoints at `x = ±1` have area — which closed #38's 1914-of-1920 edge columns at 960 of 960 on a single frame. The width is **3.0 points**, in points rather than pixels so the rail clearance is scale-free, and the profile is the biweight `(1 - u²)²`, whose compact support is what keeps unlit pixels at exactly 0.0. The seam's raw-samples prediction held: still no `MTLVertexDescriptor`, still a plain `[]const f32`. Two consequences that were not anticipated. Overlap at joints retired the "one frame cannot deposit twice on a pixel" premise the tonemap's argument rested on, taking a moving trace from 1.0000 deposits to **2.6133**. And it made per-pixel brightness scale with samples per logical point, roughly `1 + 1.6 * s`, which would white out a moving trace at 192 kHz; `TraceUniforms.density` clamps that, and it is not velocity weighting because it is one number per frame that depends on nothing about the signal.

**Verified in REAPER across four arms.** A 0.5 sine inverts to ±0.5000 exactly, at 48, 96 and 192 kHz alike; the level sweep reads +0.9991, +1.0504, +1.0894 and +1.0894, so the display is honest about level below the rail and stops counting at it, which is ADR 0017 executed rather than asserted. **The joints do not bead**, which was the one thing the plan could not settle by derivation: adjacent capsules overlap along their whole length rather than meeting end to end, because the segment pitch is under the beam width, so coverage is uniform and there is no ripple at the sample period.

**What is left of the phosphor look is filed:** velocity weighting ([#58](https://github.com/cboone/fosforo/issues/58)) and bandlimited reconstruction ([#59](https://github.com/cboone/fosforo/issues/59)).

[#22](https://github.com/cboone/fosforo/issues/22) has landed, which was phase 2 work carried forward rather than a phase 3 step: it is the install-path ambiguity the provenance gotcha below describes, and it had already voided two verification runs of the kind every remaining issue here depends on. Every build now says which worktree and commit it came from ([ADR 0018](docs/adr/0018-stamp-provenance-without-namespacing-identity.md)), `CLAP_PATH` was established to work and is deliberately not used, because this project runs one host stream at a time, and two of the issue's four proposals were refused with measurements rather than built.

[#61](https://github.com/cboone/fosforo/issues/61) has landed, pulled forward from step 9 because shader hot-reload is worth five issues' worth of iteration rather than none. A debug build watches `shaders/scope.metal` and swaps the pipelines without restarting the host, which discharges a consequence [ADR 0009](docs/adr/0009-runtime-shader-compilation.md) recorded when it chose runtime compilation. It also settled the number the rest of phase 3 will be argued against: a source Metal has not seen takes about **40 ms** to compile, against 0.14 ms for one it has, so the compile runs on a thread of its own and hands finished pipelines to the render loop through a mailbox. [#59](https://github.com/cboone/fosforo/issues/59) defers the same "where does slow work run" question about its own upsampling and can reuse that shape.

[#56](https://github.com/cboone/fosforo/issues/56) has landed, and it inherited a value rather than a defect, exactly as this paragraph used to predict: because the white point derives from the decay, the provisional `decay_per_frame = 0.90` was a pure persistence knob, and turning a per-frame factor into a time constant was a matter of naming the rate it was anchored at. That rate is 60 Hz, so `palette.decay_tau_nanos` is `-(1 / 60) / ln(0.90)` or **158.19 ms** and every offscreen number the harness printed before it prints still. On this machine the trail is now twice what it was, because the panel runs at about 120 Hz where a per-frame 0.90 faded twice as fast; at 60 Hz nothing changed. `Renderer.frame` takes an absolute monotonic reading rather than an interval, and `CVTimeStamp` was refused with an argument recorded in `src/platform/displaylink.zig`.

[#77](https://github.com/cboone/fosforo/issues/77) has landed, which is the gap #61 opened by making the shader reloadable: everything tying the Zig constants to the MSL read the _embedded_ copy at comptime, so a swapped-in file got `buildPipeline`'s missing-function check and nothing else. `bindingIndexIn` now takes its source as a parameter and one `bindings` table has two readers, the comptime test over the embedded copy and `noteBindings` over whatever came off disk. **A mismatch is warned about and swapped in anyway**, and that decision was settled by measurement rather than by taste: rendering three shaders with one index moved apiece, one per index space, every draw completed and the unbound argument read as **zeros**, giving a flat trace, a black background and no trace at all. So refusing the swap would have been trading a wrong picture the next save fixes for a reloader people stop trusting. `iface.ShaderStats.binding_mismatches` is what makes the check assertable rather than trusted. **It closes half a class**: `TraceUniforms` layout drift is still readable from nowhere, because MSL computes its own offsets.

[#92](https://github.com/cboone/fosforo/issues/92) has landed, which is item 4 of [the verification-gaps program](docs/plans/todo/2026-09-04-close-the-verification-gaps-in-the-test-suite.md) rather than a phase 3 step, and it is the same argument ADR 0013 won at #51 applied to the half that was left out. `src/gpu/measure.zig` reads a trace back as numbers and has its own tests; the thirteen `check*` functions deciding whether those numbers were the right ones lived in a 2,240-line file with **zero** test blocks that `zig build test` never compiled. The judgements are now `src/gpu/verdict.zig`, the harness keeps the driving, and `zig build smoke-trace`'s transcript is byte-identical across the move. The suite went from 230 tests to 252, and the plant table in `docs/plans/done/2026-08-29-verify-the-shader-offscreen-against-the-constants.md` gained a column naming the test that covers each row, which is what makes those plants regress rather than being prose about a check nobody re-runs. **Planting the judges is where the findings were:** a blank readback used to pass the decay checks outright, because `nan` compares false; the `expectClose` defect the issue named turned out not to exist, while a different one did; and two tests that encoded a plant were not covering it, having been planted far enough outside a bound to be caught by something else.

[#93](https://github.com/cboone/fosforo/issues/93) has landed, which is item 5 of the same program and the same move one layer down. `renderer.zig`'s `Watcher` is `if (shader.live) struct { ... } else struct { ... }` and `shader.live` folds in `!builtin.is_test`, so a test binary took the stub: the real `poll` was not merely untested but **not compiled**, and no test written in `zig build test` could have reached it. The same gate stood over `buildPipelines` and `readShader`, which carried a second copy of the bookkeeping, and the two copies **disagreed** — a compile failure under the watcher moves `rejected` alone, because nothing falls back, while the same failure when an editor opens moves `rejected` _and_ `fallbacks`. That was two pairs of `fetchAdd` calls two thousand lines apart; it is now `src/gpu/metal/reload.zig`, a six-row table with a test that reads it, beside the poll's `seen` state machine. The suite went from 297 tests to 318 and both smoke transcripts are unchanged.

**The finding is that the issue named an instrument that does not work.** #93 says its acceptance plant, a `poll` advancing `seen` only on success, is one "today only a hand-run `smoke-appkit` would catch". Run against `poll` as it stood, before anything moved: `zig build test` reported 297 of 297 and `zig build smoke-appkit` reported `ok`, with all five hot-reload arms running. **Nothing caught it.** Two more things planting produced. A third site the issue did not name, `noteBindings`, whose counter increment no test binary compiled either, because a private function reached only from gated call sites is never analyzed — `firstBindingMismatch` beneath it had five tests and the pairing had none. And a weakness in `hotReloadPhase`'s fourth arm, which under that defect can pass without the renamed shader ever being read, since it waits on `rejected >= n + 1` while the previous arm's broken file is still being re-rejected four times a second. That one stays open.

## Non-negotiables

These are settled decisions recorded in [`docs/adr/`](docs/adr/). Do not relitigate them in code review; supersede them with a new ADR instead.

- **macOS on Apple Silicon only.** Not a portability oversight (ADR 0001).
- **Zig is pinned to 0.16.0.** `build.zig.zon` is the single source of truth and CI reads it. Compiler bumps are deliberate, scheduled work (ADR 0002).
- **The plugin is authored once, as a CLAP.** Never author an Audio Unit or VST3 directly; clap-wrapper projects outward (ADR 0003).
- **Metal must not leak above `src/gpu/iface.zig`.** That seam is load-bearing even though only one backend exists (ADR 0005).
- **No WebView UI** (ADR 0006).
- **Nothing reachable from the audio thread may allocate, lock, or make a syscall** (ADR 0010).
- **The GUI smoke harness is an executable behind its own steps, never part of `zig build test`** (ADR 0013).
- **`std.Io` is reached through the one instance in `src/platform/io.zig`, constructed with `init_single_threaded` and never with `Threaded.init`.** Guarded since #90 by a comptime assertion on the value and a canary on the shape, and by the compiler, which refuses the direct substitution outright (ADR 0015).
- **The ring's release store and acquire load are verified by `zig build ring-race`, and the gate's by `zig build gate-race`, each guarded by a canary in its own file.** Weakening either without reading ADR 0016 is the failure this exists to stop (ADR 0016, #91).
- **Every ordering-critical declaration is canaried against its own source**, through `src/canary.zig`: the ring's five atomics, the `std.Io` constructor, `Gate`'s five in `src/clap/gate.zig`, `Pending` in `src/clap/gui.zig`, and `Mailbox` and `Watcher.halt` in `src/gpu/metal/renderer.zig` (#90, #91).
- **The vertical axis is absolute. The display never rescales itself to the signal, and over-scale rails rather than being hidden or clipped away** (ADR 0017).

`zig build` alone produces a loadable `.clap`, which REAPER opens natively. That is the day-to-day loop and it never invokes CMake.

**Every `install-*` step builds exactly what it installs, copies it to `~/Library/Audio/Plug-Ins`, and prints the hash of what landed; every other step stays in the worktree.** That invariant is the whole distinction between the steps whose names begin with "install", including Zig's own, which writes to `zig-out` and says so in `zig build --help`. It is also what closed #43: both install steps used to build the CLAP and neither built the Audio Unit, so `install-plugins` installed a component only if CMake happened to have been run in that worktree already, and a worktree where it had not kept whatever component another branch had installed and said nothing about it.

CMake is needed only for the Audio Unit that Logic requires, and it is much slower because it fetches the AudioUnit SDK. `zig build audio-unit` runs `scripts/build-audio-unit`, which configures only when `build/` is absent and builds `fosforo_all`; those are the two things worth getting right and they are no longer something to remember:

```bash
cmake -B build cmake/                       # what the script does once per worktree
cmake --build build --target fosforo_all    # and every time; not fosforo_auv2, see below
```

Validate with `clap-validator validate zig-out/Fosforo.clap`. CI runs it on every push against **both** `.clap` bundles, the Zig-built one and the clap-wrapper-built `build/assets/Fosforo.clap`, so neither is only a local step, and it asserts every bundle's signature alongside them. The Audio Unit has no equivalent: `auval` cannot see this component at all, for the reason in the gotchas below, so loading it in Logic is the only check there is.

## Releasing

A release is a single signed, notarized, stapled `.pkg` that places both bundles (ADR 0014). It is built locally and deliberately never in CI, because this repository is public and the alternative is Developer ID private keys in repository secrets. Three steps, each independently re-runnable, so a rejected notarization does not cost a rebuild:

```bash
export FOSFORO_SIGNING_IDENTITY="Developer ID Application: ..."
export FOSFORO_INSTALLER_IDENTITY="Developer ID Installer: ..."
scripts/build-release-bundles          # both bundles, hardened and timestamped
scripts/build-installer                # one pkg, signed with the Installer identity
scripts/notarize-installer dist/Fosforo-VERSION.pkg
```

`scripts/build-installer --unsigned` exercises packaging without a certificate. It cannot be notarized, is named so it cannot be mistaken for a release, and skips the input signature check, which it says out loud.

The credentials `notarytool` needs live in a keychain profile, never on a command line:

```bash
xcrun notarytool store-credentials "fosforo-notary" \
  --key ~/path/AuthKey_XXXXXXXX.p8 --key-id XXXXXXXX --issuer XXXXXXXX-...
```

An App Store Connect API key rather than an app-specific password, because it is scoped, independently revocable, and not the Apple ID password. The `.p8` downloads once and never again, so the copy on disk is the only copy; `.gitignore` covers `*.p8` for that reason.

**The certificates on hand expire 2027-02-01 and replacing them is outstanding** ([#30](https://github.com/cboone/fosforo/issues/30)). They were issued through Xcode under the G1 intermediate rather than G2, which caps both leaves at their issuer's expiry; the gotcha below has the full diagnosis and the check that surfaces it. Nothing already signed is at risk, because a secure timestamp outlives the certificate — what stops is signing anything new, and on current sequencing that happens before v0.1.0 is cut. Re-issue from the developer portal rather than Xcode, and do not revoke the superseded pair.

## Rules

Every one of these is here because omitting it causes **silent damage or a wrong pass**, not a legible error. The reasoning behind each is in the note named beside it; these lines are the part that has to be in context before you have opened anything.

- **Confirm provenance before trusting any result a host gave you.** The failure reads as a pass. `zig build install-clap` builds what it installs and prints the hash and provenance of what landed. See [host verification](docs/notes/host-verification.md).
- **One host stream at a time.** Install, launch, read. The shared plug-in folder and the window server are both exclusive, so a second stream corrupts someone else's run, not only yours. See [host verification](docs/notes/host-verification.md).
- **The REAPER pipe needs `2>&1` and `grep --line-buffered`, and each fails differently.** Without the first the plugin's lines pass through unfiltered; without the second the render meter arrives in bursts minutes apart, which reads as a stopped render loop. See [reading diagnostics](docs/notes/reading-diagnostics.md).
- **Run the worktree's own `scripts/measure-trace`, never a copy from anywhere else.** It restates constants a branch may have moved, so another copy runs and reports confident numbers against the wrong mapping. See [measuring a capture](docs/notes/measuring-a-capture.md).
- **Verify at 48 kHz.** Above it the window holds more samples than the drawable has pixels, and structure that appears only at a higher rate is moiré rather than signal. See [trace and phosphor physics](docs/notes/trace-and-phosphor-physics.md).
- **Captures go in `verification/`, never into a commit.** They are working artifacts of one session; what belongs in the repository is the numbers read out of them. One reached a commit before this rule existed and removing it meant rewriting three commits.
- **`zig build` does not rebuild the smoke harness.** `zig build && zig-out/bin/fosforo-smoke appkit 40` runs whatever a previous smoke step left there, with no warning and no hash to compare. Run a smoke step. See [the smoke harness](docs/notes/smoke-harness.md).
- **Run Prettier before the Markdown linter, and never pass `--fix` to `markdownlint-cli2`.** `npm run format` then `npm run lint:md`. `--fix` ignores the files you name and rewrites everything matching its `globs`, including completed plans. See [linters](docs/notes/linters.md).
- **Select files for `shfmt` with `git ls-files`, never `shfmt -d .` or `-w .`.** `shfmt` does not read `.gitignore`, so a tree walk reaches vendored scripts under `build/`. A fresh CI checkout has no `build/`, so this passes there and fails locally. See [linters](docs/notes/linters.md).
- **When a diff corrects a measured figure, grep the old value across the repository.** Figures here are quoted across `AGENTS.md`, `CHANGELOG.md`, several ADRs, the build plan and sometimes a workflow comment, so a correction applied where you noticed it leaves the stale copies reading as current.
- **Anything in `docs/plans/done/` is a historical record.** Never update a citation, a figure or a line number in one. A done plan's `path:line` citations are pre-change locations and are correct precisely because they no longer resolve. `docs/notes/` is the opposite: living, and corrected in place.
- **No job counts or run counts in prose about CI.** A declared job is not a rollup entry and reusable workflows expand, so any count goes stale on the next workflow edit. Anchor a measurement to a run id or leave it out. See [CI workflows](docs/notes/ci-workflows.md).

Two more are settled decisions rather than rules of thumb, and are stated in full under [Non-negotiables](#non-negotiables): nothing reachable from the audio thread may allocate, lock, or make a syscall; and no Metal type may be named above `src/gpu/iface.zig`.

## Gotchas

- **`xcrun` caches tool lookups.** If `xcrun metal` reports the Metal toolchain missing right after installing it, run `xcrun --kill-cache`.
- **CLAP bindings come from preprocessed headers.** Zig 0.16's `translate-c` mishandles `#pragma once` under path aliasing, so `build.zig` runs the headers through `zig cc -E` first. Object-like macros do not survive that; the ones that matter are restated and tested in `src/clap/c.zig` (ADR 0004). **Do not `refAllDecls` the translated module.** `translate-c` leaves `@compileError` stubs for declarations it could not translate, eight of them here, and referencing one detonates it: the sweep fails on `__nonnull` from `<builtin>`, a compiler attribute with nothing to do with CLAP, so the error reads as this project's bug. `src/clap/c.zig`'s own sweep therefore covers that file's declarations and `feature`, and reaches `c` only as a value, which does not descend (#95).
- **`unnamed_0` is toolchain-generated.** The anonymous union in `clap_window` is reached only through `clap.cocoaView()`. Re-verify after any Zig upgrade.
- **Metal's and AppKit's constants are hand-restated.** Their headers are Objective-C, so `translate-c` cannot read them the way it reads CLAP's. `MTLPixelFormat`, `MTLLoadAction`, `MTLStoreAction`, and `MTLPrimitiveType` live in `src/gpu/metal/renderer.zig`, and #60 added two of the first — `BGRA8Unorm_sRGB` at 81 and `RGBA32Float` at 125, both read out of `MTLPixelFormat.h` rather than recalled, which is the practice that caught the line-strip enum; `NSView.autoresizingMask` lives in `src/platform/objc.zig`. Unlike the restated CLAP macros in `src/clap/c.zig`, there is no surviving header symbol to test them against. They are ABI values Apple cannot renumber, and a wrong one shows as a black or garbled drawable rather than as anything subtle. **The two `NSView.autoresizingMask` values now have a pin anyway** ([#97](https://github.com/cboone/fosforo/issues/97)), on `c.zig:69`'s precedent and with its disclaimer: it restates 2, 16 and their OR a second time and catches a one-sided edit, which is all a restatement can do without a symbol to compare against. The pair is asserted separately as well as combined, because the OR alone reads 18 either way and cannot see the two swapped. The Metal constants have no equivalent, for the reason the sentence before this one gives: a wrong pixel format is loud, while a transposed autoresizing mask silently breaks a resize and nothing else here would say so.
- **`@embedFile` reaches `shaders/` through the import table.** It resolves relative to the importing file and cannot escape the module root, which is `src/`. `build.zig` adds the shader with `addAnonymousImport`, which is why `@embedFile("scope.metal")` works from `src/gpu/metal/`. Keeping shaders outside `src/` is deliberate: `zig build validate-shaders` treats that directory as shaders rather than as Zig.
- **Keep three deployment targets in step:** `build.zig`, `cmake/CMakeLists.txt`, and `macos/Info.plist` all specify macOS 11.0.
- **`build.zig` runs `git` at configure time, and three things about that are easy to get wrong.** It stamps the branch and commit into every binary (ADR 0018), and none of the following is stylistic. **`git rev-parse --abbrev-ref HEAD --short HEAD` prints the branch name twice**, because `--abbrev-ref` is sticky across every ref that follows it, so a combined call silently puts the branch in the field meant for the commit and produces a line that is wrong while still looking well-formed; use two calls. **Failure is a supported state, not an error**: `b.runAllowFail` with `.ignore` on stderr, never `b.run`, because `b.run` calls `process.fatal` and a tarball built from `build.zig.zon`'s `.paths` carries no `.git` at all, which must yield `branch=unknown` and a clean build. And **this costs ADR 0009 nothing**, on a stronger precedent than `/usr/bin/codesign`: `b.dependency("objc", ...)` already runs zig-objc's build function at configure time, which executes `xcrun` to find the SDK that nothing here can link Cocoa or Metal without, so a subprocess and a working Xcode or CLT install were both hard requirements before this existed. Where `xcrun` failing is fatal, `git` failing is not. The cost that is real: the option values feed the module's cache key, so the first build after each commit is a full rebuild.
- **The AUv2 build rewrites its own `Info.plist`.** Two `POST_BUILD` scripts correct what clap-wrapper generates, and the `clap-wrapper` CI job asserts both results independently, because a rewriting step cannot detect its own absence. `cmake/narrow-au-resource-usage` strips a hardcoded `resourceUsage` dictionary claiming network and whole-filesystem access, emitted next to the `sandboxSafe` flag that Apple documents as mutually exclusive with it; it no-ops safely if clap-wrapper stops emitting it, so re-check when the pin moves. `cmake/set-au-display-name` replaces the generated name and description, for the reason in the display name bullet below. Both must stay ahead of the signing command, which is the third and last `POST_BUILD` command on that target; see the next bullet for why the order is load-bearing.
- **Every bundle is signed by the build, and two different signatures are involved.** The linker ad-hoc signs the Mach-O binary on arm64 unconditionally, which is why these bundles load at all, but that signature covers only the binary: it reports `flags=0x20002(adhoc,linker-signed)` and `Sealed Resources=none`, and `codesign --verify` rejects the bundle with `code has no resources but signature indicates they must be present`. The bundle signature is a separate thing and nothing upstream supplies it. clap-wrapper's only `codesign` calls sign its own generated AUv2 build helper, `wrap_clap.cmake` has none at all, and `make_clapfirst.cmake` states that signing is the consuming project's decision. So `build.zig` signs `zig-out/Fosforo.clap` and `cmake/CMakeLists.txt` signs both bundles it builds, all three ad-hoc, and CI asserts all three. Override the identity with `zig build -Dcodesign-identity=` or `-DFOSFORO_CODESIGN_IDENTITY=`, and both call sites then add `--timestamp` and `--options runtime` as well, because notarization rejects a submission missing either. Those two follow from the identity rather than being switches of their own, so a distributable signature cannot be half-configured, and neither is ever applied ad-hoc: `--timestamp` would make a plain build need the network, and an ad-hoc signature has no certificate whose expiry a timestamp could outlive. `scripts/assert-adhoc-signature` guards that in both CI jobs, and it asserts a negative `codesign --verify` cannot: a conditional that leaked would still produce a valid signature, so the first symptom would be a job hanging on Apple's timestamp server rather than failing anything legible. It checks three independent marks, because they fail independently: the `runtime` flag, a `Timestamp=` line, and an `Authority=` chain. The positive direction has no CI equivalent, since no runner has a certificate, and is checked by hand. **The AUv2 signing command must remain the last `POST_BUILD` command registered on that target,** because signing seals the `Info.plist` the two scripts above rewrite: sign first and `codesign --verify` reports tampering rather than a missing signature, which is worse than not signing. That is also why the `clap-wrapper` job runs `codesign --verify` and both `--check` scripts together and treats the three as one test: signing in the wrong order passes the two `--check` runs and fails the signature, while a dropped signing step fails only the signature. `/usr/bin/codesign` is a base-OS binary rather than an on-demand Xcode component, so none of this costs the hermetic build ADR 0009 protects. Every automated invocation names it by absolute path rather than resolving it through `PATH`, so that stays true even where a wrapper or shim shadows the name; the commands above are the short form because a human types those.
- **Releasing involves two different certificates, and one of them is invisible to the usual check.** Bundles are signed with Developer ID **Application**; the pkg is signed with Developer ID **Installer**. `security find-identity -v -p codesigning` lists the first and **not** the second, because the `codesigning` policy does not match installer certificates, so a null result there is not evidence that one is missing. Check with `security find-identity -v` and no policy argument, and confirm the Application certificate appears in the same output as a positive control. An Apple Development certificate is the trap worth naming: it signs, timestamps and hardens exactly like a Developer ID Application one and passes `codesign --verify --strict`, and it will never notarize. Nothing short of reading the `Authority=` line tells them apart, which is what `scripts/assert-distributable-signature` exists to do.
- **A Developer ID certificate's expiry is capped by its issuer's, and Xcode can hand you a nearly-dead issuer.** The pair issued on 2026-08-04 expire 2027-02-01 `22:12:15`, six months out rather than the usual five years, and both match that instant _to the second_ despite being issued 33 seconds apart. That is Apple clamping a leaf's validity to its issuer's `notAfter`: Xcode's Manage Certificates panel issued them under the G1 `Developer ID Certification Authority`, which expires exactly then, rather than under `OU=G2`, which runs to 2031-09-17 and is already trusted in the login keychain. Nothing in the usual toolchain shows this. `security find-identity -v -p codesigning` prints neither expiry nor issuer, and `codesign -dvv` names the authority without its validity window; `security find-certificate -c "<name>" -p | openssl x509 -noout -issuer -dates` is the only check that surfaces it. Signed artifacts are unaffected, because a secure timestamp makes a signature outlive its certificate, which is the whole reason `--timestamp` is mandatory here; what expires is the ability to sign anything new. Issue replacements from the developer portal rather than Xcode, and do not revoke the superseded pair: revocation is for compromise and can invalidate already-distributed software. See issue #30.
- **`codesign --verify` and `spctl --assess` answer different questions, and passing the first says nothing about the second.** `codesign` asks whether the signature is internally consistent; Gatekeeper asks whether this machine will run the thing. Worse, a locally built file has never carried `com.apple.quarantine`, so assessing one is not a test of the download path at all. The only honest check is to fetch the release from a URL **in a browser**, confirm `xattr -p com.apple.quarantine` returns a value, and assess that copy. `curl` does not set the attribute and cannot substitute. `scripts/notarize-installer` runs the local assessment and says so, rather than implying it proved more than it did.
- **Only the pkg is stapled, not the bundles inside it.** Files laid down by an installer do not receive `com.apple.quarantine`, so the pkg's ticket is the one Gatekeeper consults and a per-bundle ticket would be a notarization round trip nothing reads. If installed bundles ever start being refused, the fallback is a first submission over a zip of the two bundles, stapling each before packaging.
- **`cmake --build` no longer touches `zig-out`, and the optimize-mode split it caused is still there.** Two facts that used to travel together and now do not. `cmake/CMakeLists.txt` drives Zig itself, through an `ALL` custom target, because the only thing CMake wants from Zig is `libfosforo_impl.a`. That target used to run a bare `zig build --release=fast`, which also reassembled the Zig-built bundle and signed it ad-hoc, since it passes no `-Dcodesign-identity`: a CMake build silently replaced whatever `zig build -Dcodesign-identity=` had produced, and every check afterwards read a different file than the one that was signed. It now runs `zig build --release=fast --prefix build/zig impl`, and **both halves of that are load-bearing.** The `impl` step assembles no bundle and signs nothing; the prefix keeps its ReleaseFast archive out of `zig-out/lib`, where it would otherwise race a Debug one from any concurrent `zig build`. Measured rather than assumed: the CLAP's hash _and_ its mtime are unchanged across a full `cmake --build`, and `codesign --verify` passes afterwards. The ordering in `scripts/build-release-bundles` is consequently no longer load-bearing, and is kept only because reversing it buys nothing. What survives unchanged is the optimize-mode disagreement: `standardOptimizeOption` declares no default, so a plain `zig build` is **Debug** while everything CMake triggers is **ReleaseFast**, and after `zig build install-plugins` the installed CLAP is Debug next to a ReleaseFast Audio Unit. That is right for local work, since Debug is what emits the render meter REAPER can show and Logic can show nothing under any mode, and wrong for a release: a shipped CLAP must be built `--release=fast` explicitly, which is what `scripts/build-release-bundles` does.
- **The hardened runtime costs this plugin nothing, and an entitlements file would be inert.** Notarization requires `--options runtime`, and the obvious worry is that ADR 0009's runtime shader compilation needs `com.apple.security.cs.allow-jit` or one of the `allow-unsigned-executable-memory` family. It needs neither, for two independent reasons, both measured rather than reasoned about. First, `newLibraryWithSource:` compiles **out of process**: Metal hands the source to `MTLCompilerService.xpc`, an Apple-signed XPC service inside `Metal.framework`, so no executable memory is ever created in the caller's address space and there is nothing for a JIT entitlement to permit. A standalone binary signed `--options runtime` with no entitlements at all compiles `shaders/scope.metal` and resolves both functions, which is a _stricter_ case than the plugin's. Second, entitlements attach to a process, and a plugin never gets one: it is loaded into the host's address space, so the host's entitlements apply and its own are ignored. REAPER runs hardened and carries `allow-jit`, `allow-unsigned-executable-memory` and `disable-library-validation`, that last being what lets it load a bundle signed by another team at all; Logic hosts AUv2 out of process in Apple's `AUHostingServiceXPC`, which carries the latter two. So there is deliberately no `entitlements.plist` in this repository, and adding one would change nothing about how the plugin runs. Re-measure before assuming otherwise; do not add entitlements speculatively.
- **A minimum editor size binds the view, and no host is obliged to bind its window to it.** `clap_gui_resize_hints_t` carries resizability and an aspect ratio and no bounds at all, so `adjust_size` and `clap_host_gui.request_resize` are the only two mechanisms, and both are requests. REAPER 7.78 implements `request_resize`, returns true, and keeps the plugin's view at the minimum; its own FX window still drags smaller, clipping the view inside it. **That is REAPER's behaviour rather than a defect here, established with a positive control:** a third-party plugin with a fixed size in Logic is also freely resizable in REAPER, so REAPER does not constrain its window to any plugin's declared size. `Editor.pushBack` is still worth its lines, because without it REAPER leaves the `NSView` a few points under while the drawable sits at the minimum, and the two disagree about the surface being rendered into. Whether another host binds its window is untested; only REAPER and Logic are available here.
- **A host can send a negative window dimension, and CLAP types them `u32`.** Dragging an editor's bottom edge up past its top makes REAPER send heights of 4294967295 and 4294967274, which are -1 and -22 computed as signed `CGFloat`. `clampAxis` in `src/clap/gui.zig` collapses anything above `i32`'s range to the minimum rather than the maximum, because no display is two billion points across and a drag that ran past zero is what actually happened. Left unguarded this reached Metal: the mailbox saturated the value to 65535 and asked for a 960x131070 drawable, eighty times the texture limit, from a thread with no way to refuse.
- **`MTLStorageModePrivate` textures are invisible to `leaks` and to peak RSS both**, which is one instrument worse than the `MTLBuffer` case below and does not follow from it. A leaked buffer moves peak RSS from 47.7 MB to 57.7 MB; a leaked accumulation texture moves it from 44.1 MB to 44.3 MB while leaking nearly two gigabytes, because shared storage is in the process's resident set and private storage is not. `gpu.Renderer.liveTextures` is therefore the only instrument rather than the better of two, and it carries an obligation `liveWindowBuffers` does not: these are rebuilt on every resize that changes the pixel count, so the resize path has to decrement as well. It still cannot catch a `releaseAccumulation` that stops sending `release`, since the count returns either way. **Shared storage is not the escape it sounds like**, which #60 measured rather than assumed: its palette lookup is sixteen kilobytes in `Shared`, and forty cycles leaking one apiece moved the `leaks` byte total from 12,544 to 12,544, against the 640 KiB a visible leak would have added. Same blindness, so it joined this counter and the operation was renamed rather than a ninth being added — the rule ADR 0013 set is to _measure_ separately, not to _count_ separately.
- **The phosphor's fade is a time constant, and three things about how it reaches the shader are easy to get backwards.** `palette.decayOver(elapsed)` is `exp(-dt / tau)` with `tau` at 158.19 ms, derived at comptime from the pair `(60 Hz, 0.90)` so the anchor is the thing to argue with rather than a decimal. **`Renderer.frame` takes an absolute clock reading, never an interval**, because it is the only thing that knows which ticks committed: six early returns can skip one, and the time a skipped tick spanned is owed to whichever frame draws next, so the clock advances beside `accum_source` after `commit` and nowhere else. Hoisting that line above the semaphore wait was planted and it does not fail the decay check — it fails `CoreNotWhite`, because a retry after `.no_frame_slot` then sees a zero interval, nothing fades, and thirty deposits pile up to 29.703 against 9.539 while the white point stays where it was. **The first frame of a renderer's life stands in one interval at the reference rate rather than zero**, which looks like the fussier choice and is not: the fade is a no-op on a cleared pair either way, but zero sends `whitePoint` to its 8e5 clamp for that frame, which `smoke-trace` caught at two levels off its prediction and no eye would have. **That 8e5 is now a pinned figure rather than an arithmetic accident** ([#96](https://github.com/cboone/fosforo/issues/96)): the clamp's floor is `palette.min_dwell`, restated in `shaders/scope.metal` and `scripts/measure-trace` and pinned in both constants tests, and `zig build test` holds `whitePoint(1.0)` at 8e5 as a literal. Deriving that expectation from `white_headroom / min_dwell` would move with the constants it guards, which is why it is written out. Before it existed, moving the floor from 1e-6 to 1e-5 in all three languages at once left the suite at 285 of 285 passing. And the `exp` is computed once per frame on the CPU rather than once per pixel in MSL, which is what `AccumUniforms` carrying a decay rather than a `dt` and a `tau` buys.
- **The clock is `display_link.monotonicNanos()` and `CVTimeStamp` was refused, which is the reverse of what `src/platform/displaylink.zig` promised for two phases.** The argument is in that file and is not "the cheap one won": exponential decay composes, `exp(-(a + b) / tau) = exp(-a / tau) * exp(-b / tau)`, so the total fade depends on how long an interval was and not on how it was cut into frames. Both clocks are monotonic and both sum to the same wall time, so `output_time` buys a better subdivision on a frame that misses its deadline — at most one refresh period of phase error against a 158 ms constant, absorbed by the next interval rather than accumulated — against the cost of laying out 80 bytes of `CVTimeStamp` with a nested `CVSMPTETime` by hand, checked by nothing, where a wrong offset yields a plausible `dt` and a phosphor at the wrong speed. `src/gpu/palette.zig` holds the composition property as a test, so the premise is executable rather than asserted.
- **`zig build smoke-trace` is the only instrument that can see frame-rate independence, and the reason no screenshot can is structural.** Every other case there measures one frame, or a run at one rate; this is a claim about how successive frames _differ_, which is why #56's body expected it to be checked by pinning a display to 60 Hz in System Settings and judging a fade by eye. `checkDecayIsInRealTime` fades the same 96 ms as twelve 8 ms steps and as six 16 ms ones and asserts the two agree: 0.5430 and 0.5439 against a predicted 0.5451, 0.18% apart, where a per-frame factor would give 0.2824 and 0.5314. **Two traps if you touch it.** The span is 96 ms rather than 100 so both arms divide it into whole nanoseconds and cover the identical interval. And the expectation is composed per step rather than asked of the span, because `palette.max_elapsed_nanos` is 41.7 ms and `decayOver(96 ms)` clamps: it predicts 0.7684 against a true 0.5451, which is the first thing this check caught and it was in the check itself.
- **Metal has no line-width API, which is why the beam is geometry rather than a line.** Verified against the SDK headers rather than assumed: no `lineWidth`, no `setLineWidth`, nothing equivalent anywhere in `Metal.framework`. That is why the phase 2 trace was one device pixel, half a point on a 2x drawable, thin and jagged. #57 fixed it the only way ADR 0007 permits: each inter-sample segment is an instanced quad and the fragment shades it by distance from the segment, so the width is **3.0 points** and the antialiasing is the profile. The three wrong ways are still wrong and are recorded so they are not re-proposed: sub-pixel redraws triple the draw and stay aliased; MSAA needs `sampleCount` on the pipeline, the layer and the attachment plus a resolve, and ADR 0007 wants analytic antialiasing _instead_; and a line-width extension does not exist to be asked for.
- **The rail sits inside the drawable, and the reason changed at #57 while the value did not.** It used to be the rasterizer's coverage diamond: a one-pixel line centred on the drawable's boundary has half its diamond off-screen and may light nothing, so a railed signal would read as an absent one, which is the worst possible way for a level indication to fail. A quad has area and does not inherit that. What `iface.trace_rail`'s 1% now has to hold is the **beam's own half-width**, since a profile centred on the boundary loses whatever falls outside and the centroid `src/gpu/measure.zig` reads is dragged inward. The arithmetic is better than it was, because it is now scale-free: 1.5 points of half-width against `(1 - 0.98) * 135`, or 2.7 points, at the smallest editor `clampSize` permits, both in points, so the display's scale cancels instead of the guarantee holding separately at each one. `src/clap/gui.zig` holds the test and its bound moved with the reason.

  **The centre-line half pixel is answered, and the answer is that no bias was ever needed.** #38 measured silence in REAPER drawing a flat line on row 539 rather than 540 at 1920x1080, reading back as `+0.0021`, and declined the `+1.0/H` NDC bias on three grounds — two of which #57 falsified, since `Renderer` now stores its size and this is the step that re-answered the question. It turned out the geometry was never off: the _estimator_ was reading the beam's top edge. A symmetric profile centred on the boundary between two rows weights them equally, so its energy-weighted centroid is that boundary exactly, and `zig build smoke-trace` now reads **centroid row 269.500, implying a sample of 0.00000** at 960x540. Nothing was biased and nothing needed to be. What would still be worth investigating is the line _flickering_ between rows during playback, which would be a tie-break going unstable; that was watched for and did not happen.

- **The trace has a floor, and it is arithmetic.** One backing pixel of excursion needs a sample of `1 / (trace_full_scale * height / 2)`: about -54 dBFS at the default editor on a 2x display, about -42 dBFS at the smallest editor on a 1x one. Below that a sine moves the trace less than a pixel and reads as flat. It is the bottom of any level sweep and it is the price of ADR 0017's fixed axis, paid knowingly.
- **It has a ceiling too, and above 48 kHz the display invents structure rather than losing it.** The 20 ms window holds `0.02 * sample_rate` samples: 960 at 48 kHz, against a 960-point default editor, which is why [#37](https://github.com/cboone/fosforo/issues/37) chose that length and recorded that anything above it would alias. At 96 kHz it is 1920 samples, which on a 1x display at the default width is two per pixel and four in an editor dragged to its 480-point minimum. Every one of them is drawn, so what reaches the screen is whichever the rasterizer's coverage happens to catch. **On periodic material that is moiré, and moiré looks exactly like a real low-frequency component** — the display asserting something the signal does not contain, which is the same category of failure ADR 0017 refuses on the vertical axis rather than a cosmetic roughness. [#62](https://github.com/cboone/fosforo/issues/62) is min/max decimation and is the fix; `src/dsp/decimate.zig` has been reserved for it since phase 0 and does not exist yet. Until it lands, **verify at 48 kHz**, and treat any structure that appears only at a higher rate as suspect before believing it.
- **Railing is invisible at the level where it starts, and looking for a flat top is the wrong test.** Clamping begins at `trace_rail / trace_full_scale`, which is 1.0889 or +0.74 dBFS, and at exactly that level it removes a tenth of a backing pixel of travel at the default editor. A plateau reaches one pixel deep at 1.091 and five at 1.100; the sine that loses 443 pixels and looks obviously clipped is at 2.0. **What railing actually shows is the peak ceasing to climb:** 1.000 peaks 43 px below the rail, 1.050 peaks 19 px below it, and every level from 1.089 up peaks on exactly the same row. That saturation is the whole of what ADR 0017 means by declining to say how far over the signal is, and a level sweep that watches for a flat top instead of a stalled peak will report a defect that is not one. A saw is the sharper probe at small overshoots, because it crosses the rail on a linear ramp rather than at a turning point.
- **Stopping the transport draws a bright vertical line that lingers for about a second, and it is the signal rather than a defect.** A host does not stop calling `process` when the transport stops; it keeps the audio device running and hands over silence. So the ring holds a **step** from the last sample to zero, one inter-sample interval wide and up to the full drawable tall, and the beam draws it faithfully. Two things make it prominent rather than subtle, and neither is a bug. Every segment currently deposits the same energy per pixel whatever its screen length, so a segment spanning 500 rows lights all 500 as brightly as an informative slow one. And #60's move to `BGRA8Unorm_sRGB` made the toe 12.92 times steeper, so a single deposit now stays above green 16 for 54 frames rather than 31, roughly doubling visible persistence. [#79](https://github.com/cboone/fosforo/issues/79) tracks it, and **the expected resolution is that [#58](https://github.com/cboone/fosforo/issues/58) closes it as covered rather than fixed**: velocity weighting is precisely the relationship this artifact violates, and under it a 500-row segment would deposit 1/500 as much per pixel and be dim by construction. Check #58 against it before writing any rule to suppress it. Distinct from a _stale_ window, which is [#53](https://github.com/cboone/fosforo/issues/53) and looks nothing like this: there the picture stops changing, here it changes correctly and the change is ugly.
- **Logic cannot be launched from a terminal to read the plugin's diagnostics, the way REAPER can.** Running `Logic Pro.app/Contents/MacOS/Logic Pro` directly starts it outside the launch services path it expects and most plugins then fail to register, so the run is not the one worth measuring. There is no equivalent of REAPER's terminal-launch trick, and the debug `stderr` mirror in `src/clap/log.zig` is therefore unreadable in Logic. Verify the Audio Unit by the pixel sample described above, or by `zig build smoke-appkit`, and treat the CLAP in REAPER as the place diagnostics are read.
- **The display name lives in four places.** It cannot be derived from one source, because it crosses Zig, CMake, and a generated plist. `src/clap/plugin.zig` holds the CLAP descriptor's `name` and `description` and is the source of truth; `macos/Info.plist` carries `CFBundleName` and `CFBundleDisplayName` for the Zig-built bundle; `DISPLAY_NAME` in `cmake/CMakeLists.txt` covers the CLAP that CMake builds; and `cmake/set-au-display-name` covers the Audio Unit, whose plist clap-wrapper composes from the ASCII `OUTPUT_NAME` and then describes as a wrapper. Change one, change all four. The ASCII `Fosforo` that names files, binaries, and `CFBundleExecutable` is a separate string and must not follow.

The manufacturer name and display name are free metadata. See the plan's identifiers section before touching any of them.
- **Shader validation is deliberately not part of `zig build test`,** so the build stays hermetic (ADR 0009).
- **`zig build test` is a Debug build, and a module reached only from a `test` block is never type-checked by `zig build`.** Two independent facts, both easy to assume the other way round, and each with a consequence. `standardOptimizeOption` declares no default and CI's reusable workflow passes no `-Doptimize`, so the ordinary test run is Debug: `std.debug.assert` is live there and gone from the `--release=fast` build that ships, which is exactly why every trust boundary in this project refuses rather than asserts, and why `state.zig`'s `TestStream.seed` reaches for `@panic`.

  **The suite now runs in three modes and this bullet's first clause is the default rather than the whole story** ([#94](https://github.com/cboone/fosforo/issues/94)). `zig build test` still follows `-Doptimize`, so it is Debug unless told otherwise; `zig build test-safe` and `zig build test-release` are _pinned_, to `ReleaseSafe` and to `ReleaseFast`, and a `test-modes` job runs both. `addTestStep` in `build.zig` is where the reasoning lives. Cold on this machine the three cost 5.49 s, 9.65 s and 10.68 s, and the test binaries are 4,630,248, 1,912,376 and 1,928,504 bytes; `strings -a` finds `reached unreachable code` in the first two and not the third, which is the free positive control that the modes really differ. **The three are additive and the Debug one cannot be retired**, which is measured rather than argued: `shader.zig`'s "nothing is read from disk in a test build" asserts `!shader.live`, and `live` is `builtin.mode == .Debug and !builtin.is_test`, so outside Debug the first clause has already decided it. Planted, `zig build test` fails 1 of 285 while both release steps report 285 of 285.

  **Four things #94 established that are worth not rediscovering.** The `ci` job **cannot** host the step, because it is a reusable workflow from another repository with no hook for one, which is why `test-modes` is its own job. `assert(fba.end_index == 0)` in `plugin.zig` is **vacuous in every mode**, not merely Debug-only: `scratchBytes` returns 0 unconditionally and both `passThrough` and `tap` take the allocator and discard it, so it is a tripwire for a future step that wants scratch rather than a live check, and it is the wrong example to reach for when arguing about assertions. **Zig's `std.debug.assert` is an ordinary function, so its argument is evaluated in every optimize mode** — the C bug class of putting work inside an assert does not exist here, confirmed by planting `buildPalette`'s whole loop into an assert argument and watching all three modes stay green; what ReleaseFast strips is the `unreachable` branch, not the call. And **an assertion is worth least in the mode where it is the only thing left**, which the `Ring.init` plant quantified: deleting `if (minimum_capacity == 0) return error.EmptyCapacity;` makes Debug print `panic: reached unreachable code` with a trace through `std/math.zig:1219`, makes ReleaseSafe print the same panic with the trace optimized down to the test runner and no `std.math` line at all, and makes ReleaseFast print `terminated with signal TRAP` — no message, no trace, nothing named. That is the executable form of "refuse rather than assert".

  Separately, Zig analyzes `test` declarations only in a test build, so a module named solely in `src/main.zig`'s test block is parsed but never checked by a plain `zig build`: a type error in it passes the `Build`, `clap-validator` and `clap-wrapper` jobs and fails only `Test`. `src/dsp/ring.zig` was in that state until `src/clap/plugin.zig` imported it (#36). **Acquiring a caller only half fixes this, and the half it leaves is the surprising one:** Zig's analysis is lazy per declaration, not per module, so a plain `zig build` now checks `Ring.init`, `deinit`, `write` and `clear`, which the plugin calls, and still does not check `Ring.read` or `Ring.capacity`, which only tests call. A `pub fn` nothing reaches is not analyzed however the file it lives in was imported. Both halves were measured rather than reasoned about: a type error planted in `capacity` builds clean, and the same error in `write` fails the build. The build cache cannot answer this for you, because a manifest lists the files the compiler read rather than the ones it checked; the check that does answer it is a type error in the specific declaration you care about, which still produces a binary if nothing calls it. **[#95](https://github.com/cboone/fosforo/issues/95) closed half of this, and the half it left standing is the half measured above.** Every module `zig build test` compiles now carries a `testing.refAllDecls(@This());`, plus one call per public container type declared at file scope, so a `pub fn` with no caller anywhere fails `Test` where it used to pass everything: `palette.dominantToTonemapped` was live in exactly that state and no build of any kind compiled it. **A plain `zig build` is unchanged**, because `refAllDecls` opens with `if (!builtin.is_test) return;`, and the plant above was re-run rather than reasoned about: a type error in `dominantToTonemapped` still produces a signed `.clap` and fails only `Test`. Two things stay lazy in both builds, and both were measured the same way. **Private declarations**, because `std.meta.declarations` returns public ones only, so the same plant on a private method of `Ring` builds clean while the public version fails. And **containers nested more than one level deep**, because `refAllDeclsRecursive` was removed in Zig 0.16 and `refAllDecls(@This())` reaches the _type_ `Ring` rather than its methods, which is why each file names its own types individually rather than relying on the first call. A type with no declarations today is named anyway: the rule "types that currently have methods" reopens the hole in the file that adds one. `src/main.zig` holds the check that stops the convention lapsing, over the **23** files a test build compiles; `src/smoke.zig` is the 24th and is outside all of it, which is [#92](https://github.com/cboone/fosforo/issues/92)'s. That count was twenty when #95 wrote it and moves with the tree — #92 added `gpu/verdict.zig` and #93 added `gpu/metal/reload.zig` — so **re-count it rather than adding to whatever it reads**; the check itself ties the two lists together, so a module added to one and not the other fails `Test`.

- **`src/dsp/ring.zig`'s memory ordering is verified by `zig build ring-race`, one of the two checks here that cannot run on this machine.** The release store in `write` and the acquire load in `read` are the whole of ADR 0010's protocol, and every test of that module is single-threaded, so replacing the release with a `.monotonic` store passes all 144 tests. `src/ring_race.zig` runs the two on real threads under Thread Sanitizer, and the reason that is not the stress test it looks like is the whole point: TSan does not look for corruption, it builds a happens-before graph and reports two threads reaching one address with no edge between them, so a weakened store is flagged whether or not the hardware ever reorders. Zig 0.16 links a `-fsanitize-thread` binary on `aarch64-macos` that segfaults before `main`, re-measured on 0.16.0 rather than inherited, so this runs on Linux in the `race` job and `zig build ring-race` refuses on a macOS host with a message saying where it does run. **Three things about it are load-bearing and each looks optional.** The harness has a deliberately weakened second arm that must be flagged, because everything the real arm proves is an absence and `scripts/race-check` cannot tell a correct ring from an instrument that was never running without it; the writer is bounded so it cannot lap the reader, because the torn-window path this design accepts on purpose is a data race in TSan's model and would fail the job at random; and a source canary in `ring.zig` reads the five atomic operations as text so the weakening also fails `zig build test` on the machine you are on, which the sanitizer job cannot do for you. See ADR 0016 before changing any of them. **That canary is now the shape rather than the instance**, which is [#90](https://github.com/cboone/fosforo/issues/90): its two helpers live in `src/canary.zig`, five files reach them, and the two flaws it carried are fixed there once rather than copied. A statement is matched **trimmed**, so re-indenting one into an `if` block is a wash rather than a failure, and a line whose trimmed text begins with `//` is not a statement line at all, so a new doc comment naming `self.cursor.load` cannot break a count. That second property is not only defensive: it is what makes `mentions(code, "Threaded.init") == 0` expressible in a file whose docstring names `Threaded.init` twice in order to forbid it. `canary.statedBefore` is the one thing counting cannot do, and `Mailbox.take` in the renderer is why it exists: its two statements are individually correct in either order, and reversing them hands the render thread three pipeline pointers drawn from two different compiles. **Drawing the trace still does not close this**, which is worth knowing because two plans in `docs/plans/done/` say it would: a weakened store's visibility window is nanoseconds against a window that lags 20 ms and redraws sixty times a second, so a sine looks like a sine either way. The third plan in that chain, `2026-08-19-read-a-trailing-window-and-upload-it-across-the-seam.md`, says the opposite at length and is the one that ended the hand-offs.
- **`zig build gate-race` does the same for the editor's teardown barrier, and the rule it establishes is what decides whether anything else here can have an arm at all.** `Gate` lives in `src/clap/gate.zig` rather than inside `src/clap/gui.zig` for exactly one reason: that file reaches CLAP's translated headers, `objc` and CoreVideo and cannot be built for Linux, and `Gate` reaches nothing but `std`. **A Thread Sanitizer arm can discriminate an ordering only where that ordering guards _non-atomic_ memory**, because TSan reports two threads reaching one address with no edge between them and two relaxed atomic accesses to one word are not a race in that model. So `src/gate_race.zig` stands a plain `[]u64` in for the eleven fields `Editor.destroy` writes after `close` returns and `Editor.tick` reads from inside the gate; without that payload both arms come back clean and the harness measures nothing. **Three details are load-bearing and each looks incidental**, so each has its own canary rather than a comment: the rendezvous flag is `.monotonic` on both sides, because release-acquire there supplies the very edge under test; the closer writes the payload **before** `join`, because `join` is itself an edge; and the replica differs from the real `Gate` in exactly one ordering, because a control that quietly stopped controlling anything is the one failure the Linux job cannot see. **A fourth is `hold_spins`, and it exists because the check went red rather than because anyone predicted it:** how long the holder takes to _leave_ is itself the cost of the ordering being varied, since TSan instruments a release store as a full clock publish and a relaxed one as almost nothing, so without an explicit hold the weakened arm's holder was gone before the closer arrived and `contended` read 0 against the clean arm's 195. Both arms now contend in 256 rounds of 256, 0.17% apart on spins. **Do not fix a `NeverContended` failure by relaxing that assertion**, which is the whole thing it is there to refuse. **All five of `Gate`'s orderings were planted in the real type and only two flag**, `leave`'s release and the acquire load in `close`'s spin, which are the two halves of one edge; `enter`'s acquire, `enter`'s refusal store and `close`'s `fetchOr` all come back clean. **The issue that filed this work named `enter`'s acquire for the control arm**, which is one of the clean three, so building it as filed would have produced a control that reported nothing and a failure reading as a broken sanitizer. ADR 0016's #91 amendment carries both tables with their run ids.
- **`Pending` has no sanitizer arm and cannot usefully have one, which is measured rather than conceded.** Its whole message is packed into one `u64` (`gui.zig:167-173`), `take` reads nothing else, and `tick` uses only the value returned, so a weakened `post` leaves two relaxed atomic accesses and nothing to report. That was established with a 2x2 rather than asserted: with one thing riding alongside the word a weakened `post` is flagged, and without one it is not. **The first attempt at that control was wrong in a way worth knowing**, because it wrote the payload before spawning the taker and thread creation is itself a happens-before edge, so both payload arms came back clean and proved nothing. What guards `Pending` is therefore its canary in `gui.zig` and its unit tests, and the `gpu.Size` extraction #91 proposed in order to enable an arm was not needed and not done. **If a field is ever added that the `u64` does not carry**, a pointer to a heap-allocated update most obviously, the release becomes load-bearing in a way a sanitizer could see, and that is the moment to revisit this rather than cite it.
- **`sanitize_thread` alone produces a Thread Sanitizer binary that detects nothing and says nothing about it, and `use_llvm = true` is what fixes it.** Zig 0.16 defaults to its self-hosted x86_64 backend for a Debug build on Linux, and that backend **links the sanitizer runtime while emitting none of its instrumentation**. The binary is the right size, it builds, links, runs, exits zero and reports no races, whatever you race inside it. There is no warning, because nothing is wrong from the compiler's point of view: you asked for a runtime and you got one. Measured by disassembling both builds of the same file rather than inferred: the default backend stores straight to the shared word, and adding `-fllvm` emits a `__tsan_write8` call immediately before that same store. This is the reason `scripts/race-check` runs its deliberately-racing arm **first** and refuses to read anything into the subject's silence until that arm has been flagged, and it is not a hypothetical: the first CI run of the race job, when it was still named `ring-race`, reported a clean control, which is precisely the false pass the ordering exists to catch. Anything else here that ever acquires a sanitizer needs the same flag and the same kind of control.
- **`b.dependency` runs a dependency's `build` function at configure time, so a step that needs none of it can still be killed by one.** The first CI run of `ring-race` aborted with `unhandled error` inside zig-objc's `build.zig`, which calls `appleSDKPath` and panics on any OS that is not Darwin, before a single step ran and although the harness's module reaches neither zig-objc nor CLAP. Fetching a dependency's tarball is a cost you pay whatever step you asked for; _describing_ its graph is a failure, and only the second one is fatal, which is the half easy to assume away. `build()` therefore registers `addRingRaceStep` and returns before constructing `Core` whenever the target is not macOS. Everything past that line is macOS-only anyway (ADR 0001), so the early return costs nothing, and it is what makes `zig build -Dtarget=x86_64-linux-gnu` do anything here at all. Anything else that ever needs to build off this platform goes above that return, not below it.
- **A clean `leaks` report is not evidence until you know `leaks` ran.** It exits non-zero whenever it finds anything and it always finds something: AppKit's LaunchServices chatter leaks a few hundred `NSXPCConnection` allocations per run, so its exit code cannot be the gate. `scripts/smoke-leak-check` therefore asserts that the harness passed and that a parseable report exists _before_ it concludes anything from an absence. Match leaked objects by class prefix, never by the framework's public class names: dropping the command queue release in `Renderer.deinit` leaks an object `leaks` calls `AGXG17XFamilyCommandQueue`, and a grep for `MTLCommandQueue` reports that planted leak as clean.
- **`leaks` cannot see a leaked `MTLBuffer` at all, and this was measured rather than reasoned about.** Dropping the release of the window buffer ring in `Renderer.deinit` and running the harness 60 times produces a report `scripts/smoke-leak-check` calls clean, while the _same_ omission applied to the command queue is caught in the same run. The leak is real: peak RSS across 200 cycles goes from 47.7 MB to 57.7 MB, and none of the 234 leaked classes in the report is a buffer under any name. `leaks` walks the malloc heap, and a Metal buffer's storage is not in it. This is a sharper form of the class-prefix gotcha above: there the right prefix finds the object, here there is no object to find. So the backend counts its own, through `live_windows` and `gpu.Renderer.liveWindowBuffers`, and `src/smoke.zig` asserts it is zero after the cycle loop; removing the release from `deinit` fails with `WindowBuffersLeaked`. **The counter proves the ring was handed back, not that `release` was sent**, so a `releaseWindows` that stopped releasing would still balance; what it catches is the realistic failure, a path that builds a ring and forgets it, which is what `probe` would otherwise have been. **Any allocation added later should be checked against `leaks` with a planted leak before assuming `smoke-leaks` covers it** — not only a Metal resource that is not a buffer, which is what this sentence used to say and which is how the case in the next bullet went unexamined for four issues.
- **`scripts/smoke-leak-check`'s class check is an allowlist of Objective-C class prefixes, and this project's own allocations do not have a class.** So a plain `c_allocator` leak was invisible to it: dropping `self.history.deinit` from `plugin.destroy` and running 40 cycles leaks roughly 42.6 million bytes against a clean 18,816, and the check called it clean, because `leaks` writes a block with no class as something the `<ClassName 0xADDRESS>` extractor does not match. That is a byte total two thousand times the baseline reported as nothing at all, in the check that was about to become this project's leak gate in CI. `MAXIMUM_LEAKED_BYTES` is what closes it, and the two assertions are complementary rather than one subsuming the other: a leaked command queue is 137,152 bytes, _under_ the bound, and is caught only by its class; a leaked history ring has no class and is caught only by the bound. **The leak count is not a discriminator and must not become one.** Across two runs of that same planted leak the report gave 232 leaks and then 328, against a clean 288 that does not move at all, so the count wanders in both directions while forty megabytes go missing and one of those runs would have read as an improvement.
- **The three leak instruments do not rank the way they read, and the difference is what each is blind to rather than how thorough each is.** #63 was filed proposing a fourth, a peak-RSS slope, and refused after this table was worked out; see ADR 0013 for the refusal.

  | Planted defect                                   | `leaks` | Byte bound | `liveWindowBuffers` | `liveTextures` | `zig build test` |
  | ------------------------------------------------ | ------- | ---------- | ------------------- | -------------- | ---------------- |
  | Command queue or pipeline state never released   | yes     | no         | no                  | no             | no               |
  | Window buffer ring built and forgotten           | no      | no         | yes                 | no             | no               |
  | Accumulation pair built and forgotten            | no      | no         | no                  | yes            | no               |
  | Palette lookup built and forgotten               | no      | no         | no                  | yes            | no               |
  | Either `release` stops being sent, still counted | no      | no         | no                  | no             | no               |
  | A plain allocation this project owns             | no      | yes        | no                  | no             | on tested paths  |

  Four things to carry out of it. **`leaks` walks the malloc heap**, so it sees Objective-C objects and misses both a Metal buffer's storage and a block with no class. **The byte bound sees anything large**, which is why it is the one that reaches this project's own allocations, and it is set 56 times above the observed baseline precisely so it needs no calibration against the machine it runs on. **The counters are exact**, and they are the only instrument for a texture of either kind — `MTLStorageModePrivate` storage is in neither the malloc heap nor the resident set, and #60 measured that a small `Shared` texture is invisible to both as well. They no longer name _which_ resource, which is why the harness's message says "textures" rather than "accumulation textures": a counter that cannot tell two kinds apart must not claim to. **The bottom row is covered by nothing**, deliberately: a `releaseWindows` that decrements without releasing balances every counter and leaks storage no instrument here can see, and chasing it was the whole of what a peak-RSS slope would have added.

- **`shfmt` reads `.editorconfig`, but only when given no parser or printer options.** The shell profile, equivalent to `-i 2 -ci -sr`, lives there because `cmake/narrow-au-resource-usage` was written to a style the repository never recorded, so bare `shfmt` reported an already-consistent file as unformatted. Passing any option from `shfmt --help`'s "Parser options" or "Printer options" groups (`-ln`, `-p`, `-s`, `-i`, `-bn`, `-ci`, `-sr`, `-kp`, `-fn`, `-mn`) makes `shfmt` discard `.editorconfig` wholesale, which means `shfmt -d` is correct and `shfmt -i 2 -d` silently is not. The output-mode selectors are exempt, so `-d`, `-w`, `-l` and `-f` are all safe. Verified per flag, not inferred from the documentation. The scripts in `cmake/` have no extension, so the section names each one directly; a `[*.sh]` section does not match them. **A new shell script must be added to that section.** The `shell` job selects files by shebang, so it lints a new script immediately, while `.editorconfig` styles it only once listed, and the failure that asymmetry produces is `shfmt` reporting tabs against a file that matches its siblings exactly. - **`typos` runs from its own workflow, and that placement is what makes it enforce anything.** `.github/workflows/typos.yml` is separate from `ci.yml` because that workflow ignores `*.md`, `docs/**`, `LICENSE` and the agent config files on both triggers, which is right for a set of macOS builds and exactly wrong for a spell checker: the files it exists to check are the files that would skip it, so a job added there would be green on every pull request that could have failed it. `paths-ignore` is workflow-level rather than job-level, so no job can be exempted from it, and dropping `docs/**` from those lists would run the CMake build on every typo fix instead. Every Action here is pinned by commit and the pins get explained in prose; `typos` skips 40-character hex strings and not 7-character ones, so `91f9abd` reads to it as a misspelling of "and". The second pattern suppresses a span between `<!-- spellchecker:off -->` and `<!-- spellchecker:on -->`, which exists because `typos` has no inline directive at 1.49.0 and a document explaining a spell checker has to be able to spell out what it catches; an unclosed marker suppresses nothing rather than everything after it. **Add to `typos.toml` rather than rewording a word the tool is wrong about,** which is what the `precessing` entry already is: a phase-space loop that slowly rotates exhibits precession, whatever the audio context suggests. **Which of the two tables you add to is not a style choice.** <!-- spellchecker:off -->`extend-words` allows a _word_, and `typos` splits an identifier into words before judging it, so `PNGs` is rejected for the `PN` inside it and an `extend-words` entry keyed on `PNGs` suppresses nothing at all, silently, while one keyed on `PN` would allow that fragment everywhere.<!-- spellchecker:on --> Whole identifiers go in `extend-identifiers`, which is where `PNGs` is, and this sentence sits between the `spellchecker` markers for the reason the paragraph above gives.
- **Prettier fixes Markdown and `markdownlint-cli2` verifies it, and the division of labour is the whole point** ([#85](https://github.com/cboone/fosforo/issues/85), [#106](https://github.com/cboone/fosforo/issues/106)). `.markdownlint-cli2.jsonc` pins `MD060` to `aligned`, which means every table's pipes must line up vertically, and that is by far the easiest rule here to break by hand: prose tables run to 400 characters a cell, so a one-word edit to a row silently unaligns it. **`MD060` has no fixer at any version**, so for four phases the only remedy was hand-padding, and nothing ran the tool anyway: `main` reported 0 findings while a live branch reported 129, of which 127 sat in that branch's own plan file. `.github/workflows/markdown.yml` closes that, on `typos.yml`'s precedent and carrying no `paths-ignore` for its reason. **The fix is** `npm run format`, which aligns every table and whose output satisfies `MD060` exactly; run it before the linter rather than reading findings you were going to regenerate. **`npm ci` first, and that is load-bearing rather than setup boilerplate**: `npx prettier` with no `node_modules` present downloads and runs the _latest_ release, measured at 3.9.6 against the pinned 3.8.1, and `npm run` falls through to a global install if one exists. Both leave you formatting a branch with a tool CI does not check it with, which is this repository's recurring failure wearing a new hat. The workflow is safe because `npm ci` precedes its steps in the same job, and its `Report tool versions` step is what proves the lockfile resolved. **`markdownlint-cli2 --fix` is still forbidden**, and that has not softened: it ignores the file arguments it is given and rewrites every file matching its `globs`, so a run meant to tidy one document reformats all of them. - **`ruff` lints the one Python file here, and nothing else can see it.** `scripts/measure-trace` is the only `.py`-less Python in the tree and the `shell` job cannot reach it: that job selects with `shfmt -f`, which finds shell files by shebang, and `env -S uv run ... python` is not one it knows. The tell in a passing log is `ruff format --check` printing the number of files it read, which must be 1. Two more things are not what you would guess. **ruff's default rule set is wider than the `E4, E7, E9, F` it is usually described as**, and at 0.16.5 it carries pylint's `PLW` and flake8-executable's `EXE`, which is how a `subprocess.run` with no explicit `check=` was found in a script that had been producing numbers for weeks; that is also why the version is pinned, on `typos`' precedent, since the rule set ships inside the binary. And **ruff formats Python fenced inside Markdown**, which would put all 53 `.md` files in its remit; that is excluded, because `ci.yml` ignores `*.md` and `docs/**` on both triggers, so a doc with an unformatted fence could never run the job that would catch it and would instead turn some later Zig change red. **`ruff` does not read `.editorconfig`**, unlike `shfmt`, so the `[measure-trace]` section there and `ruff.toml` are two independent statements of one style, kept in step by hand, with `ruff.toml` as the authority.
- **`--target fosforo_auv2` does not build the CLAP.** Setting `AUV2_MANUFACTURER_CODE` sends `make_clapfirst_plugins` down its explicit-configuration branch, which never adds a dependency from the AUv2 target to the CLAP one. Build `fosforo_all` when both artifacts are wanted. `scripts/build-audio-unit` encodes that, along with configuring only when `build/` is absent, and it is what both `zig build audio-unit` and the `clap-wrapper` CI job run, so the rule cannot be true in only one of the two places.
- **`std.Io` is adopted, narrowly, and `Threaded.init` must never be called.** Zig 0.16 moved `Mutex`, every clock, and `sleep` behind an `Io` instance. `src/platform/io.zig` owns the only one, built with `init_single_threaded`; `Threaded.init` calls `posix.sigaction` on `SIG.IO` and `SIG.PIPE`, and a plugin lives in the host's address space, so that replaces REAPER's or Logic's handlers rather than installing its own. Nothing in the type system stops it and the symptom surfaces in the host, which is why the constructor is named in one place. **The fear that motivated the alternative was measured and was wrong:** `Threaded.io()` names all 113 vtable entries so none can be stripped, but the debug `.clap` already carried 325 `Io.Threaded` symbols before any of this, because `std.debug.print` in `src/clap/log.zig` links the implementation for the debug-only `stderr` mirror. Adopting it for the render meter's clock moved the debug binary by -128 bytes and left the release binary byte-identical, since `monotonicNanos` was reached only from the debug-only `Editor.report` and was stripped with its caller. **#56 ended that half of it and not the half ADR 0015 is about.** The decay reads the clock every frame, so a `--release=fast` binary now imports `clock_gettime_nsec_np` and is **176 bytes** larger, measured by building with and without that one call; `Io.Threaded`'s symbols are still absent from it, which is what the vtable argument was ever about, and `init_single_threaded` is still the only constructor. **Two local primitives are deliberately not covered:** `Gate` in `src/clap/gui.zig`, because `Io.Mutex`'s contended path calls `futexWait` inside a gate `Editor.tick` holds across its whole body, and the libdispatch semaphore in `src/gpu/metal/renderer.zig`, because `std.Io.Semaphore` has `wait` and `waitUncancelable` and no try-wait at all. Both say so at the source. And `extern "c"` still bypasses the deployment-target check, so read the SDK header's availability line before adding another: these are Zig's declarations and no header attribute is ever read (ADR 0015).
- **`CVDisplayLink` is deprecated as of macOS 15 and is kept anyway.** Its replacements, `CAMetalDisplayLink` and `-[NSView displayLinkWithTarget:selector:]`, are macOS 14 and later, and the deployment target is 11.0 in three places. Nothing warns, because `src/platform/displaylink.zig` declares the functions itself and no deprecated header attribute is ever read, so the compiler will not be the thing that tells you this changed. Revisit it with the ADR that raises the deployment target, not incidentally.
- **`show` no longer draws anything, which is why `Renderer.frame` reports an outcome.** It starts the display link, and the first tick arrives on CoreVideo's thread a refresh period later. That silently removed `Renderer.frame` from the smoke harness, which called `show` and `hide` back to back: instrumenting the tick counted zero frames across ten cycles in a passing run. `frame` returns an `iface.Outcome`, `Editor` counts presented frames behind `framesPresented()`, and `src/smoke.zig` waits for the count to advance. If you add an early return to `frame`, give it an `Outcome` that is not `presented`, or the harness will start reporting frames that were never drawn.
- **`CVDisplayLinkStop` does not promise what teardown needs to know.** It stops future callbacks and says nothing about one already running, so `Editor.destroy` closes a `Gate` before freeing anything the tick touches. The gate's single word carries both the closed flag and the count of ticks inside, because checking the flag and entering as two operations is exactly the race it exists to close. Do not replace it with a bare atomic bool.
- **Nothing the render thread waits on may be unbounded, because `Editor.tick` holds the gate across all of it.** `Gate.close` spins until every tick inside has left, on the host's main thread, so any wait `Renderer.frame` can enter becomes a wait the DAW's UI can enter when an editor closes. The in-flight semaphore is therefore a try-wait rather than the canonical `DISPATCH_TIME_FOREVER`: a GPU that never signalled a completion handler would otherwise hang teardown for the life of the process. This bounds rather than eliminates the stall, and the residue is deliberate: `nextDrawable` can still take up to its own one-second timeout before returning nil, so a wedged GPU can stall an editor closing for about a second. Unbounded was the defect; a second is a stutter. Adding a new wait to `frame` means checking it against this.
- **The copy into a per-frame buffer happens inside `Renderer.frame`, after the semaphore wait, and moving it into `upload` would be a defect that only shows under load.** A per-frame buffer is safe to write only once its slot is known free, and the slot is taken by the try-wait at the top of `frame`. `Editor.tick` calls `upload` before `frame`, so an `upload` that wrote the GPU buffer directly would be writing one the GPU may still be reading on exactly the ticks where the wait goes on to fail: the frames dropped under load are the frames that corrupt. It shows as tearing rather than as a crash, which is the kind of thing that gets blamed on the GPU. `upload` therefore lands in a CPU staging array and `frame` copies staging into `windows[slot]`, advancing `slot` immediately after a successful wait. Writing the buffer from `upload` is still possible, but it needs `max_frames_in_flight + 1` buffers and it breaks the moment an upload is skipped, because the buffer it would rebind then holds a window from four encodes ago rather than the last good one. Staging also means a torn read costs nothing: `Editor.readWindow` skips the upload, and `frame` redraws the last intact window.
- **The history buffer's storage belongs to the instance, and `plugin.destroy` must free it after `editor.destroy()`.** `Editor.destroy` closes the `Gate` and spins until no tick is inside it, which is what establishes that the render thread is not partway through `Ring.read`; the free is safe only on that side of it, and swapping the two lines reintroduces a use-after-free in the one window where the editor is still ticking. The reason it is not freed in `deactivate` at all is that a host may deactivate with the editor open, which REAPER and Logic both do when a track is disabled, and there is no gate on that path. That lifetime is also why `history_samples` is a constant rather than a function of the sample rate: `create` runs before any rate exists. `activate` therefore clears rather than reallocates, and that `clear` is now the _only_ thing making a new activation's history fresh, since `Ring.deinit` never touched the cursor and the fresh-`Ring` assignment that used to carry it is gone.
- **`Editor.destroy` resets what the editor owns and deliberately leaves `window` and `history` alone.** Those two are published by `plugin.init` and `plugin.activate` and describe the instance, which outlives any number of editors; a host closing and reopening an editor on an active plugin is ordinary. Clearing them there would leave the second editor reading nothing for the rest of the activation, with no symptom but a trace that never moved. The counters beside them, `presented` and `torn`, go the other way and must be cleared, because a stale count would be the next editor's opening claim.
- **`activate`'s sample-rate bounds are load-bearing now in a way they were not before.** Sizing the history from the rate used to refuse absurd values as a side effect: `Ring.init` rejected anything that saturated a `usize` or rounded down to no slots, so `activate`'s own check only had to keep `nan` out. Moving the allocation to `create` took that away, which is why `min_sample_rate` and `max_sample_rate` exist. They are wide enough that nothing a host could legitimately negotiate is refused; what they exclude is a rate that makes `self.sample_rate` useless to divide by, which phase 3 does.
- **Every early return in `Renderer.frame` has to hand its semaphore slot back.** The slot is taken at the top and handed to the command buffer's completion handler at the bottom; a `defer` covers everything between. Three skipped frames that each swallowed a slot would drain the semaphore to zero and stop the render loop permanently, which reads as "rendering stopped after a busy moment" and is the classic way this pattern fails.
- **The completion block captures the semaphore as an `objc.c.id`, deliberately.** `zig-objc` retains `id`-typed captures when the runtime copies a block to the heap, which is what lets `Renderer.deinit` release the semaphore while frames are still executing on the GPU. Changing the capture to a raw pointer compiles and then signals freed memory whenever an editor closes under load.
- **The render thread may set the layer's drawable configuration but not its frame.** `Renderer.resize` sets `contentsScale` and `drawableSize` inside a `CATransaction`; the layer's `frame` is set from `setFrameSize:` on the main thread in `src/platform/view.zig`. That split is ADR 0010's "the render thread touches Metal only and must never mutate AppKit state", and `platform.assertNotMainThread` in `frame` and `resize` enforces the other direction in debug builds.
- **The runtime view class name carries an address-derived suffix.** `objc_allocateClassPair` returns nil on a name that is already registered, and two copies of this plugin genuinely do coexist in one process when the CLAP and the clap-wrapper Audio Unit are both installed. Reusing the first copy's class would be worse than failing, because its method implementations point into that copy's `__TEXT` and dangle when it unloads. The class is never disposed, since disposing one with live instances is illegal.
- **REAPER accepts `clap.log` messages and discards them.** It implements the extension, so `Log.init` finds it and a host-only design would send every diagnostic into a hole with no visible destination. That is why debug builds mirror to `stderr` as well as calling the host, rather than treating `stderr` as a fallback for hosts that offer nothing. Launch REAPER from a terminal to read them.
- **[`clap-host`](https://github.com/free-audio/clap-host) is where those messages can actually be read, and it is the only host here that shows anything at all from a release build.** It is the CLAP reference host, it implements `clap.log`, and it routes messages into Qt's logging rather than dropping them the way REAPER does. Since the `stderr` mirror is compiled out of a release build, and Logic cannot be launched from a terminal at all, a `--release=fast` plugin otherwise has no readable diagnostic channel anywhere. It is a **manual** tool and nothing else: not a build dependency, not a CI step, not a substitute for a DAW. Build it once, outside this repository, and keep it:

  ```bash
  brew install ninja rtaudio rtmidi   # cmake, qtbase and pkgconf are already present for other reasons
  git clone --recurse-submodules https://github.com/free-audio/clap-host ~/Development/clap-host
  cd ~/Development/clap-host && cmake --preset ninja-system && cmake --build --preset ninja-system
  ```

  Do not install `qt6`: that alias resolves to the `qt` metapackage, while `find_package` asks only for `Qt6Core` and `Qt6Widgets`, both of which are in `qtbase`, and `qtbase` is linked into `/opt/homebrew` rather than keg-only, so no `CMAKE_PREFIX_PATH` is needed. `--recurse-submodules` is load-bearing, since `clap` and `clap-helpers` are submodules and configuring fails without them; `vcpkg` comes along too and the `ninja-system` preset never touches it. All three declare `cmake_minimum_required(VERSION 3.17)`, above CMake 4's floor of 3.5, so CMake 4.4.2 configures with no policy shim. Then, from a worktree:

  ```bash
  ~/Development/clap-host/builds/ninja-system/host/Debug/clap-host -p "$PWD/zig-out/Fosforo.clap"
  ```

  **Because it takes an explicit path, it reads the worktree rather than `~/Library/Audio/Plug-Ins/`,** which sidesteps the provenance hazard above entirely: no install step and no hash comparison, because you named the file. `-p` accepts the bundle directory or the inner binary and both work, but for different reasons than you would guess. A bare `dlopen` on the bundle fails with `not a file`; `QLibrary` is what resolves it to `Contents/MacOS/Fosforo`, confirmed with `DYLD_PRINT_LIBRARIES=1`, so the bundle form depends on Qt rather than on anything about the bundle. The long option is `--clap-plugin`, not the `--plugin` upstream's README claims.

  **The severity mapping is lossy, and one severity vanishes.** `CLAP_LOG_DEBUG` becomes `qDebug()`, `CLAP_LOG_INFO` becomes `qInfo()`, and `CLAP_LOG_WARNING`, `CLAP_LOG_ERROR`, `CLAP_LOG_FATAL` and `CLAP_LOG_HOST_MISBEHAVING` all collapse into `qWarning()`. `CLAP_LOG_PLUGIN_MISBEHAVING` falls out of the switch entirely and prints nothing, so a message sent at that severity is silently discarded by the one host adopted for reading messages. Nothing emits it today; anyone who adds one should know.

  **In a debug build every message appears twice,** once bare from Qt and once carrying the `[fosforo]` prefix from the `stderr` mirror, and that doubling is the tell for which channel you are reading. A release build shows only the bare copies, which is the positive control that the host path works rather than the mirror. `rendering at N Hz` disappears in release for an unrelated reason, `src/clap/gui.zig:629`, so a release run shows the lifecycle messages and no render meter.

  **It exercises more of the editor lifecycle than the issue proposing it claimed.** `create`, `get_size`, `set_parent`, `set_transient`, `suggest_title`, `show`, `hide` and `destroy` all run, which makes it a second opinion on embedding and, unlike the Audio Unit, a caller of `gui->hide`. Grepping its source for `set_parent` finds nothing, because it drives the plugin through clap-helpers' `PluginProxy`, which renames them to `guiSetParent` and the rest; grep the camelCase names or you will conclude it does nothing.

  **It cannot test resizing, and reaching for it to do so is the mistake worth naming.** `set_size`, `can_resize` and `adjust_size` are never called, and `host/main-window.cc` pins the window with `QSizePolicy::Fixed` and `setFixedSize()`, so the user cannot drag it. The one direction it implements is `guiRequestResize`, plugin to host, which this project does not use. It is not a load test either: a minimal Qt example says nothing about multi-instance behaviour or dropouts, and REAPER and Logic stay the tools for that. It also stays manual permanently, because Qt6, CMake, Ninja, rtaudio and rtmidi are precisely the non-hermetic dependency ADR 0009 keeps off the build, and ADR 0013 already assigns automated GUI verification to `src/smoke.zig`.

The window is 960x605 for a 960x540 editor, the extra 65 points being Qt's menu bar.
