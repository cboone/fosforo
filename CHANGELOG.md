## [Unreleased]

### Added

- **The phosphor.** The trace is no longer redrawn from nothing every frame: it deposits additively into a persistent `RGBA16F` ping-pong pair that decays between frames, and a second pass resolves the accumulated energy onto the drawable. Floating point is required rather than preferred, because an 8-bit blend toward black stalls once a value rounds back to the same integer and leaves a ghost trail that never clears. The decay is a provisional per-frame constant until [#56](https://github.com/cboone/fosforo/issues/56) measures elapsed time, and the resolve is deliberately trivial until [#60](https://github.com/cboone/fosforo/issues/60) supplies a tonemap, which means a dwelling beam saturates toward white: the ratio between a fresh deposit and a dwelt-on one is `1 / (1 - decay)`, and no linear mapping into 8 bits shows both ends of it. `Renderer` also remembers its own geometry for the first time, in whole backing pixels computed once, because the accumulation and the drawable are read against each other at integer coordinates and two roundings of one expression would disagree. Two findings came out of verifying it and both are recorded where they will be looked for. **A leaked `MTLTexture` is invisible to `leaks` *and* to peak RSS**, which does not follow from the `MTLBuffer` case where RSS caught it, so the backend counts its own through `liveAccumulationTextures` and that is the only instrument rather than the better of two. And a resolve gain that normalised a stationary trace to phase 2's colour divided every *moving* trace by ten, rendering a sine as a black display; it passed 160 unit tests, both smoke halves, `smoke-leaks`, `clap-validator` and the Metal validation layer, and was found by eye in under a minute ([#55](https://github.com/cboone/fosforo/issues/55), [ADR 0007](docs/adr/0007-renderer-simulates-a-crt.md), [ADR 0013](docs/adr/0013-gui-smoke-harness-as-a-build-step.md)).
- **The trace.** The sample window is drawn over the background as a single aliased line strip, one device pixel wide, which is phase 2's exit criterion and the first thing this project renders that is derived from audio. Deliberately crude: no persistence, no decay, no velocity weighting, no reconstruction, all of which are phase 3 and all of which are easier to judge on how they look once there is a working signal path under them. The one decision here that is not provisional is the vertical axis, which is fixed and absolute: full scale is ±1.0, it draws 5% of the height in from each edge, and a sample beyond it rails visibly rather than being hidden, rescaled, or clipped away. A scope that silently rescales is lying about level, which is the one thing a measurement instrument may not do, so that is now [ADR 0017](docs/adr/0017-absolute-vertical-axis.md) rather than three lines of shader arithmetic anyone could reasonably change. The margin is what carries it: the strip between a full-scale peak and the rail is what makes 0 dBFS and +6 dBFS two different pictures, and the rail sits inside the drawable rather than on its edge because a one-pixel line centred on the framebuffer boundary may rasterize to nothing, which would make a railed signal read as an absent one. The sample count reaches the shader through `setVertexBytes:` rather than a fourth `MTLBuffer`, since Metal copies those bytes at encode time and a fourth buffer would be a fourth resource `leaks` cannot see ([#38](https://github.com/cboone/fosforo/issues/38), [ADR 0017](docs/adr/0017-absolute-vertical-axis.md)).
- The smoke harness now counts windows read and uploaded, and asserts a reopened editor still reads. Issue #38 asked whether `smoke-appkit` could assert more than "a frame was presented", and the answer turned out to be that its existing torn-window assertion was vacuous: `windowsTorn() == 0` is equally satisfied by no read ever having happened, which is what a dropped history pointer or a dropped `setWindow` would produce. `Editor.windowsUploaded` splits "the loop is drawing" from "the loop is drawing the samples", the way `framesPresented` split "running" from "drawing", and four planted defects each trip exactly the assertion that names them. A drawable readback was considered and refused: it would mean dropping `framebufferOnly` from the shipping renderer in every host on every frame so that a check could run in CI, and it needs a golden image pinning a shader phase 3 replaces. Each cycle also destroys and reopens an editor on a still-activated plugin, which is the Logic path and which makes an existing comment in `Editor.destroy` enforceable for the first time ([#38](https://github.com/cboone/fosforo/issues/38), [ADR 0013](docs/adr/0013-gui-smoke-harness-as-a-build-step.md)).
- The render thread now reads a trailing window of history every tick and uploads it across the seam. `Editor.tick` takes a 20 ms window relative to an acquire load of the cursor and hands it to `upload` on `gpu/iface.zig`, which stages it on the CPU; `Renderer.frame` copies staging into a per-frame `MTLBuffer` and binds it. Keeping the upload apart from the trace was the point of splitting it out: a path that neither stalls nor leaks is a claim `smoke-appkit` and `smoke-leaks` can make and a picture cannot. Two decisions in it are load-bearing. **The history's storage takes the instance's lifetime**, allocated in `create` and freed in `destroy` after `editor.destroy()` has closed the `Gate` and spun until no tick is inside, because `deactivate` runs on the main thread and REAPER and Logic both deactivate with the editor open when a track is disabled — managing that race with a second gate was more machinery than deleting it. The cost is that capacity stops being derived from the sample rate, since `create` runs before a rate exists, and becomes a fixed `1 << 18` samples; ADR 0010's margin survives it, a 20 ms window at 192 kHz being 3840 samples against 262144. **The copy into the GPU buffer happens inside `frame`, after the in-flight semaphore's try-wait**, rather than inside `upload`, because a per-frame buffer is safe to write only once its slot is known free: an `upload` that wrote it directly would corrupt exactly the frames dropped under load, which shows as tearing rather than as a crash. Staging also makes a torn read free — `readWindow` skips the upload and `frame` redraws the last intact window ([#37](https://github.com/cboone/fosforo/issues/37), [ADR 0010](docs/adr/0010-lock-free-history-buffer.md), [ADR 0005](docs/adr/0005-metal-behind-a-renderer-seam.md)).
- The history buffer's memory ordering is now verified rather than merely specified. Its release store and acquire load are the whole of ADR 0010's protocol between the audio thread and the render thread, every test of that module is single-threaded, and replacing the release with a `.monotonic` store passed all of them, so nothing in the repository would have noticed the weakening. `zig build ring-race` runs `write` and `read` on two threads under Thread Sanitizer, which is not the stress test it resembles: TSan does not look for corruption, it builds a happens-before graph and reports two threads reaching one address with no edge between them, so a relaxed store is flagged whether or not the hardware ever reorders. It runs on Linux, because Zig links a `-fsanitize-thread` binary on Apple Silicon that segfaults before `main`, which makes this the first check here that the development machine cannot run and the first CI job that is not macOS. Three properties of it are load-bearing and each looks optional: a deliberately weakened second arm that must be flagged, without which a clean result cannot be told from an instrument that was never running; a writer bounded so it cannot lap the reader, because the torn-window path this design accepts on purpose is a data race in the sanitizer's model; and a source canary in `src/dsp/ring.zig` that reads the five atomic operations as text, so the weakening also fails `zig build test` on a Mac ([#44](https://github.com/cboone/fosforo/issues/44), [ADR 0016](docs/adr/0016-verify-the-ring-ordering-with-tsan.md), [ADR 0010](docs/adr/0010-lock-free-history-buffer.md)).
- The audio thread now taps the signal into the history buffer. `process` writes into the `Ring` downstream of the pass-through, and the buffer's memory moves only on the main thread, which is what ADR 0010 allows. As this landed, `activate` sized the ring from the negotiated sample rate and `deactivate` freed it; [#37](https://github.com/cboone/fosforo/issues/37) moved both to `create` and `destroy` to delete a use-after-free, and the entry below carries that reasoning. What is tapped is the left channel of the **output**, and both halves are decisions worth naming because they are awkward to revisit once phase 3 draws from them. One channel, because ADR 0010 describes an analyzer that "passes audio through and taps one channel" and ADR 0012 files stereo monitoring under a lens deferred past v0.1.0; the second channel, when it arrives, is a second `Ring` sharing nothing rather than a sum, which would destroy at capture time exactly what an X-Y vectorscope needs. And the output side, because by the time the tap runs the pass-through has already silenced whatever the input failed to reach, so a host that hands over an unusable input still produces a moving timeline of the silence the track actually carried, rather than a trace frozen on the last good block. A block the host flags as constant is copied in full rather than skipped, since the header is explicit that checking the mask is optional "and this implies that the buffer must be filled with the constant value", and skipping it would both freeze the trace whenever a track went quiet and stop the cursor advancing with the stream, misaligning every window read afterwards. `scratchBytes` still returns zero, now as an answer rather than a stub: the tap copies out of the host's own buffer into storage `activate` already owns, so it has nothing to allocate, and a zero-length fixed buffer is still what turns any future allocation on that path into `error.OutOfMemory` at the call site instead of a heap call on the audio thread ([#36](https://github.com/cboone/fosforo/issues/36), [ADR 0010](docs/adr/0010-lock-free-history-buffer.md)).
- A `reset` clears the history, which is CLAP's own definition of that callback, and it does so as a sequence of ordinary writes of silence rather than by blanking the stored samples in place. The shape is the decision, not the clearing, and it took two attempts to get right. `coherent` compares the cursor before and after a read's copy, so it can only report tearing that cursor *movement* reveals. A `@memset` of the storage under a single cursor store fails that test in both orderings: publish after the fill and a reader whose whole copy lands inside the fill observes the same cursor twice and is told an overwritten window was intact; publish before it and the same hole moves to readers that snapshot during the fill. One store cannot bracket a write as wide as the buffer. `write` is not exposed to this, because it writes *ahead* of the cursor while a reader reads behind it, so the two overlap only when the producer laps, and lapping is what the cursor shows. Doing the clear as repeated writes inherits that property instead of approximating it, and bounds the residual uncertainty at one unpublished chunk, which is what an ordinary audio block already costs. Without a clear at all, a scope would keep drawing audio from the far side of a transport locate, and phase 4's trigger would scan backward into it looking for a threshold crossing ([#36](https://github.com/cboone/fosforo/issues/36)).
- A lock-free circular history buffer, `src/dsp/ring.zig`, carrying one monotonically increasing write cursor that is published with release semantics once per block and read with an acquire load. This is the entire concurrency story between the audio thread and the render thread, and it is deliberately not a queue: a scope wants the most recent window and is perfectly happy to overwrite everything older, so "deliver every item exactly once" is a guarantee that costs complexity to provide and that nothing here wants. Three choices are worth naming. The capacity rounds up to a power of two so the wrap is a mask, which buys nothing for the two operations that exist today, since each wraps at most twice per call, and buys phase 4's backward sample-by-sample scan for a trigger crossing, which is the first caller where the wrap is per-sample. A read of more samples than have been written is zero-padded at the front, which is the case a scope opened before playback starts hits on its very first frame and which draws as a flat line filling in from the right. And `read` reports whether the producer lapped the window during the copy rather than assuming it could not: the margin between a capacity of about a second and a display window of tens of milliseconds is what makes a seqlock retry loop unnecessary, and it is the one assumption the whole structure rests on. It lands with no caller, because the audio-thread tap and the render-thread read are separate issues, and that separation is what makes it the only part of the signal path testable with no host, no GPU, and no window server ([#35](https://github.com/cboone/fosforo/issues/35), [ADR 0010](docs/adr/0010-lock-free-history-buffer.md)).
- `clap-host`, the CLAP reference host, is adopted as a third and deliberately manual verification target, and `AGENTS.md` records the build recipe, the invocation, and what it does and does not cover. It displays `clap.log` rather than discarding it, which gives the project a readable diagnostic channel for the first time: REAPER implements the extension and drops what it is sent, Logic cannot be launched from a terminal at all, and the `stderr` mirror that papers over both is compiled out of a release build, so until now a `--release=fast` plugin could not be asked what it thought it was doing. It also takes an explicit plugin path, so it reads the worktree instead of `~/Library/Audio/Plug-Ins/` and the installed-versus-built ambiguity does not arise. It stays manual permanently, since Qt6, CMake, Ninja, rtaudio and rtmidi are exactly the non-hermetic dependency ADR 0009 keeps off the build and ADR 0013 already assigns automated GUI verification to `src/smoke.zig` ([#32](https://github.com/cboone/fosforo/issues/32), [ADR 0009](docs/adr/0009-runtime-shader-compilation.md), [ADR 0013](docs/adr/0013-gui-smoke-harness-as-a-build-step.md)).
- Rendering is driven by a `CVDisplayLink` tied to the display the editor is on, so frames are paced by vsync rather than drawn once from `show`. The loop stops while the editor is hidden, which keeps several loaded instances from paying for frames nobody is looking at ([#5](https://github.com/cboone/fosforo/issues/5)).
- The editor is resizable, freely on both axes and clamped to a 480x270 minimum. The 960x540 default is a starting size and not a ratio to preserve: the reason it is wide is that a scope's horizontal axis is time, which is an argument for letting someone buy more of it rather than for locking 16:9 ([#5](https://github.com/cboone/fosforo/issues/5)).
- The GUI smoke harness now asserts that frames are actually presented, that a resize survives the render loop, and that hiding the editor stops it. `Renderer.frame` reports an outcome instead of returning nothing, which is the seam signal ADR 0013 said was needed and assigned to this issue. Before it, a build in which every `nextDrawable` returned nil drew nothing and passed every check the project had ([#5](https://github.com/cboone/fosforo/issues/5), [#19](https://github.com/cboone/fosforo/issues/19)).
- A single-slot mailbox carrying resizes from the host's main thread to the render thread, serviced at the top of a tick before anything it invalidates is read. This is the one genuine threading seam in the design (ADR 0010), and it lands now, while the only resource behind the seam is a drawable, rather than in phase 3 when the accumulation textures make the same mistake a use-after-free ([#5](https://github.com/cboone/fosforo/issues/5)).
- The `clap.gui` extension, an `NSView` the host embeds, and a `CAMetalLayer` presenting a frame behind it. This is the first time the whole chain runs end to end: a host asks for an extension, gets a vtable of `callconv(.c)` callbacks, hands over a view through a C union, and receives a drawable painted by a shader compiled from a string at runtime. The deliverable is a dim cleared rectangle rather than anything resembling an oscilloscope, which is what phase 1 is for — getting the chain working once so it never has to be debugged again. Three structural pieces arrive with it and outlive it: the renderer seam at `src/gpu/iface.zig`, defined before any Metal was written behind it; runtime shader compilation, which becomes real rather than hypothetical; and `zig-objc`, which until now was a dependency nothing imported. The editor is a fixed 960x540 here and reports `can_resize` as false, because a resize callback arrives on the main thread and has to reallocate resources a render thread is using, and the mailbox that makes that safe only means anything once a render thread exists ([#4](https://github.com/cboone/fosforo/issues/4), [ADR 0005](docs/adr/0005-metal-behind-a-renderer-seam.md), [ADR 0008](docs/adr/0008-objective-c-glue-via-zig-objc.md), [ADR 0009](docs/adr/0009-runtime-shader-compilation.md)).
- Stereo audio ports, a pass-through `process`, versioned state, and diagnostics through the host, which together turn a plugin that instantiates into one that carries audio. `clap.audio-ports` gives the host somewhere to route signal; `process` copies input to output, so inserting the plugin on a track is transparent; `clap.state` writes a 4-byte magic and a little-endian `u32` version now, and tolerates unrecognized trailing bytes on load, so a project saved against this build still opens once there is real state to persist; and `clap.log` routes messages through the host, because `stderr` is invisible inside most DAWs. The forward-looking piece is the real-time seam from ADR 0010: the DSP path takes an allocator parameter fed by a `FixedBufferAllocator` sized at `activate` over a zero-length slice, so any allocation on that path fails at the call site rather than reaching the heap, and "does the audio path allocate" becomes a fact about the call graph rather than a convention someone hopefully honoured ([#3](https://github.com/cboone/fosforo/issues/3), [ADR 0010](docs/adr/0010-lock-free-history-buffer.md)).
- CLAP plugin factory, descriptor, and instance lifecycle, so the plugin is instantiable by a host for the first time ([#2](https://github.com/cboone/fosforo/issues/2)).
- The permanent CLAP plugin `id`, `com.catamount.fosforo`. Hosts persist this into project files, so it will not change again ([#2](https://github.com/cboone/fosforo/issues/2)).
- A GUI smoke harness, `zig build smoke`, which is the only thing in the project that runs a Metal or an AppKit call rather than type-checking one. It plays the host: a real `NSWindow`, the real `clap_entry`, and the editor opened and torn down repeatedly through the `clap.gui` vtable. Split into a `gpu` half that needs no window and covers runtime shader compilation, which `zig build validate-shaders` cannot prove, and an `appkit` half that covers view embedding and the lifecycle. `zig build smoke-leaks` wraps the second in `leaks --atExit` and fails if anything this project owns survives 400 open and close cycles. Never part of `zig build test`, so the default build stays hermetic ([#19](https://github.com/cboone/fosforo/issues/19), [ADR 0013](docs/adr/0013-gui-smoke-harness-as-a-build-step.md)).
- CI runs the smoke harness on every push. The `gpu` half is required; the `appkit` half runs under `continue-on-error` until a real run settles whether a hosted runner grants an unbundled process a window-server connection. **It does:** the AppKit half has succeeded on every sampled run since, so the question the gating was hedging against is answered, and what keeps `continue-on-error` is now a decision about what may block a merge rather than an open question about the runner ([#19](https://github.com/cboone/fosforo/issues/19)).

### Changed

- The leak check runs in CI, judges total leaked bytes as well as leaked classes, and takes a cycle count from the build. It had never run anywhere but a keyboard, which was defensible while an editor held about 96 KiB of window buffers and stopped being so at #55's 33 MB. Getting it there turned up two things and refused a third. **Its class check was an allowlist of Objective-C class prefixes, and this project's own allocations do not have a class**, so a dropped `history.deinit` leaked roughly 42.6 million bytes against a clean 18,816 and the check called it clean: two thousand times the baseline reported as nothing at all, in the check about to become the leak gate. A byte bound closes it, and the two assertions are complementary rather than one subsuming the other, since a leaked command queue is 137,152 bytes and is caught only by its class. The leak *count* is not a discriminator and now says so: across two runs of that planted leak it gave 232 and then 328 against a clean 288, so one of them would have read as an improvement. **And 400 cycles bought nothing either assertion reads** — across five runs at both depths the report gave 288 leaks for 18,816 bytes four times and 285 for 18,464 once, so tenfold more work moves the figure by under 2% and only run to run, because AppKit's chatter is a fixed startup cost — while costing everything, since the harness is bound by display refresh and 400 cycles now takes 113 s rather than the 51.8 s recorded before #55's four resizes. CI runs 40 through a new `-Dleak-cycles`, under `continue-on-error` on ADR 0013's precedent, since it is the AppKit half with an instrument around it. The **peak-RSS slope check proposed alongside it is refused**, and ADR 0013 carries the reasoning rather than a comment on a check that does not exist: the one defect it demonstrably catches is already caught by `liveWindowBuffers` at 10 cycles and exactly, what remains is the `release`-that-stops-being-sent hole that is equally uncovered for the textures, and it is blind to the `MTLStorageModePrivate` storage that is now the largest thing here. It is a calibrated instrument for a defect an uncalibrated one already catches ([#63](https://github.com/cboone/fosforo/issues/63), [ADR 0013](docs/adr/0013-gui-smoke-harness-as-a-build-step.md)).

- Every step that installs now builds exactly what it installs, copies it to `~/Library/Audio/Plug-Ins`, and prints the hash of what landed, and the Audio Unit is a build step rather than two CMake invocations to remember. Those are one change rather than two, because the old asymmetry is what made the names unreadable: both install steps built the CLAP, neither built the component, so the real distinction between `install-clap` and `install-plugins` was not "one bundle versus two" but "an unverified copy" versus "a verified copy that also picks up a component somebody else built". A worktree where CMake had never run kept whatever `Fosforo.component` another branch had installed, could not overwrite it because nothing had been built to copy, and said nothing about it, so Logic loaded a plugin from a different branch, it rendered, and it read as a pass. That was observed rather than imagined, next to a correctly installed CLAP from the branch under test. `zig build audio-unit` now runs `scripts/build-audio-unit`, which carries the two constraints that were prose in `AGENTS.md`: configure only when `build/` is absent, since CMake regenerates its own build system when `CMakeLists.txt` changes, and build `fosforo_all` rather than `fosforo_auv2`, which does not build the CLAP beside it. The `clap-wrapper` CI job runs the same script from a cold checkout on every push, so neither rule can be true in only one of the two places. `install-clap` drops its inline `cp -R` for `scripts/install-plugins --clap-only` and inherits the hash comparison it never had, leaving one implementation of "copy a bundle and prove it landed"; that script now also reports an installed component this build cannot account for, naming its hash and its modification date, since a component from a fortnight ago beside a CLAP from a minute ago is the whole tell. It reports rather than refuses, because the CLAP-only loop is deliberately the common one. Zig's own `install` step keeps its name, which cannot move, and is re-described: its destination is the entire distinction between it and the two steps beside it, so `zig build --help` now says `zig-out` out loud ([#43](https://github.com/cboone/fosforo/issues/43)).

- `cmake --build` no longer rebuilds, reassembles or re-signs `zig-out/Fosforo.clap`. `cmake/CMakeLists.txt` drives the Zig build itself, because the only thing it wants from Zig is `libfosforo_impl.a`, and it asked for that by running a bare `zig build --release=fast`, which also assembled the bundle and ad-hoc signed it, since the custom target passes no identity. So a CMake build silently replaced whatever `zig build -Dcodesign-identity=` had produced and every check downstream read a different file than the one that had been signed, which `scripts/build-release-bundles` worked around by building the Audio Unit first. It now runs `zig build --release=fast --prefix build/zig impl`, and both halves of that carry weight: the new `impl` step assembles no bundle and signs nothing, and the separate prefix keeps its ReleaseFast archive out of `zig-out/lib`, where it would otherwise race a Debug one from any concurrent Zig build. Measured rather than reasoned about: the CLAP's hash *and* its mtime survive a full `cmake --build`, and `codesign --verify` passes afterwards, which it could not be trusted to before. `b.installArtifact(impl)` goes with it, since nothing reads `zig-out/lib` once CMake has its own prefix, so a plain `zig build` now emits the bundle and nothing else. The optimize-mode split is unaffected and still worth knowing: the installed CLAP is Debug next to a ReleaseFast Audio Unit, which is right for local work and wrong for a release ([#43](https://github.com/cboone/fosforo/issues/43)).

- CI now runs `clap-validator` against the built `.clap` on every push, so the validation that ADR 0003 and `AGENTS.md` both call for is enforced rather than left to whoever remembers to run it locally. The validator is pinned to a commit and built with a pinned Rust toolchain, then cached, so upstream cannot turn CI red without a change here ([#10](https://github.com/cboone/fosforo/issues/10)).
- CI now covers the clap-wrapper-built `.clap` too, not just the Zig-built one. The two share an implementation but not an entry point, so a defect in the clap-wrapper seam used to pass CI silently, and ADR 0003 makes that seam load-bearing. The job that asserted the AU sandbox claims now builds both wrapper artifacts and validates the CLAP, and is renamed from `audio-unit-sandbox` to `clap-wrapper` to match ([#12](https://github.com/cboone/fosforo/issues/12), [#7](https://github.com/cboone/fosforo/issues/7)).
- CI now asserts that every bundle it builds carries a valid signature. For the Audio Unit that assertion is inseparable from the two `Info.plist` checks beside it, because signing seals the plist those checks cover: a signing step that ran too early passes both of them and fails the signature check, and a signing step that was dropped fails only the signature check, so the three together are what pins the order down ([#20](https://github.com/cboone/fosforo/issues/20)).

- CI job timeouts are now set from measured runtimes rather than copied from neighbouring jobs, cutting the worst-case spend on a single wedged macOS job from 45 minutes to 10. Every ceiling sits at roughly 4x the slowest run observed for that job, with the figure and its sample size recorded beside it. The passing path is unaffected; what changes is how long a hung job bills before Actions cancels it, which matters because all but one job runs on `macos-latest` at ten times the Linux rate. `shaders` is a deliberate exception: its ceiling does not budget for the Metal toolchain download, which has never fired on any sampled run and is unmeasured ([#17](https://github.com/cboone/fosforo/issues/17)).

- Supplying a code-signing identity now produces a signature that can actually be notarized. Both signing call sites add `--timestamp` and `--options runtime` whenever the identity is not `-`, because notarization rejects a submission missing either, and an identity on its own was never enough to distribute anything. The two flags follow from the identity rather than being switches of their own, so a distributable signature cannot be half-configured. The default path is untouched and still needs no keychain, no certificate and no network: `--timestamp` would make a plain build reach Apple's timestamp server, and an ad-hoc signature has no certificate whose expiry a timestamp could outlive ([#24](https://github.com/cboone/fosforo/issues/24)).

- A release is now a single signed, notarized, stapled `.pkg` that places both bundles where their hosts scan for them, and the user chooses whether that is the whole machine or just their account. The plugin ships as a `.clap` and a `.component` belonging in two different directories, which is the case installers exist for; `notarytool` also takes a pkg directly and `stapler` can staple one as a single file, neither of which is true of a bare bundle. Three scripts under `scripts/` build it, each independently re-runnable so a rejected notarization does not cost a rebuild, and each asserting what the next one is about to assume: that both bundles carry a Developer ID signature rather than merely existing, that every place the version is written agrees, and that the payload lands where hosts look for it. Signing runs locally and deliberately never in CI, because this repository is public and the alternative is Developer ID private keys in repository secrets ([#24](https://github.com/cboone/fosforo/issues/24), ADR 0014).

### Fixed

- The AUv2 component no longer declares the `resourceUsage` sandbox claims clap-wrapper generates by default, `network.client` and `temporary-exception.files.all.read-write`. The plugin needs neither, and Apple documents the dictionary as mutually exclusive with the `sandboxSafe` flag that was being set alongside it ([#1](https://github.com/cboone/fosforo/issues/1)).
- Every bundle the build produces now carries a bundle signature and passes `codesign --verify`. The linker ad-hoc signs the Mach-O binary on arm64, which is why the plugins loaded, but nothing wrote a `Contents/_CodeSignature`, so all three bundles reported `code has no resources but signature indicates they must be present` and none of them was distributable. clap-wrapper cannot supply this: its only signing calls cover its own generated build helper, and it documents bundle signing as the consuming project's decision. Signing is ad-hoc by default, so a plain build still needs no keychain and no certificate, and the identity is a single override away for an eventual release ([#20](https://github.com/cboone/fosforo/issues/20)).
- The plugin presents the same display name in every format. Logic read `Catamount: Fosforo` and described the plugin as `Fosforo CLAP to AU Wrapper`, a string clap-wrapper writes about itself, while REAPER read `Fósforo`. `make_clapfirst_plugins` offers a single `OUTPUT_NAME` that names the bundle file and supplies the display string at once, so the two concerns are now separated by a `POST_BUILD` pass over the generated plist, and the Audio Unit reads `Catamount: Fósforo` with the CLAP descriptor's own description. Bundle filenames, binaries, and `CFBundleExecutable` stay ASCII `Fosforo` ([#9](https://github.com/cboone/fosforo/issues/9)).
