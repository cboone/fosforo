# Concurrency and canaries

The memory orderings a single-threaded suite cannot see, the sanitizer arms that check them, and the canaries that catch a weakening on the machine you are on. Read this before touching an atomic, a canary, `std.Io`, or a race harness. [ADR 0016](../adr/0016-verify-the-ring-ordering-with-tsan.md) and [ADR 0015](../adr/0015-adopt-std-io-single-instance.md) are the decisions.

- **`src/dsp/ring.zig`'s memory ordering is verified by `zig build ring-race`, one of the two checks here that cannot run on this machine.** The release store in `write` and the acquire load in `read` are the whole of ADR 0010's protocol, and every test of that module is single-threaded, so replacing the release with a `.monotonic` store passes all 144 tests. `src/ring_race.zig` runs the two on real threads under Thread Sanitizer, and the reason that is not the stress test it looks like is the whole point: TSan does not look for corruption, it builds a happens-before graph and reports two threads reaching one address with no edge between them, so a weakened store is flagged whether or not the hardware ever reorders. Zig 0.16 links a `-fsanitize-thread` binary on `aarch64-macos` that segfaults before `main`, re-measured on 0.16.0 rather than inherited, so this runs on Linux in the `race` job and `zig build ring-race` refuses on a macOS host with a message saying where it does run. **Three things about it are load-bearing and each looks optional.** The harness has a deliberately weakened second arm that must be flagged, because everything the real arm proves is an absence and `scripts/race-check` cannot tell a correct ring from an instrument that was never running without it; the writer is bounded so it cannot lap the reader, because the torn-window path this design accepts on purpose is a data race in TSan's model and would fail the job at random; and a source canary in `ring.zig` reads the five atomic operations as text so the weakening also fails `zig build test` on the machine you are on, which the sanitizer job cannot do for you. See ADR 0016 before changing any of them. **That canary is now the shape rather than the instance**, which is [#90](https://github.com/cboone/fosforo/issues/90): its two helpers live in `src/canary.zig`, five files reach them, and the two flaws it carried are fixed there once rather than copied. A statement is matched **trimmed**, so re-indenting one into an `if` block is a wash rather than a failure, and a line whose trimmed text begins with `//` is not a statement line at all, so a new doc comment naming `self.cursor.load` cannot break a count. That second property is not only defensive: it is what makes `mentions(code, "Threaded.init") == 0` expressible in a file whose docstring names `Threaded.init` twice in order to forbid it. `canary.statedBefore` is the one thing counting cannot do, and `Mailbox.take` in the renderer is why it exists: its two statements are individually correct in either order, and reversing them hands the render thread three pipeline pointers drawn from two different compiles. **Drawing the trace still does not close this**, which is worth knowing because two plans in `docs/plans/done/` say it would: a weakened store's visibility window is nanoseconds against a window that lags 20 ms and redraws sixty times a second, so a sine looks like a sine either way. The third plan in that chain, `2026-08-19-read-a-trailing-window-and-upload-it-across-the-seam.md`, says the opposite at length and is the one that ended the hand-offs.

- **`zig build gate-race` does the same for the editor's teardown barrier, and the rule it establishes is what decides whether anything else here can have an arm at all.** `Gate` lives in `src/clap/gate.zig` rather than inside `src/clap/gui.zig` for exactly one reason: that file reaches CLAP's translated headers, `objc` and CoreVideo and cannot be built for Linux, and `Gate` reaches nothing but `std`. **A Thread Sanitizer arm can discriminate an ordering only where that ordering guards _non-atomic_ memory**, because TSan reports two threads reaching one address with no edge between them and two relaxed atomic accesses to one word are not a race in that model. So `src/gate_race.zig` stands a plain `[]u64` in for the eleven fields `Editor.destroy` writes after `close` returns and `Editor.tick` reads from inside the gate; without that payload both arms come back clean and the harness measures nothing. **Three details are load-bearing and each looks incidental**, so each has its own canary rather than a comment: the rendezvous flag is `.monotonic` on both sides, because release-acquire there supplies the very edge under test; the closer writes the payload **before** `join`, because `join` is itself an edge; and the replica differs from the real `Gate` in exactly one ordering, because a control that quietly stopped controlling anything is the one failure the Linux job cannot see. **A fourth is `hold_spins`, and it exists because the check went red rather than because anyone predicted it:** how long the holder takes to _leave_ is itself the cost of the ordering being varied, since TSan instruments a release store as a full clock publish and a relaxed one as almost nothing, so without an explicit hold the weakened arm's holder was gone before the closer arrived and `contended` read 0 against the clean arm's 195. Both arms now contend in 256 rounds of 256, 0.17% apart on spins. **Do not fix a `NeverContended` failure by relaxing that assertion**, which is the whole thing it is there to refuse. **All five of `Gate`'s orderings were planted in the real type and only two flag**, `leave`'s release and the acquire load in `close`'s spin, which are the two halves of one edge; `enter`'s acquire, `enter`'s refusal store and `close`'s `fetchOr` all come back clean. **The issue that filed this work named `enter`'s acquire for the control arm**, which is one of the clean three, so building it as filed would have produced a control that reported nothing and a failure reading as a broken sanitizer. ADR 0016's #91 amendment carries both tables with their run ids.

- **`Pending` has no sanitizer arm and cannot usefully have one, which is measured rather than conceded.** Its whole message is packed into one `u64` (`Packed` at `gui.zig:143`, over the slot at `:136`), `take` reads nothing else, and `tick` uses only the value returned, so a weakened `post` leaves two relaxed atomic accesses and nothing to report. That was established with a 2x2 rather than asserted: with one thing riding alongside the word a weakened `post` is flagged, and without one it is not. **The first attempt at that control was wrong in a way worth knowing**, because it wrote the payload before spawning the taker and thread creation is itself a happens-before edge, so both payload arms came back clean and proved nothing. What guards `Pending` is therefore its canary in `gui.zig` and its unit tests, and the `gpu.Size` extraction #91 proposed in order to enable an arm was not needed and not done. **If a field is ever added that the `u64` does not carry**, a pointer to a heap-allocated update most obviously, the release becomes load-bearing in a way a sanitizer could see, and that is the moment to revisit this rather than cite it.

- **`sanitize_thread` alone produces a Thread Sanitizer binary that detects nothing and says nothing about it, and `use_llvm = true` is what fixes it.** Zig 0.16 defaults to its self-hosted x86_64 backend for a Debug build on Linux, and that backend **links the sanitizer runtime while emitting none of its instrumentation**. The binary is the right size, it builds, links, runs, exits zero and reports no races, whatever you race inside it. There is no warning, because nothing is wrong from the compiler's point of view: you asked for a runtime and you got one. Measured by disassembling both builds of the same file rather than inferred: the default backend stores straight to the shared word, and adding `-fllvm` emits a `__tsan_write8` call immediately before that same store. This is the reason `scripts/race-check` runs its deliberately-racing arm **first** and refuses to read anything into the subject's silence until that arm has been flagged, and it is not a hypothetical: the first CI run of the race job, when it was still named `ring-race`, reported a clean control, which is precisely the false pass the ordering exists to catch. Anything else here that ever acquires a sanitizer needs the same flag and the same kind of control.

- **`b.dependency` runs a dependency's `build` function at configure time, so a step that needs none of it can still be killed by one.** The first CI run of `ring-race` aborted with `unhandled error` inside zig-objc's `build.zig`, which calls `appleSDKPath` and panics on any OS that is not Darwin, before a single step ran and although the harness's module reaches neither zig-objc nor CLAP. Fetching a dependency's tarball is a cost you pay whatever step you asked for; _describing_ its graph is a failure, and only the second one is fatal, which is the half easy to assume away. `build()` therefore registers `addRingRaceStep` and returns before constructing `Core` whenever the target is not macOS. Everything past that line is macOS-only anyway (ADR 0001), so the early return costs nothing, and it is what makes `zig build -Dtarget=x86_64-linux-gnu` do anything here at all. Anything else that ever needs to build off this platform goes above that return, not below it.

- **`std.Io` is adopted, narrowly, and `Threaded.init` must never be called.** Zig 0.16 moved `Mutex`, every clock, and `sleep` behind an `Io` instance. `src/platform/io.zig` owns the only one, built with `init_single_threaded`; `Threaded.init` calls `posix.sigaction` on `SIG.IO` and `SIG.PIPE`, and a plugin lives in the host's address space, so that replaces REAPER's or Logic's handlers rather than installing its own. **The type system already refuses the obvious substitution**, which is worth knowing before deciding what still needs guarding: `Threaded.init` calls `posix.sigaction` and `std.Thread.getCpuCount`, and a container-level initializer must be comptime-evaluable, so writing it at that declaration is a compile error rather than a plugin that ships. What it refuses nothing about is the restructure that reaches the same place, an `= undefined` plus a `setup` function calling `init` at runtime, and the symptom of that surfaces in the host rather than here. That is the gap the canary and the three comptime assertions on the value cover, and it is why the constructor is named in one place. **The fear that motivated the alternative was measured and was wrong:** `Threaded.io()` names all 113 vtable entries so none can be stripped, but the debug `.clap` already carried 325 `Io.Threaded` symbols before any of this, because `std.debug.print` in `src/clap/log.zig` links the implementation for the debug-only `stderr` mirror. Adopting it for the render meter's clock moved the debug binary by -128 bytes and left the release binary byte-identical, since `monotonicNanos` was reached only from the debug-only `Editor.report` and was stripped with its caller. **#56 ended that half of it and not the half ADR 0015 is about.** The decay reads the clock every frame, so a `--release=fast` binary now imports `clock_gettime_nsec_np` and is **176 bytes** larger, measured by building with and without that one call; `Io.Threaded`'s symbols are still absent from it, which is what the vtable argument was ever about, and `init_single_threaded` is still the only constructor. **Two local primitives are deliberately not covered:** `Gate` in `src/clap/gate.zig`, because `Io.Mutex`'s contended path calls `futexWait` inside a gate `Editor.tick` holds across its whole body, and the libdispatch semaphore in `src/gpu/metal/renderer.zig`, because `std.Io.Semaphore` has `wait` and `waitUncancelable` and no try-wait at all. Both say so at the source. And `extern "c"` still bypasses the deployment-target check, so read the SDK header's availability line before adding another: these are Zig's declarations and no header attribute is ever read (ADR 0015).
