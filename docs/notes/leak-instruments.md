# Leak instruments

Three instruments, each blind to something different, and the differences are what matter rather than how thorough each is. Read this before adding an allocation of any kind, or before concluding anything from a `leaks` report.

- **`MTLStorageModePrivate` textures are invisible to `leaks` and to peak RSS both**, which is one instrument worse than the `MTLBuffer` case below and does not follow from it. A leaked buffer moves peak RSS from 47.7 MB to 57.7 MB; a leaked accumulation texture moves it from 44.1 MB to 44.3 MB while leaking nearly two gigabytes, because shared storage is in the process's resident set and private storage is not. `gpu.Renderer.liveTextures` is therefore the only instrument rather than the better of two, and it carries an obligation `liveWindowBuffers` does not: these are rebuilt on every resize that changes the pixel count, so the resize path has to decrement as well. It still cannot catch a `releaseAccumulation` that stops sending `release`, since the count returns either way. **Shared storage is not the escape it sounds like**, which #60 measured rather than assumed: its palette lookup is sixteen kilobytes in `Shared`, and forty cycles leaking one apiece moved the `leaks` byte total from 12,544 to 12,544, against the 640 KiB a visible leak would have added. Same blindness, so it joined this counter and the operation was renamed rather than a ninth being added — the rule ADR 0013 set is to _measure_ separately, not to _count_ separately.

- **A clean `leaks` report is not evidence until you know `leaks` ran.** It exits non-zero whenever it finds anything and it always finds something: AppKit's LaunchServices chatter leaks a few hundred `NSXPCConnection` allocations per run, so its exit code cannot be the gate. `scripts/smoke-leak-check` therefore asserts that the harness passed and that a parseable report exists _before_ it concludes anything from an absence. Match leaked objects by class prefix, never by the framework's public class names: dropping the command queue release in `Renderer.deinit` leaks an object `leaks` calls `AGXG17XFamilyCommandQueue`, and a grep for `MTLCommandQueue` reports that planted leak as clean.

- **`leaks` cannot see a leaked `MTLBuffer` at all, and this was measured rather than reasoned about.** Dropping the release of the window buffer ring in `Renderer.deinit` and running the harness 60 times produces a report `scripts/smoke-leak-check` calls clean, while the _same_ omission applied to the command queue is caught in the same run. The leak is real: peak RSS across 200 cycles goes from 47.7 MB to 57.7 MB, and none of the 234 leaked classes in the report is a buffer under any name. `leaks` walks the malloc heap, and a Metal buffer's storage is not in it. This is a sharper form of the class-prefix gotcha above: there the right prefix finds the object, here there is no object to find. So the backend counts its own, through `live_windows` and `gpu.Renderer.liveWindowBuffers`, and `src/smoke.zig` asserts it is zero after the cycle loop; removing the release from `deinit` fails with `WindowBuffersLeaked`. **The counter proves the ring was handed back, not that `release` was sent**, so a `releaseWindows` that stopped releasing would still balance; what it catches is the realistic failure, a path that builds a ring and forgets it, which is what `probe` would otherwise have been. **Any allocation added later should be checked against `leaks` with a planted leak before assuming `smoke-leaks` covers it** — not only a Metal resource that is not a buffer, which is what this sentence used to say and which is how the case in the next bullet went unexamined for four issues.

- **`scripts/smoke-leak-check`'s class check is an allowlist of Objective-C class prefixes, and this project's own allocations do not have a class.** So a plain `c_allocator` leak was invisible to it: dropping `self.history.deinit` from `plugin.destroy` and running 40 cycles leaks roughly 42.6 million bytes against a clean 18,816, and the check called it clean, because `leaks` writes a block with no class as something the `<ClassName 0xADDRESS>` extractor does not match. That is a byte total two thousand times the baseline reported as nothing at all, in the check that was about to become this project's leak gate in CI. `MAXIMUM_LEAKED_BYTES` is what closes it, and the two assertions are complementary rather than one subsuming the other: a leaked command queue is 137,152 bytes, _under_ the bound, and is caught only by its class; a leaked history ring has no class and is caught only by the bound. **The leak count is not a discriminator and must not become one.** Across two runs of that same planted leak the report gave 232 leaks and then 328, against a clean 288 that does not move at all, so the count wanders in both directions while forty megabytes go missing and one of those runs would have read as an improvement.

- **The three leak instruments do not rank the way they read, and the difference is what each is blind to rather than how thorough each is.** #63 was filed proposing a fourth, a peak-RSS slope, and refused after this table was worked out; see ADR 0013 for the refusal.

  | Planted defect                                   | `leaks` | Byte bound | `liveWindowBuffers` | `liveTextures` | `zig build test` |
  | ------------------------------------------------ | ------- | ---------- | ------------------- | -------------- | ---------------- |
  | Command queue or pipeline state never released   | yes     | no         | no                  | no             | no               |
  | Window buffer ring built and forgotten           | no      | no         | yes                 | no             | no               |
  | Accumulation pair built and forgotten            | no      | no         | no                  | yes            | no               |
  | Palette lookup built and forgotten               | no      | no         | no                  | yes            | no               |
  | Either `release` stops being sent, still counted | no      | no         | no                  | no             | no               |
  | A plain allocation this project owns             | no      | yes        | no                  | no             | on tested paths  |

  Four things to carry out of it. **`leaks` walks the malloc heap**, so it sees Objective-C objects and misses both a Metal buffer's storage and a block with no class. **The byte bound sees anything large**, which is why it is the one that reaches this project's own allocations, and it is set 56 times above the observed baseline precisely so it needs no calibration against the machine it runs on. **The counters are exact**, and they are the only instrument for a texture of either kind — `MTLStorageModePrivate` storage is in neither the malloc heap nor the resident set, and #60 measured that a small `Shared` texture is invisible to both as well. They no longer name _which_ resource, which is why the harness's message says "textures" rather than "accumulation textures": a counter that cannot tell two kinds apart must not claim to. **The bottom row is covered by nothing**, deliberately: a `releaseWindows` that decrements without releasing balances every counter and leaks storage no instrument here can see, and chasing it was the whole of what a peak-RSS slope would have added.
