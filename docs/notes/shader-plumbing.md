# Shader plumbing

What connects the Zig constants to `shaders/scope.metal`, what does not, and what a wrong connection actually costs. Read this before editing the shader or anything that binds to it. [ADR 0009](../adr/0009-runtime-shader-compilation.md) is why the shader is compiled at runtime.

- **Two Metal misconfigurations present a frame and draw the wrong picture, and only the validation layer names them.** An accumulation texture without `MTLTextureUsageRenderTarget`, and a pipeline compiled against a different pixel format from the attachment it encodes into. Both were planted and both pass `smoke-appkit` cleanly; `MTL_DEBUG_LAYER=1 MTL_DEBUG_LAYER_ERROR_MODE=assert zig-out/bin/fosforo-smoke appkit 3` reports each by name. Run it by hand after any change to a pipeline's format, a texture's usage, or a render pass's attachments. It is not in CI and [#63](https://github.com/cboone/fosforo/issues/63) is where that is being decided. #60 is the first change to actually trip that trigger — it moved the drawable's format and added a texture — and it came back clean at `appkit 3`, which is what one constant feeding the layer, the pipeline and the offscreen target buys.

- **Nothing links `TraceUniforms` in `src/gpu/metal/renderer.zig` to the struct of the same name in `shaders/scope.metal`.** Two declarations in two languages, and MSL computes its own offsets. A field added or reordered on one side only does not fail: it draws a plausible trace at the wrong scale, which is the hardest kind of wrong to notice. The `@sizeOf`/`@alignOf`/`@offsetOf` test in `renderer.zig` is the only thing that would catch it, and the binding indices have the same problem and a sharper answer, a check that reads the index out of the declaration carrying it rather than searching for the attribute alone. **Searching for the bare attribute is vacuous here and looked fine for two issues.** `buffer(0)` appears in this shader whatever the Zig side says, so `indexOf("buffer(0)")` passes when two indices are swapped, when a fragment binding drifts while a vertex one still uses the number, and when either of the two fragment textures moves alone. All three were planted against the old test and all three passed it. `bindingIndexIn` anchors on the parameter, and fragment textures, fragment buffers and vertex buffers being three separate index spaces is exactly why three of these constants are zero and why a bare search proves nothing about any of them. **The two have diverged since #77 and the layout is the half left behind**: the indices are now read out of a _reloaded_ shader as well, because MSL states them as literals in the text, while the offsets it computes itself are readable from nowhere. Scalars only in that struct, deliberately: MSL aligns `float2` to 8 and `float4` to 16, so a vector member introduces padding the Zig side would have to reproduce by hand.

- **`zig build validate-shaders` never links a pipeline state, and `zig build smoke-gpu` does.** `metal -fsyntax-only` parses and type-checks and stops there, so a vertex function whose buffer arguments the pipeline cannot satisfy passes it and fails at `newRenderPipelineStateWithDescriptor:`. `probe` shares `buildPipelines` with `init`, so the GPU half of the smoke harness is the check that covers that, and the two jobs are not interchangeable despite both being described as validating the shader.

- **Compiling the shader costs about 40 ms when the source has changed and about 0.14 ms when it has not, and everything anyone reasons about here depends on knowing which case they are in.** Metal caches a compiled library by source hash _across processes_, so the two figures differ by a factor of nearly three hundred and the cheap one is the one an ordinary `set_parent` pays. Measured on this machine by timing `newLibraryWithSource:` and the three `newRenderPipelineStateWithDescriptor:` calls separately, in Debug, over 20 compiles in one process and five separate processes. **A cache miss**, which is what every hot reload is by definition: 34.3 to 43.5 ms with a median of 40.0 ms in the steady state, and 57 to 68 ms for the first compile in a process, the extra being the XPC connection to `MTLCompilerService` being set up. **A cache hit**, which is every launch of an unchanged build after the first on the machine: 0.14 ms total, 0.04 of it the library. In both cases the three pipeline states are noise, 0.17 to 0.80 ms, so `newLibraryWithSource:` _is_ the cost and `Pipelines`' one-library-not-three argument is about the miss. Two things follow. The `Pipelines` docstring's claim that this is "the most expensive thing `init` does and sits on `set_parent`, where a host is waiting" is true only on a cold cache; in the steady state `init` is dominated by the accumulation textures instead. And 40 ms is five vsyncs at 120 Hz, which is what makes compiling on the render thread the wrong answer rather than merely inelegant: `Editor.tick` holds the `Gate` across its whole body, so an editor closed during a compile would busy-spin the host's main thread for the duration.

- **A debug build reloads the shader from disk while a host is running it, and two separate gates keep that out of a release.** `build.zig` hands debug builds the absolute path of `shaders/scope.metal` and hands every other build the empty string; `src/gpu/metal/shader.zig` reads it only when `builtin.mode == .Debug and !builtin.is_test`. **Neither gate substitutes for the other and the split is not belt-and-braces.** The first decides whether the bytes exist in the binary, which is the only way "no shipped binary carries a path into somebody else's worktree" is a proof rather than a claim about the optimizer, and the `clap-wrapper` job asserts that negative with the provenance marker as its positive control. The second decides whether any code runs, which `build.zig` cannot do: an empty option still links the watcher and a 64 KiB buffer into a release build. And only the second can carry `!builtin.is_test`, which is what keeps `zig build test` from reading the filesystem, since a test binary is a Debug build; `src/clap/log.zig:109` is the idiom it copies and one test in `shader.zig` fails if the term is dropped. `FOSFORO_SHADER_PATH` overrides the baked path, which is what survives a `git worktree move` with no rebuild, lets one installed debug bundle be aimed at whichever worktree is being worked in, and makes the whole thing testable. **The fallback rule has one case that is not obvious:** a set-but-missing env path falls back to the _embedded copy_, never to the build option, because you said which file you meant; and a relative env path is refused outright, because a plugin's working directory belongs to the DAW.

- **Compiling a shader on a thread that draws frames now trips an assertion, and that guard is the shape to copy rather than a detail of this one feature.** `platform.assertNotMainThread` keeps the render path unreachable from the main thread; this is the same rule from the side nothing guarded. A debug-only `threadlocal` in `src/gpu/metal/renderer.zig` marks every thread that has entered `frame`, `resize` or `upload`, and `buildPipelinesFromSource` asserts it is unset. **A threadlocal rather than an atomic is the design, not a detail:** several open editors mean several display-link threads, and one process-wide slot would hold whichever marked itself last. It exists because the harness is the wrong instrument for this: 40 ms inside a tick is invisible to a frame counter with a two-second timeout, so a compile that drifted back into the render loop reports a clean run, which was planted and confirmed. [#59](https://github.com/cboone/fosforo/issues/59) has to answer the same question about its own upsampling and inherits the guard for free.

- **A hot-reloaded shader's binding indices are checked and its `TraceUniforms` layout is not, which is half a class closed and the sharper half left open** ([#77](https://github.com/cboone/fosforo/issues/77)). The `TraceUniforms` layout test and the `measure-trace` constants test still read the **embedded** copy at comptime, which is correct: a test about a file that can change between a build and a frame would say nothing, and making `zig build test` read the filesystem is the hermeticity ADR 0009 protects. What changed is that `bindingIndexIn` now takes its source as a parameter, so the comptime test walks `bindings` over the embedded copy and `noteBindings` walks the same table over whatever came off disk. A binding added to that table is covered by both, and neither list can drift from the other because there is one list.

  **What a moved `[[buffer(N)]]` actually costs was measured, and the comment that used to sit above `window_buffer_index` was wrong about it.** It said Metal "reports an unbound buffer at draw time"; it does not. Rendered through `zig build smoke-trace` against three copies of the shipped shader with one index moved apiece, one per index space, every draw completed and the process survived: the vertex `samples` binding at `buffer(3)` gave a flat trace at zero, the palette at `texture(2)` gave a black background, and `trace_fragment`'s uniforms at `buffer(1)` gave no trace at all. The unbound argument reads as **zeros**, so the failure is a confident wrong picture with no diagnostic anywhere. Only `MTL_DEBUG_LAYER=1` names it, and it names it exactly — `Vertex Function(trace_vertex): missing Buffer binding at index 3 for samples[0]` — before asserting, which is the by-hand check the gotcha above already prescribes rather than anything CI runs.

  **That measurement is what decided warn over refuse**, which was the open question #77 owned rather than a detail. Keeping the swap costs a wrong picture the next save fixes, not a wedged GPU, so a mismatch prints a named line and the shader is swapped in anyway. `iface.ShaderStats.binding_mismatches` is what makes that assertable rather than trusted: `zig build smoke-gpu` plants a shader that binds elsewhere and asserts the counter moved _and_ the reload happened, so reversing the decision fails something. The identical-copy arm beside it carries the negative control, without which "the mismatch was noticed" could not be told from "every reload is reported as a mismatch".

  **Two call sites read a source off disk and only one is reachable from a smoke arm.** `buildPipelines` serves the editor opening, which is what `probe` reaches and what the arm above exercises; `Watcher.poll` serves the live swap and is asserted by a canary in `src/canary.zig`'s idiom instead. That is not laziness: an arm on the watcher would have to draw through the mismatch, and while that is survivable it _aborts_ under the `MTL_DEBUG_LAYER=1` invocation the gotchas prescribe, so planting one there would break a documented manual check with a deliberate fixture.

  **The residue, and it is a false positive rather than a hole.** The anchor is a parameter declaration, because searching for the bare attribute is vacuous for the reason the bullet above gives, so renaming a parameter without moving its index reads as a mismatch. It costs one printed line naming the anchor it looked for, never a refused swap.

  **`noteBindings` itself was compiled by no test binary until [#93](https://github.com/cboone/fosforo/issues/93), which is a sharper version of the same lazy-analysis hole.** It is private and was reached only from the two call sites behind `shader.live`, and Zig analyses a private declaration only if something calls it, so `firstBindingMismatch` beneath it had five tests while the pairing — a mismatch found is a mismatch counted — had none, and `refAllDecls` cannot help because it sweeps public declarations only. It now takes the tally as a parameter, which is what gives it a test caller: a planted moved index moves a local `reload.Counters` by one, with the shipped shader as the negative control.

  **`TraceUniforms` layout drift stays open and nothing here can see it.** MSL computes its own offsets, so a field added or reordered on one side only leaves text that still describes the struct correctly and draws a plausible trace at the wrong scale. #51 does not close it: `smoke-trace` measures the **embedded** shader and nothing reloads during a trace run. Closing it needs a readback of a _reloaded_ shader, which ADR 0013 refuses. So if the trace goes wrong immediately after a save and no mismatch line was printed, suspect the struct before the signal path, and run `zig build test`, which rebuilds against the edited file and does check it. **A build-time test comparing the two copies was considered and refused**, because they agree by construction through `@embedFile`'s cache dependency and the only way to write one is as a runtime test that reads the filesystem from inside `zig build test`.

- [#93](https://github.com/cboone/fosforo/issues/93) has landed, which is item 5 of the same program and the same move one layer down. `renderer.zig`'s `Watcher` is `if (shader.live) struct { ... } else struct { ... }` and `shader.live` folds in `!builtin.is_test`, so a test binary took the stub: the real `poll` was not merely untested but **not compiled**, and no test written in `zig build test` could have reached it. The same gate stood over `buildPipelines` and `readShader`, which carried a second copy of the bookkeeping, and the two copies **disagreed** — a compile failure under the watcher moves `rejected` alone, because nothing falls back, while the same failure when an editor opens moves `rejected` _and_ `fallbacks`. That was two pairs of `fetchAdd` calls two thousand lines apart; it is now `src/gpu/metal/reload.zig`, a six-row table with a test that reads it, beside the poll's `seen` state machine. The suite went from 297 tests to 318 and both smoke transcripts are unchanged.

  **The finding is that the issue named an instrument that does not work.** #93 says its acceptance plant, a `poll` advancing `seen` only on success, is one "today only a hand-run `smoke-appkit` would catch". Run against `poll` as it stood, before anything moved: `zig build test` reported 297 of 297 and `zig build smoke-appkit` reported `ok`, with all five hot-reload arms running. **Nothing caught it.** Two more things planting produced. A third site the issue did not name, `noteBindings`, whose counter increment no test binary compiled either, because a private function reached only from gated call sites is never analyzed — `firstBindingMismatch` beneath it had five tests and the pairing had none. And a weakness in `hotReloadPhase`'s fourth arm, which under that defect can pass without the renamed shader ever being read, since it waits on `rejected >= n + 1` while the previous arm's broken file is still being re-rejected four times a second. That one stays open.
