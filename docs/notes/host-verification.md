# Host verification

A host loads what is installed, not what you just built, and this is the single most expensive confusion in this repository. Read this before running the plugin in REAPER or Logic, and before trusting any result one of them gave you. [ADR 0018](../adr/0018-stamp-provenance-without-namespacing-identity.md) is why provenance is stamped at all.

- **A host loads what is installed, not what you just built, and the two are different acts.** `zig build` and `cmake --build` write into the worktree; REAPER and Logic read `~/Library/Audio/Plug-Ins/`. Nothing connects them but a copy someone has to remember to make, and this repository is normally checked out as several worktrees on several branches that all compete for that one location, so the installed bundle belongs to whichever of them copied last. **Confirm provenance before trusting any result a host gave you**, because the failure is silent and reads as a pass: a branch that added a resizable editor was once "verified" against an installed build whose `can_resize` returned false, where the window edge could not be dragged and nothing happening was the only available outcome.

  ```bash
  shasum -a 256 ~/Library/Audio/Plug-Ins/CLAP/Fosforo.clap/Contents/MacOS/Fosforo \
                zig-out/Fosforo.clap/Contents/MacOS/Fosforo
  shasum -a 256 ~/Library/Audio/Plug-Ins/Components/Fosforo.component/Contents/MacOS/Fosforo \
                build/assets/Fosforo.component/Contents/MacOS/Fosforo
  ```

  Two identical hashes mean the host is loading the branch under test; anything else means the result describes some other build. **`zig build install-plugins` builds both bundles, does both copies and both comparisons**, and printing the hashes is the point of it rather than a flourish; reach for it instead of the manual `cp`, which is how the Audio Unit went stale twice.

  **Every bundle now says which worktree built it, which is what the hashes above cannot do.** `build.zig` asks git at configure time and `src/build_info.zig` stamps a `fosforo-build:` line into the binary, so `scripts/read-provenance` answers "whose build is this?" from an installed file with nothing else in hand (ADR 0018). `install-plugins` reports it on every path, including the outgoing bundle it is about to delete, which is the moment this repository's central hazard actually happens and used to happen in silence:

  ```text
  clap: 9d15b5c59185  /Users/…/Fosforo.clap
  clap:   built from chore/add-build-provenance 4105425
  clap:   replaced main 3745df2
  ```

  A hash comparison answers "is this the build I just made?" and can only answer it when this worktree has a build to compare against; provenance answers the other question, which is the one that has cost time. `--check` asserts the marker is present, and CI runs it on the Zig-built CLAP and on both CMake-built artifacts, because the marker survives `--release=fast` only as a claim about the optimizer until something checks.

  **The Audio Unit is the half that goes stale, and the way it does so is by nothing happening.** `install-plugins` builds it now, so the ordinary path is covered, but `install-clap` deliberately does not, and there is no copy to compare when nothing was built. A component installed by some other branch then stays where it is, and a `shasum` of it against `build/assets/` is a comparison against a file that does not exist. That is why `scripts/install-plugins` reports an installed component it cannot account for, with its hash, its modification date _and_ now the branch that built it: a date invites an inference and a branch name ends the question. It was what was missed once already (#43). It is a report rather than a refusal, because the CLAP-only loop is the common one.

  **A symlinked Audio Unit is invisible to macOS, and this is the trap the report exists to catch.** [#22](https://github.com/cboone/fosforo/issues/22) proposed pointing the shared `Components` directory at the active worktree; it was built and refused, because the component is then never registered. Logic's own scan log, `~/Library/Caches/AudioUnitCache/Logs/AUScan*.plist`, is the only instrument (`auval` cannot see this component at all), and it reads 60 Audio Units with `Fósforo` present as a copy, 59 with it absent as a symlink, and 60 again when the copy is restored. **Give the registrar time to settle before relaunching Logic**, or the reading is worthless: a first attempt read 59 for the copy as well, and only its control caught that. Nothing here creates such a link any more, and `install-plugins` detects, explains and replaces one made by hand.

  **One host stream at a time, and that is the working rule rather than a constraint to route around.** Only one worktree verifies against a host at any moment. So the loop is: install, launch, read. No `CLAP_PATH`, no moving bundles aside, no second copy of anything claiming `com.catamount.fosforo`.

  ```bash
  # Launch the binary, not `open -a`: an app started through LaunchServices does
  # not inherit the calling shell's environment, and this is also how clap.log is
  # read at all. Two details in that pipe are load-bearing, see below.
  zig build install-clap
  /Applications/REAPER.app/Contents/MacOS/REAPER 2>&1 | grep --line-buffered fosforo
  ```

  **`2>&1` and `--line-buffered` are both required, and each fails differently.** `src/clap/log.zig` mirrors through `std.debug.print`, which writes to **stderr**, so a bare `| grep fosforo` filters stdout and lets every one of the plugin's own lines through unfiltered — the pipe appears to do nothing. And `grep` block-buffers when its output is not a terminal, so the once-a-second `rendering at N Hz` meter arrives in bursts minutes apart, which reads exactly like a render loop that has stopped.

  **`zig build install-clap` is the whole of the provenance answer.** It builds exactly what it installs, copies it, and prints the hash _and_ the provenance of what landed beside the provenance of the bundle it just replaced, which is why [ADR 0018](docs/adr/0018-stamp-provenance-without-namespacing-identity.md) exists. That is a stronger answer to "am I looking at my build?" than avoiding the shared directory is, and nothing has to be moved aside or restored afterwards.

  **Hot reload needs no environment variable under this rule.** `build.zig` bakes the absolute path of this worktree's `shaders/scope.metal` into every debug build, so a bundle installed from here is already aimed at here and saving the file changes the picture in the running host. `FOSFORO_SHADER_PATH` survives as the escape hatch for a worktree that has been _moved_ since it was built, and for aiming one installed bundle at a different checkout; neither is the ordinary case.

  **`CLAP_PATH` was measured, works, and is deliberately not used.** `clap/entry.h` says a host must query it, `:`-separated and searched recursively, in addition to the standard locations, and REAPER 7.79 honours it: with `~/Library/Audio/Plug-Ins/CLAP` empty, a bundle in a worktree's `zig-out` is found, scanned and instantiated, and each instantiation prints its own provenance line naming that worktree. [#22](https://github.com/cboone/fosforo/issues/22) established that. What it buys is concurrency this project does not want, at the cost of a hazard it does: because the variable is _additive_, both copies claim `com.catamount.fosforo`, and REAPER caches CLAP bundles by filename with no path at all. With both present it loaded the `CLAP_PATH` copy and kept one cache entry — but the specification says nothing about precedence, and that is not something to build a verification run on. Recorded so the measurement is not repeated, not so the route is taken.

  **The Audio Unit has no equivalent and never did.** `AudioComponentRegistrar` scans only the two standard `Components` directories, there is no `AU_PATH`, and the symlink route is closed by the bullet above. So the component is exclusive to one worktree at a time, permanently and by the filesystem rather than by choice — which makes it the one constraint here that cannot be argued with, however the CLAP is loaded.

  **What it is no longer is half the verification, and that clause should not be leaned on.** The Audio Unit's exclusivity was offered as the second reason for the one-stream rule, on the grounds that half of every issue's verification could not parallelize whatever the CLAP did. Counting host mentions in the four most recent renderer plans says otherwise: #55 names Logic nine times against REAPER's nine, and #60, #56 and #57 name it **zero** times each, against six, three and two. **Three consecutive renderer issues verified in REAPER alone**, because #55 was the one that allocated textures and so wanted the AUv2 path, where clap-wrapper destroys an editor rather than hiding it. Logic remains mandatory for anything touching allocation, the editor lifecycle, or multi-instance load, and it is not the routine cost this sentence used to imply. The load-bearing reasons for one host stream are the shared install path and the window server; the Audio Unit is the reason a _Logic_ issue is exclusive, which is a narrower claim.

  **The GPU and the window server are the second exclusive resource**, and they bind independently of the install path. `smoke-appkit` and `smoke-leaks` need them, since two harnesses cannot both open windows and time each other's frames. `smoke-gpu` and `smoke-trace` are exempt, since both acquire a device and neither opens a window, which is what makes them the cheap checks to run while something else holds a window open. Compiling, `zig build test` and `validate-shaders` contend for neither and overlap freely.

  **`clap-host` is what reads a release build's diagnostics, and that is now the whole of why it is here.** It takes an explicit path, so it reads the worktree rather than `~/Library/Audio/Plug-Ins/`, with no install step and no hash comparison to get wrong. Its original billing was concurrency — a second stream confirming a render while another owned the installed bundle — and the one-stream rule above retires that: there is no second stream. What survives is the thing nothing else does, which is that a `--release=fast` plugin has no readable diagnostic channel anywhere else. REAPER accepts `clap.log` and discards it, Logic cannot be launched from a terminal at all, and the `stderr` mirror is compiled out of a release build. It cannot test resizing and is not a load test, so it does not replace REAPER or Logic; what it does mean is that a second stream can confirm a render, exercise the editor lifecycle and read `clap.log` while another stream owns the installed bundle. The build plan's phase 3 section carries the working order this implies. [#22](https://github.com/cboone/fosforo/issues/22) has since relaxed the first constraint through `CLAP_PATH`, which REAPER honours, so `clap-host` is no longer the only way to run a CLAP out of a worktree; there is still no equivalent for the Audio Unit, so that half stays exclusive whatever happens.

- **In the Audio Unit an editor is destroyed rather than hidden.** clap-wrapper's AUv2 view calls `_destroyWindow` from `viewDidMoveToWindow` and from `dealloc`, and never calls `gui->hide` at all, just as it never calls `gui->show`. So `Editor.hidden` is only ever exercised by a CLAP host: in Logic the render loop starts at `set_parent` and stops at `gui->destroy`, which means an open editor window is a running display link and a closed one has no editor behind it at all. That is what makes "N open editors" a sound way to count concurrent render loops there.

- **`auval` cannot see this component, and neither can `AudioComponentFindNext`.** On Darwin 25.5.0 both enumerate only Apple's built-in components, from an ordinary terminal outside any sandbox, while Logic sees every installed Audio Unit including this one. A null result from either is not evidence that the component failed to register. Use a host.

- **`~/Library/Caches/AudioUnitCache` is not the AU registration cache.** Deleting it is the standard advice, it changes nothing, and it is not rebuilt afterwards. The capability data lives in `~/Library/Preferences/com.apple.audio.AudioComponentCache.plist`. Relaunching Logic triggers a rescan; `killall AudioComponentRegistrar` does not, and `launchctl kickstart` on the registrar is refused under SIP.
