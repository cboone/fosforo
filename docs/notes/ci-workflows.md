# CI workflows

What dispatches `ci.yml`, what each pinned tool can and cannot see, and where the runner budget actually binds. Read this before editing anything under `.github/workflows/`.

- **`ci.yml` runs on a pull request against any base, and three gaps survive that.** `branches:` on a `pull_request` trigger reads the pull request's _base_ ref, so the `[main]` this file carried until [#87](https://github.com/cboone/fosforo/issues/87) meant a pull request targeting anything else dispatched none of the jobs this workflow declares, while the page still read green, because `typos`, `gitleaks` and `trufflehog` all carry a bare `pull_request:` and ran. It was never a decision: `git blame` puts the whole trigger block in `b3108ed`, the commit that founded CI here, and the three workflows written since disagree with it. **The fix is measured rather than asserted:** a throwaway pull request based on `ci/stacked-prs` rather than on `main`, created with plain `gh pr create --base`, produced run `34271723634`, `event: pull_request`, `success` in 152 s, with all twelve job names present. **Do not put a job count in prose about this workflow**, which this branch established twice in one day rather than by preference: the count said "the nine jobs" for months against a file that declared eight, Copilot caught it, and [#99](https://github.com/cboone/fosforo/issues/99) then added `actionlint` and made nine right again before the correction had merged. A declared job is not a rollup entry either, since the reusable `ci` expands into `Test`, `Format`, `Build`, `Cross compile` and `Scrut` and the last two skip on every run. The twelve above is anchored to run `34271723634` and stays as measured, on the rule in `.github/docs.instructions.md`; the same workflow after `actionlint` landed shows thirteen names and eleven executions, measured on run `34285826257`. **[#86](https://github.com/cboone/fosforo/pull/86) is not that measurement and could not be**, which is the trap worth naming: its four files were `AGENTS.md`, `README.md` and two under `docs/`, every one of them on the `paths-ignore` list, so dropping the branch filter would not have changed that pull request's outcome at all. `paths-ignore` still reads the `base...head` diff, which for a stacked pull request is the child's own changes against its parent, so a documentation-only stacked branch runs nothing either way and a probe written as one proves nothing. **`push` keeps its `[main]` filter** and must, since a push to a branch with an open pull request already dispatches `pull_request`, so widening it too would run everything twice. **The three gaps are silences rather than failures.** A push to a _base_ branch fires no event on the child, because `synchronize` means the head moved, so a child's green result can describe a merge against an older parent. Auto-retargeting after the parent merges is an `edited` event, which is not in the default activity set, so that fires nothing either. And **a stack already open stays dark after this lands**, because the `on:` block is read from the merge commit: the fix has to reach that ref, by merging `main` into the parent or rebasing it, _and_ the child's head has to move afterwards. Closing and reopening the child is the cheapest unblock, since `reopened` is a default activity type and runs the real merge ref; `workflow_dispatch` is the other and is weaker, because it runs `refs/heads/<branch>` without the base merged in. Rebasing onto `main` and retargeting before merge is the convention that mitigates the first two, and it is a convention rather than a mechanism. **`concurrency` needed no change**, since `github.ref` is `refs/pull/N/merge` on a pull request, so the group is keyed by pull request number and two members of one stack cannot collide. **A native stacked pull request is why the filter looked defensible**, and is how to stack here now: GitHub triggers those as if every pull request in the stack targeted the stack's base, so `branches: [main]` would have run the whole stack. It is public preview and subject to change, it covers only stacks created as such through `gh stack` or the web UI, and one retargeted by hand with `gh pr create --base`, which is what #86 was, is not one, so the trigger cannot be left depending on how a pull request was created. **The cost of all this is queue depth rather than money.** Runner minutes are free on a public repository, measured at `billable.MACOS.total_ms = 0` over nine macOS jobs and three Ubuntu ones, but the documented ceiling is **5 concurrent macOS jobs** on Free, Pro and Team alike, shared across every repository on the account, against more than that many real macOS jobs once `ci / Cross compile` and `ci / Scrut` skip. **Deliberately not a count**, on the rule this note states below and `AGENTS.md` repeats: the last one here said seven and went stale the moment #94 added `test-modes`. So every run is already two waves deep: on run `34267759051` peak concurrency is exactly 5, and `ci / Build` and `ci / Test` are admitted only as `ci / Format` and `shaders` free their slots. Job budgets are unaffected, which is the natural worry and is unfounded, because a `timeout-minutes` starts when the job starts rather than when the run does. A deep stack is what would change that arithmetic, and GitHub's own answer to it, gating expensive jobs on `github.event.pull_request.stack.position`, is deliberately not built here: it would reintroduce "some jobs do not run on some pull requests", which is the failure this bullet exists to record.

- **`actionlint` lints the workflows, and what it cannot see is this repository's own pinning policy.** The `actionlint` job in `ci.yml` pins 1.7.12 with a committed SHA256, on the `shell`, `python` and `typos` precedent, and it closed the fourth instance of a check that is configured, believed to be running, and silently is not ([#99](https://github.com/cboone/fosforo/issues/99)); `actionlint` had sat in the build plan's phase 0 exit criteria and in no workflow since phase 0. It is a job in `ci.yml` rather than its own workflow, and that was confirmed rather than assumed: `typos` is separate because `ci.yml`'s `paths-ignore` lists cover the files it checks, and **none of those patterns matches** `.github/**`, so a workflow edit always triggers this workflow. What still applies is [#87](https://github.com/cboone/fosforo/issues/87), since `pull_request` carries `branches: [main]`. **Measured coverage, each null result sharing a run with a positive control.** It catches a misspelled `runs-on`, an `if:` naming a step id that does not exist, a `needs:` naming a missing job, a `shellcheck` finding in a `run:` block, and both unknown and missing-required inputs on the **local** composite action. It does **not** check `with:` inputs on a SHA-pinned third-party action, because its input database is bundled in the binary and keyed by _tag_: `actions/checkout@v4` with a bogus input is reported and the identical input on `actions/checkout@d23441a4` is not. Nor does it resolve a **remote reusable workflow's** inputs at all. Since every action here is pinned to a commit, which is not negotiable, that whole class is invisible and always will be. **This supersedes a claim in a completed plan.** `docs/plans/done/2026-07-29-tighten-ci-job-timeouts.md` records that `actionlint` "resolves the pinned SHA to check" a reusable workflow's inputs; it does not, in either sense. That file stays as the historical record it is and this bullet is the live statement. **Two operational traps.** It resolves `./.github/actions/...` through the git project root, so run outside a checkout it skips every local-action check **silently and exits 0** — a first attempt at the coverage above produced three false negatives for exactly that reason. And **with no `shellcheck` on `PATH` it skips the `run:` block integration in the same silence**: a planted `SC2086` exits 1 with `shellcheck` present and 0 without, and `-shellcheck=/nonexistent` behaves like the latter. That is why the job installs the pinned 0.11.0 rather than trusting the runner image's 0.9.0, why `SHELLCHECK_VERSION` and `SHELLCHECK_SHA256` moved to workflow-level `env` beside the validator's pair, and why `Report tool versions` prints the `shellcheck` line: it is the only evidence in a passing log that the integration had anything to shell out to. That integration is also the **only** thing linting the embedded shell in `ci.yml`, since the `shell` job selects tracked files by shebang and a `run:` block is not a file.

- **`mlugg/setup-zig` has no `version-file` input, and passing one was inert for five jobs.** Every direct use of it here used to pass `version-file: build.zig.zon`; the action declares `version`, `mirror`, `use-cache`, `cache-key`, `cache-size-limit` and `use-tool-cache` and nothing else, at any version, so it was ignored and every run said so in a warning nothing tracked. **The behaviour was accidentally correct, which is why it survived**: leaving `version` at its empty default is precisely what makes the action read `minimum_zig_version` from `build.zig.zon`, so the right compiler was installed by the fallback path rather than by the input naming the file. Deleting the input therefore could not change which Zig CI installs, and #99 deleted it from all five. Do not restore it. Note the asymmetry that makes this easy to get wrong: `ci.yml`'s `ci` job passes `zig-version-file:` to `cboone/gh-actions`' reusable workflow, which **does** declare it, so one of the two spellings is correct and the other never was. Nothing catches this class, per the bullet above: the action is SHA-pinned, so `actionlint` cannot see its inputs, and the reusable workflow's inputs it does not resolve at all. The only instrument is the warning in a run's log.

- **`clap-validator` is pinned twice over,** at workflow-level `env` in `.github/workflows/ci.yml`: the validator commit, because it is installed from git rather than a registry and a tag can move, and the Rust toolchain that builds it, because the crate declares an MSRV the runner image may stop satisfying. Bump them together and the cache key follows automatically. Warnings do not fail either job: `clap-validator` exits non-zero on failed and crashed tests only, so a `WARNING` line is visible in the log without breaking the build.

- **Two jobs validate a `.clap`, and they share one cached validator.** `.github/actions/clap-validator` is a local composite action that builds and caches it; `clap-validator` and `clap-wrapper` both call it and pass the workflow-level pins. The cache key lives only in that action, because a key written twice can drift, and a drifted key still passes: it just pays a full Rust build every run. On a cold cache both jobs build concurrently and race to save, which is safe, since the loser warns rather than failing.

  **`.github/actions/shellcheck` is the second such action and exists for a sharper version of the same reason.** The `shell` and `actionlint` jobs both need shellcheck, and the version and checksum had already been hoisted to workflow-level `env` on the drift argument, while the five-line install block stayed byte-identical in both. A drifted copy of _that_ is worse than a drifted cache key: the `actionlint` job's failure mode for a missing or wrong shellcheck is a **silent skip** of every `run:` block with a green exit, not a slow build. **The action is checked, unlike a SHA-pinned one**, which is the asymmetry worth knowing when deciding where to put shared steps: `actionlint` resolves a local action through the git project root and validates its `with:` inputs against its declared ones, so a bogus input is reported — measured with a planted one — where the identical mistake on a commit-pinned third-party action is invisible to it.

- **A `timeout-minutes` is measured or it says it is not, and it is never copied from a neighbour.** Most sit at roughly 4x the slowest run observed for that job, with the figure and its sample size in a comment beside it; `docs/plans/done/2026-07-29-tighten-ci-job-timeouts.md` holds the full table and the queries that produced it. Re-measure before changing one, rather than copying a neighbour: that is exactly how the old values propagated, and it left `shell` at 150x. Three details are easy to get wrong. The `ci / *`, `gitleaks / *` and `trufflehog / *` values are `with:` inputs rather than job keys, because those jobs belong to reusable workflows, and one input covers all of a workflow's jobs, so the value is set by the slowest of them. **The exceptions fall into two classes, and both say so at the ceiling itself.** `shaders` and `smoke` are measured and deliberately not 4x: `shaders`' ceiling does not budget for the Metal toolchain download, which has never fired and is unmeasured, so if a runner image ever ships without the toolchain the job fails rather than carrying insurance indefinitely, and the ceiling gets raised once with real data; `smoke`'s stays at 8 rather than tracking 4x its measured 98s, because its worst case is structural rather than statistical, two of its steps being given two and three minutes to be seen wedging on a window server, and a ceiling derived from the observed duration would cut the job off below budgets it grants on purpose. **The other class is a ceiling set before the job had ever run**, which is `python`, `actionlint`, `markdown` and `budget`, all four at the 3-minute floor those Ubuntu static-analysis jobs share and all four carrying an explicit instruction to re-measure from real runs rather than carrying the number onward. That the second class exists at all is why the claim here is not "every one is measured". And **a step-level `timeout-minutes` cannot exceed its job's**, so it is only a label wherever the job would catch the same wedge anyway, as on that download step and on `smoke`'s leak step, and a real bound only on a step that can fail the job by itself, which since #72 is what `smoke-appkit` is. The upstream `Validate inputs` job sets no timeout at all and inherits GitHub's 360; that one is not reachable from this repository. **Both secret-scanning workflows named their caller job `scan` until a drift sweep, and the cost was one duplicated rollup row rather than two.** A reusable workflow's rows read `<caller job>/<inner job>`, so `scan / gitleaks` and `scan / trufflehog` were always distinct while `scan / Validate inputs` appeared twice, identically -- the ambiguous branch-protection target the rule below names. The caller jobs are now `gitleaks` and `trufflehog`, measured off a run's real job names rather than reasoned about.

- **Three assertions in the `clap-wrapper` job grep for Zig declarations and nothing links them to the declaration.** `fosforo-build:`, written with a trailing space, is `build_info.marker_prefix`; `shaders/scope.metal` is `build.zig`'s `shader_source_path`; and `FOSFORO_SHADER_PATH` is `shader.path_env`. The first two are also restated in `scripts/read-provenance` and `build.zig` respectively, and `src/build_info.zig` ties the script's copy to the Zig one by reading it as text — the workflow's copy is a **third** spelling that test cannot see. **The positive control covers the wrong half.** Grepping the marker first proves the binary is readable before the two negatives run, which is what it was written for; it says nothing about whether either needle is still the string the code emits. Rename `path_env`'s value and the "no shipped binary carries the shader-reload path" assertion greps forever for something that can no longer appear, passes, and is vacuous. The cheap mitigation is the comment beside the step naming all three declarations; the real one is a test that reads `ci.yml` the way `build_info.zig` reads `read-provenance`, which is filed rather than done.
