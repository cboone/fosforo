# Linters

Five tools, each with a way of passing without having checked anything. Read this before running or configuring `shfmt`, `typos`, `ruff`, Prettier or `markdownlint-cli2`.

- **`shfmt` reads `.editorconfig`, but only when given no parser or printer options.** The shell profile, equivalent to `-i 2 -ci -sr`, lives there because `cmake/narrow-au-resource-usage` was written to a style the repository never recorded, so bare `shfmt` reported an already-consistent file as unformatted. Passing any option from `shfmt --help`'s "Parser options" or "Printer options" groups (`-ln`, `-p`, `-s`, `-i`, `-bn`, `-ci`, `-sr`, `-kp`, `-fn`, `-mn`) makes `shfmt` discard `.editorconfig` wholesale, which means `shfmt -d` is correct and `shfmt -i 2 -d` silently is not. The output-mode selectors are exempt, so `-d`, `-w`, `-l` and `-f` are all safe. Verified per flag, not inferred from the documentation. The scripts in `cmake/` have no extension, so the section names each one directly; a `[*.sh]` section does not match them. **A new shell script must be added to that section.** The `shell` job selects files by shebang, so it lints a new script immediately, while `.editorconfig` styles it only once listed, and the failure that asymmetry produces is `shfmt` reporting tabs against a file that matches its siblings exactly. Always select files with `git ls-files`, never `shfmt -d .`: `shfmt` does not read `.gitignore`, so walking the tree reaches vendored scripts under `build/` once the CMake build has run, and `shfmt -w .` will reformat them. A fresh CI checkout has no `build/`, so `-d .` passes there and fails locally. The `shell` CI job enforces this and `shellcheck` together, and `.editorconfig` is deliberately absent from that workflow's `paths-ignore` lists so a change to the profile cannot skip the job that checks it.

- **`typos` runs from its own workflow, and that placement is what makes it enforce anything.** `.github/workflows/typos.yml` is separate from `ci.yml` because that workflow ignores `*.md`, `docs/**`, `LICENSE` and the agent config files on both triggers, which is right for a set of macOS builds and exactly wrong for a spell checker: the files it exists to check are the files that would skip it, so a job added there would be green on every pull request that could have failed it. `paths-ignore` is workflow-level rather than job-level, so no job can be exempted from it, and dropping `docs/**` from those lists would run the CMake build on every typo fix instead. The typos workflow therefore carries no `paths-ignore` at all, on the precedent that keeps `.editorconfig` out of `ci.yml`'s lists, and it runs on Ubuntu with a pinned binary and a committed SHA256 for the same reasons the `shell` job does, plus one this tool adds: its dictionary ships inside the binary, so an unpinned upgrade can introduce findings with no change on this side. The other half of making it run is `extend-ignore-re` in `typos.toml`, and both patterns there are load-bearing. Every Action here is pinned by commit and the pins get explained in prose; `typos` skips 40-character hex strings and not 7-character ones, so `91f9abd` reads to it as a misspelling of "and". That is not one finding in one plan file but a class recurring on every documented pin, and it is why this check was failing on `main` at the moment it was written. The pattern is anchored on backticks rather than on a word boundary, so both pin lengths are ignored while a misspelling beside either is still caught. The second pattern suppresses a span between `<!-- spellchecker:off -->` and `<!-- spellchecker:on -->`, which exists because `typos` has no inline directive at 1.49.0 and a document explaining a spell checker has to be able to spell out what it catches; an unclosed marker suppresses nothing rather than everything after it. **Add to `typos.toml` rather than rewording a word the tool is wrong about,** which is what the `precessing` entry already is: a phase-space loop that slowly rotates exhibits precession, whatever the audio context suggests. **Which of the two tables you add to is not a style choice.** <!-- spellchecker:off -->`extend-words` allows a _word_, and `typos` splits an identifier into words before judging it, so `PNGs` is rejected for the `PN` inside it and an `extend-words` entry keyed on `PNGs` suppresses nothing at all, silently, while one keyed on `PN` would allow that fragment everywhere.<!-- spellchecker:on --> Whole identifiers go in `extend-identifiers`, which is where `PNGs` is, and this sentence sits between the `spellchecker` markers for the reason the paragraph above gives.

- **Prettier fixes Markdown and `markdownlint-cli2` verifies it, and the division of labour is the whole point** ([#85](https://github.com/cboone/fosforo/issues/85), [#106](https://github.com/cboone/fosforo/issues/106)). `.markdownlint-cli2.jsonc` pins `MD060` to `aligned`, which means every table's pipes must line up vertically, and that is by far the easiest rule here to break by hand: prose tables run to 400 characters a cell, so a one-word edit to a row silently unaligns it. **`MD060` has no fixer at any version**, so for four phases the only remedy was hand-padding, and nothing ran the tool anyway: `main` reported 0 findings while a live branch reported 129, of which 127 sat in that branch's own plan file. `.github/workflows/markdown.yml` closes that, on `typos.yml`'s precedent and carrying no `paths-ignore` for its reason. **The fix is** `npm run format`, which aligns every table and whose output satisfies `MD060` exactly; run it before the linter rather than reading findings you were going to regenerate. **`npm ci` first, and that is load-bearing rather than setup boilerplate**: `npx prettier` with no `node_modules` present downloads and runs whatever is _latest_ at that moment rather than the pinned release, and `npm run` falls through to a global install if one exists. Both leave you formatting a branch with a tool CI does not check it with, which is this repository's recurring failure wearing a new hat. **That gap is currently zero, and that is the trap rather than the reassurance.** [#119](https://github.com/cboone/fosforo/issues/119) took Prettier to 3.9.6 and [#121](https://github.com/cboone/fosforo/pull/121) took `markdownlint-cli2` to 0.23.2, and both are latest as of 2026-09-09, so an unpinned run agrees with CI by coincidence and goes on agreeing until upstream ships anything. The warning is unobservable rather than untrue, and the demonstration this bullet used to carry, a latest of 3.9.6 against a pinned 3.8.1, is what the bump spent. The workflow is safe because `npm ci` precedes its steps in the same job, and its `Report tool versions` step is what proves the lockfile resolved. **`markdownlint-cli2 --fix` is still forbidden**, and that has not softened: it ignores the file arguments it is given and rewrites every file matching its `globs`, so a run meant to tidy one document reformats all of them. It also cannot fix `MD060`, so it is a hazard with no upside here. **Name the binary rather than the tool**, which is the correction [#115](https://github.com/cboone/fosforo/pull/115) took: there is no `markdownlint` executable in this repository, only `markdownlint-cli2`, so a warning phrased against the former is one a reader can believe does not apply to them.

- **The pins are not self-enforcing, and Dependabot can move one without naming it.** `markdownlint-cli2` went from 0.21.0 to 0.23.2 in [#121](https://github.com/cboone/fosforo/pull/121), whose commit message is about two _indirect_ packages, `js-yaml` and `markdown-it`, and never mentions the direct dependency it bumped to reach them. The one-line `package.json` change was the pin. **That matters here specifically because this tool's rules ship inside it**: a release can introduce or retire findings with no change on this side. **Half of that is already guarded, and by this repository's own design.** `markdown.yml` carries no `paths-ignore`, so #121's own pull request ran both tools over the whole tree at 0.23.2 and passed, which is that workflow doing exactly what it was built to do. **What a green run there does not prove is the other direction.** It establishes no _new_ findings rather than the _same_ findings, so a release that retires or relaxes a rule passes silently, and the pin having moved at all stays invisible behind a message naming only `js-yaml` and `markdown-it`. Both of those were closed by hand in [#119](https://github.com/cboone/fosforo/issues/119): 0.23.2 reports 96 files and 0 issues, matching 0.21.0 exactly; a planted misaligned table still produces 3 `MD060` errors, so the instrument fires rather than having gone quiet; and `node_modules/**` is still load-bearing, since dropping it surfaced `MD060`, `MD036`, `MD045` and `MD047` findings out of dependency READMEs. It came out clean, which is the outcome and not the lesson. **Read the `package.json` diff of any dependency pull request here rather than its message**, because for these two tools the pin and the behaviour are the same thing. Whether to put a mechanism behind that habit is [#122](https://github.com/cboone/fosforo/issues/122); there is no `.github/dependabot.yml` today, since security updates run from repository settings and need none.

- **Three things about that pair are counterintuitive, and each was measured rather than assumed.** **`markdownlint-cli2` lints `node_modules/`** and Prettier does not: one installed package carrying a misaligned table took a clean run from 78 files and 0 errors to 79 and 2, naming a README nobody here wrote, which is why `node_modules/**` is on the `ignores` list and is load-bearing rather than tidy. **`MD049` is `false` rather than `consistent`**, because Prettier writes `_emphasis_` everywhere except inside a word, where CommonMark does not read underscores as emphasis at all, so it correctly leaves `*un*defined` alone at `docs/plans/done/2026-07-29-consistent-display-name-across-clap-and-au.md:33`; `consistent` then takes that asterisk as the file's expected style and reports every underscore after it. A completed plan claims `MD049` is pinned to asterisk. It never has been, that file stays as the historical record it is, and this bullet is the live statement. And **Prettier deleted spaces around inline code spans until 3.9.0** when a code span containing two asterisks sits inside a strong-emphasis span, silently changing what the prose renders as. The pin moved past it in [#119](https://github.com/cboone/fosforo/issues/119), and the version is recorded here rather than the bullet deleted, because every 3.8.x still corrupts the construct and this repository's prose is read by people who are not on the pin. Bisected rather than taken from a changelog: 3.8.1 through 3.8.5 all corrupt the minimal case and 3.9.0 leaves it byte-identical, and the fix is incidental, arriving with the parser swap from `remark-parse` to `micromark` rather than as a targeted patch, which is why it was measured here instead of trusted. The two paragraphs reworded to move the span outside the emphasis stay reworded, since reverting them would spend a diff to re-arm a construct only one version range handles correctly. `<!-- prettier-ignore -->` was the alternative rejected when that reword was made, on the grounds that it holds only in a loose list and `AGENTS.md`'s Gotchas list was tight. **That reason no longer applies to the file you are reading**, whose list is loose, and the marker was measured to hold in it against a control that converts; rewording is still preferred, because it removes the hazard where the marker only pins it.

- **`ruff` lints the one Python file here, and nothing else can see it.** `scripts/measure-trace` is the only `.py`-less Python in the tree and the `shell` job cannot reach it: that job selects with `shfmt -f`, which finds shell files by shebang, and `env -S uv run ... python` is not one it knows. Measured rather than assumed, `git ls-files -z | xargs -0 shfmt -f` does not return that file, so before the `python` job existed the tool producing this project's published numbers was the only unchecked file in the repository. **The job's real failure mode is a vacuous pass**, because ruff discovers Python by extension and this file has none. `extend-include` in `ruff.toml` is what makes it visible, and **a bare `measure-trace` there matches nothing while reporting success**: ruff globs with a literal path separator, so a pattern containing no `/` matches only at the repository root. With an unused import planted in the script, that spelling reported "All checks passed" and `**/measure-trace` caught it. The tell in a passing log is `ruff format --check` printing the number of files it read, which must be 1. Two more things are not what you would guess. **ruff's default rule set is wider than the `E4, E7, E9, F` it is usually described as**, and at 0.16.5 it carries pylint's `PLW` and flake8-executable's `EXE`, which is how a `subprocess.run` with no explicit `check=` was found in a script that had been producing numbers for weeks; that is also why the version is pinned, on `typos`' precedent, since the rule set ships inside the binary. And **ruff formats Python fenced inside Markdown**, which would put every tracked `.md` file in its remit; that is excluded, because `ci.yml` ignores `*.md` and `docs/**` on both triggers, so a doc with an unformatted fence could never run the job that would catch it and would instead turn some later Zig change red. **`ruff` does not read `.editorconfig`**, unlike `shfmt`, so the `[measure-trace]` section there and `ruff.toml` are two independent statements of one style, kept in step by hand, with `ruff.toml` as the authority.

- **`zig-pkg/` is real, is produced by a plain `zig build`, and every ignore list here needs its own entry for it.** Zig 0.16 unpacks `build.zig.zon`'s dependencies into it beside `.zig-cache/` and `zig-out/` — no environment variable and no flag, and the global cache at `~/.cache/zig` gets a copy as well rather than instead. Today that is CLAP's tarball and `zig-objc`, about 4 MB of third-party C headers, Markdown and Zig. It is listed in `.gitignore`, `.prettierignore`, `.markdownlint-cli2.jsonc`, `typos.toml` and `.gitleaks.toml`, five files, because none of those tools reads any of the others' lists.
  **It reads as dead configuration and is not, which is the trap worth recording.** A drift sweep proposed deleting all five entries on the evidence that nothing under `build.zig`, `cmake/`, `scripts/` or `src/` writes the path and `rg` found no reference to it anywhere — and `rg` found none **because `.gitignore` was hiding the directory from `rg`**. The entry under audit was what made the audit's null result look conclusive. Removing them turned up immediately: `npm run format` walked into vendored CLAP Markdown, `markdownlint` reported MD041 on upstream READMEs, and `typos` reported twenty-odd misspellings in `zig-objc` and CLAP headers. **Pair any "this ignore entry is unused" claim with `ls`, not with a grep**, since every tool whose ignore list you are auditing is a tool that hides its own evidence.
