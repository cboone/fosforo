# Measuring a capture

`scripts/measure-trace` is this project's display contract restated in Python, not a general tool, and a screenshot is not written in the framebuffer's colour space. Read this before capturing the editor or quoting any number read out of a capture. **Several figures below are the only copy in the repository.**

- **`scripts/measure-trace` is the instrument that reads a picture, and it is this project's display contract restated in Python rather than a general tool.** Every number in #38's verification came out of it: the level sweep's peak rows, the plateau widths, the period counts, the implied sample values, all of them quoted in this file and in ADR 0017's reasoning as measurements. Point it at a `screencapture -o -x -t png -W` of the editor and it finds the drawable inside the window by itself, then reports rows and the sample values they imply. **Run the copy in the worktree under test**, never one from elsewhere: it restates constants from `src/gpu/iface.zig` and `src/gpu/palette.zig`, and a branch that moves one moves the tool in the same commit, so `main`'s copy is the wrong instrument for a branch. A stale copy lived in `~/Music/fosforo-test-tones/` until 2026-09-02, five times smaller than the committed tool and predating the tonemap, the palette and the centroid; it would have run and produced confident numbers against a mapping the shader no longer uses. That directory now holds a `README.md` saying so, and deliberately holds no copy and no symlink. **It restates constants it does not own**, `trace_full_scale` and `trace_rail` from `src/gpu/iface.zig` and the background, the core exponent, the white headroom, the dwell floor, the four tints and `decay_tau_nanos` from `src/gpu/palette.zig`, and the test in `src/gpu/metal/renderer.zig` that reads the script as text is the only thing linking them; without it a constant that moved would leave the tool confidently reporting against the old mapping. It cannot measure any other oscilloscope, which is why it lives here and not in `audio-tools`, and it is the second half of one procedure: render, play, capture, measure. The first half went the other way, to `audio-tools`, and the bullet below on the test signals carries its new path and the invocation that reproduces this project's set. **Three things it will not tell you.** Under persistence the _lit rows_ are the envelope over the fade rather than this frame's beam, so it prints a line saying so whenever a trail is lit; that is #55 changing what the measurement means rather than a defect. **#57 answered it for the reported peak and trough, which are now centroids**, and the way it first got that wrong is worth keeping: a centroid over the whole _column_ averages the trail, so a 0.5 sine read `+0.0359` — silence — while the lit rows either side implied ±0.505 correctly. The centroid is taken over a column's first and last contiguous lit _run_ instead, which reads ±0.5000 exactly on the same capture. `src/gpu/measure.zig` sums whole columns and is right to, because the harness drives one deposit into a cleared accumulation and there is no trail to average. It cannot see a palette other than the one the shader selects, so `--palette` has to be given to match `palette_row`. And since #56 it cannot see the **refresh rate the capture was taken at**, which now sets the white point: `--refresh` defaults to 120 for this machine's panel, and the two numbers it reaches are affected very differently. The lit threshold barely moves — 120.62 at 48 Hz to 120.33 at 240, three tenths of a byte, though it straddles a rounding boundary so the printed integer goes 121 below about 90 Hz and 120 above. The energy behind the brightest pixel moves a great deal, because inverting the curve near saturation is where the white point does its work: `t = 0.9` reads 5.0 deposits at 60 Hz and 7.0 at 120.

  **That readout is quantized far too coarsely to compare two captures, which #57 established with numbers.** Near `t = 0.9` one 8-bit level is about **0.45 deposits**: `g` of 243, 244, 245, 246 and 247 read 6.80, 7.22, 7.69, 8.21 and 8.77. On top of that the sweep is free-running, so nine captures of _identical_ material at three sample rates scattered from 4.88 to 8.77 — a factor of 1.8 — while the effect being looked for was a factor of 1.4. **Do not use this number to compare captures.** It is a readout of one pixel of one frame, useful for "is anything near the white point", and #57 wasted an arm of its host verification discovering that the hard way. Anything that needs per-frame energy compared across conditions belongs in `zig build smoke-trace`, which drives a single deposit into a cleared accumulation and has neither the dwell, the phase, nor the quantization. Pass `--refresh` before quoting that number off a capture taken at anything but 120.

  **#60 was expected to end the green-channel isolation and did not, which is now a constraint rather than a reprieve.** Every gradient's largest tint component is exactly 1.0, so that channel stays an affine readout of the tonemapped value and the isolation, the guard and every published row survive with re-derived numbers. A re-tint that broke that property would change the meaning of every channel readout in this project at once and fail nothing but the one test written for it. What did change is `--threshold`, which is now **derived from an energy** rather than defaulted to 64: a fixed byte would have silently doubled the persistence envelope this tool reports, from about thirteen frames of trail to twenty-eight, because the sRGB toe moved what a byte means.

  **`zig build smoke-trace` did not retire it, and the two answer different questions.** This one reads a _host's_ screenshot, so it covers the audio path, the ring, the display link and the compositor, and it is the only thing that can tell a live editor from one frozen five seconds ago. The harness renders a window it supplied itself into a texture, so it says nothing about any of that and everything about the shader's arithmetic. Two consequences: #38's host procedure still needs this tool, and the premise its guard rests on is asserted executably by the harness. **That premise changed with #60 and the assertion moved with it**: the deposit no longer carries a colour, so `checkBeamIsOneColour` and its measured ray of 0.2998 and 0.4500 are retired, and `checkDepositIsScalar` asserts instead that the accumulation's four channels agree to 0.00000 at every lit pixel — which is what now makes green the energy. `src/gpu/measure.zig` is its Zig counterpart and deliberately not a port: it reads linear floats rather than an 8-bit picture in a display's colour space, so it needs neither the crop, nor the guard, nor the sRGB conversion. **The half-pixel disagreement between them is gone**, which #57 forced rather than tidied: this tool omitted the pixel-centre term, which was defensible while every assertion was stated in a one-pixel band, and the centroid took the harness's tolerance to a twentieth of a pixel. At that point the offset was ten times the tolerance and the two instruments disagreed about captures they had both measured correctly. Numbers published before #57 were read off a lit edge and are half a pixel from comparable; the ones after it agree exactly.

- **Its guard refuses a capture by colour, its ray became a curve under #60, and its margins are the one thing here still carrying pre-#60 numbers.** The structure survived because the premise generalised: the picture is still a one-dimensional manifold, now a gradient rather than a straight ray, and the dominant channel still inverts it _exactly_ because every gradient's largest tint component is 1.0. So the guard decodes the capture to linear, inverts on that channel, predicts the others through the palette, and re-encodes to compare in levels. **Re-derived from two REAPER captures rather than carried forward**, since the pre-#60 pair was measured against a straight ray: a 100 Hz sine at 0.5 and a level-2.000 sine, both at 1920x1080, read after the sRGB conversion.

  |          | sine 0.5 | level 2.000 |
  | -------- | -------- | ----------- |
  | lossless | 0.02%    | 0.02%       |
  | JPEG q95 | 22.19%   | 34.39%      |
  | JPEG q80 | 30.35%   | 43.70%      |
  | JPEG q60 | 28.34%   | 41.96%      |

  Three orders of magnitude, the same margin the ray had, so the threshold sits 25x above a good capture and 1100x below a recompressed one and needs no calibration against the machine it runs on. A tolerance of 1 would refuse a good capture at 2.01% and 3.49%, which is what makes this a floor rather than a preference.

  **#57 moved the tolerance from 2 to 3, and the old value was refusing good captures.** A falloff skirt puts about a percent of the drawable in the gradient's toe, where the sRGB curve runs at 3294.6 bytes per unit linear, and quantization there reaches three levels where a one-pixel trace only ever reached two. Re-derived against the same two captures the table above uses, each compared with itself recompressed:

  |             | sine 0.5 |        |        |        | level 2.000 |        |        |        |
  | ----------- | -------- | ------ | ------ | ------ | ----------- | ------ | ------ | ------ |
  |             | lossless | q95    | q80    | q60    | lossless    | q95    | q80    | q60    |
  | tolerance 2 | 1.29%    | 38.18% | 45.85% | 42.61% | 0.71%       | 76.56% | 83.99% | 86.32% |
  | tolerance 3 | 0.26%    | 35.30% | 43.37% | 40.09% | 0.15%       | 68.63% | 77.62% | 78.70% |

  **At 2 both good captures are refused**, at 1.29% and 0.71% against a 0.5% line, so this was not a marginal call. At 3 they read 0.26% and 0.15%, leaving the threshold 1.9x and 3.3x above a good capture and 137x below the worst recompression — the same three orders of magnitude the pre-#57 pair had, which is what keeps it needing no calibration against the machine it runs on.

  **`SATURATED` stopped being inert here, which is what it was kept for.** It removed 3774 pixels of a pre-#60 capture and two of a post-#60 one; a post-#57 level-2.000 capture has **8338** of 2,073,600 excluded, because overlap at a wide beam's joints reaches the white point where a one-pixel line did not. The note that predicted #58 would make it matter again was right about the direction and early about the issue. **`SATURATED` is nearly inert and is kept for when it is not**: it removed 3774 pixels of a pre-#60 capture and removes two of a post-#60 one, because almost nothing reaches the white point while `white_headroom` stays provisional.

- **The shade count the guard replaced was a trap #55 set, and #60 retired what remained of it.** The old rule refused any drawable holding more than 32 distinct green levels, on the premise that a lossless capture holds two. True of a trace with no persistence and false the moment one fades: measured on a synthetic capture reproducing the shader's arithmetic, a moving trace with a trail holds **193**, so every good PNG was refused with a message telling the author to recapture it. What replaces it is a fact about the shader. Everything on the drawable is `background + c * beam`, because every deposit is the same colour and the decay multiplies the whole vector, so green predicts red and blue exactly and a fading pixel slides _along_ that ray rather than off it. Chroma subsampling and ringing leave it, and so does a capture taken on a scaled display, which the count could not see at all. The margin is three orders of magnitude: 0.00% off the ray for a lossless capture against 32% to 43% for JPEG at every quality from 95 down to 60. **The count itself is now useless as a trail detector**, because a gradient puts dozens of levels in a single frame whether or not anything is fading; the tool reports it for continuity with #38's tables and reads the lit _rows_ to decide whether a trail is present. **Below that the crop refuses first**, because a quality-40 JPEG destroys the exact `RGB(5, 5, 8)` `find_drawable` looks for, which is why that message names recompression as well as "not the editor".

- **A screenshot is written in the display's colour space, not the framebuffer's, and the discrepancy hides at exactly the value everyone checks.** The plugin writes into a `BGRA8Unorm_sRGB` drawable, so the render-output stage encodes its linear output on write; the compositor treats the stored bytes as sRGB, converts them for the display, and `screencapture` writes _those_ numbers with the display's profile attached. **The stored bytes are the same ones format 80 stored before #60**, which is the whole reason that change was arranged to preserve them — what moved is which linear value produces a given byte, not the byte. On this machine `sips -g profile` reports a capture as **Display P3**, so a screenshot's pixels are not the shader's pixels. **#60's format change is invisible here, which was measured rather than argued**: a `clap-host` capture converted out of the display's profile reads exactly `RGB(5, 5, 8)` across 99.9% of the drawable, the same bytes format 80 put on screen, and silence reads `RGB(255, 255, 255)` on row 539 because a stationary trace dwells to the white point. The error is proportional to saturation and vanishes at black: measured on a REAPER capture at 2018x1778, the background survived as exactly `RGB(5, 5, 8)` while red at green 200-240 read **119 against the 70.9 the beam colour implies**, and 2.74% of the drawable sat off the colour ray. `scripts/measure-trace` therefore converts to sRGB before measuring anything, which takes that capture to 0.0074% off the ray and red to 70.9 against a predicted 70.9. **Two consequences worth carrying.** The pixel-sampling advice above is still correct and is now known to be correct _only_ at the background, which is the one place the conversion is identity, so it can confirm that a render happened and can say nothing about what any brighter pixel became. And **no published row changed**: green barely moves under the conversion, so that capture's peak row is 459 either way and #38's tables stand. What was wrong was chroma, which is all the guard reads.

- **The signals the host verification plays are rendered by a tool in another repository, and only two of its numbers belong to this project.** `scripts/make-test-tones` was a bash-and-ffmpeg script here until [#67](https://github.com/cboone/fosforo/issues/67) deleted it; the generator it became is `tools/test-signals/maketones.py` in [cboone/audio-tools](https://github.com/cboone/audio-tools), parameterised so every frequency, level, duration and gate is an argument. This is the invocation that reproduces this project's twenty files:

  ```bash
  # from the root of an audio-tools checkout, not this one
  uv run tools/test-signals/maketones.py --outdir ~/Music/fosforo-test-tones \
    --levels 0.002 0.010 0.100 0.500 1.000 1.050 1.089 2.000 \
    --saws 0.900 1.100
  ```

  **Everything not named there is a default, and the two flags are the whole of what was ever plugin-specific.** `1.089` is `trace_rail / trace_full_scale` from `src/gpu/iface.zig`, or `0.98 / 0.9`, the ratio at which the trace stops climbing, and `1.050` is the last level below it that does not rail, so the pair brackets that threshold and makes the stalled peak the railing bullet below describes observable at all; the saws at `0.900` and `1.100` straddle the same threshold on a linear ramp, which is what makes a small overshoot legible rather than a matter of opinion; and the `0.002` floor is this display's own one-backing-pixel limit, the arithmetic recorded in the trace-floor bullet below, not a general choice. The six sine frequencies, the hard-panned pair, the click and the gated burst are that tool's defaults. **Nothing measured with the old script needs re-running.** The port was validated against the twenty WAVs still at `~/Music/fosforo-test-tones/` and every file is bit-identical to its ffmpeg counterpart, saws and gated transients included, so #38's tables, the figures quoted in this file, and ADR 0017's reasoning all stand as measurements rather than becoming claims about a generator that no longer exists.

- **A full-screen `screencapture` over-crops, and `find_drawable`'s own failure message points at the wrong culprit.** Measured against a `clap-host` window: the crop came back 2296x1232 for a 1920x1080 drawable, having swept in adjacent dark chrome, and `scripts/measure-trace` refused it at 19.8% off the colour ray with the message about recompression and resampling. The **median deviation was 0.00**, which is the tell that the picture was fine and the bounding box was not. Capture the window rather than the screen. `-W` is interactive and is the ordinary way to do it: `screencapture -o -x -t png -W shot.png`, then click the editor. That is not a workaround, and clicking is only friction rather than a source of error, because `find_drawable` crops from the background rather than from the window's bounds.

  Non-interactively the id comes from `CGWindowListCopyWindowInfo`, which took the same session to 0.02% off the ray and the expected 1920x1080. There is no shell tool for that on a stock macOS, so it is one command:

  ```bash
  # REAPER's on-screen windows, as `id width height title`. One line because a
  # multi-line `python -c` cannot be indented into this list item without Python
  # rejecting the indent, and unindenting it ends the block.
  uv run --with pyobjc-framework-Quartz python -c 'import Quartz as Q; [print(w["kCGWindowNumber"], int(w["kCGWindowBounds"]["Width"]), int(w["kCGWindowBounds"]["Height"]), w.get("kCGWindowName","")) for w in Q.CGWindowListCopyWindowInfo(Q.kCGWindowListOptionOnScreenOnly | Q.kCGWindowListExcludeDesktopElements, Q.kCGNullWindowID) if w.get("kCGWindowOwnerName") == "REAPER"]'

  screencapture -o -x -t png -l <id> verification/shot.png
  ```

  **Captures go in `verification/`**, which is tracked through a `.gitkeep` so the path always exists, with its contents gitignored. They are working artifacts of one session: frequent, a couple of megabytes each, and superseded by the next build. What belongs in the repository is the _numbers_ `scripts/measure-trace` reads out of them, recorded in the issue or the plan. One capture reached a commit before that rule existed, and removing it meant rewriting three commits.

  **The editor is not its own window.** It is an `NSView` REAPER embeds in the window it opens for the plugin, so that is the id to capture and the main window titled after the project is the wrong one. Observed titles in REAPER 7.79: the one to capture is `CLAP: Fósforo (Catamount) - Track 2 "Test Tones"` at 960x593, which is a 960-point editor plus REAPER's own chrome, against `Fósforo - REAPER v7.79 - EVALUATION LICENSE` at 1728x1085 for the project. It is `CLAP:` rather than `FX:` because this is a CLAP; picking by size is the more durable rule. That is also why the capture needs cropping at all. Read `--explain` before recapturing: a high refusal with a zero median is a crop, and a high refusal with a high median is the lossy capture the message describes.
